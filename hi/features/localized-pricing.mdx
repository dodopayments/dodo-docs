## स्थानीयकृत मूल्य निर्धारण क्या है?

हर उत्पाद की एक आधार मुद्रा में एक मूल कीमत होती है। स्थानीयकृत मूल्य निर्धारण आपको को **प्रति मुद्रा या प्रति देश सेट की गई निश्चित कीमतों के साथ** उस आधार को ओवरराइड करने देता है। इसे चालू करने के लिए उत्पाद पर एक `pricing_mode` सेट करें, फिर प्रति बाजार एक नियम संलग्न करें।

यह अंतरराष्ट्रीय pricing के लिए कई स्वतंत्र levers में से एक है, जिनमें से प्रत्येक एक अलग समस्या हल करता है:

| Mechanism | यह क्या करता है | ग्राहक को दिखाई देने वाली संख्या |
| :--- | :--- | :--- |
| **Localized Pricing** | आपके द्वारा प्रत्येक currency या country के लिए तय की गई fixed price | ठीक वही amount जो आपने तय की है |
| [**Adaptive Currency**](/features/adaptive-currency) | live FX rates पर आपकी base price को automatically convert करता है | current exchange rate पर convert की गई base price |
| [**Purchasing Power Parity**](/features/purchasing-power-parity) | country के अनुसार आपकी price का एक हिस्सा automatically charge करता है | base price का एक percentage |
| [**Charm Pricing**](/features/charm-pricing) | converted price को automatically एक साफ़ ending तक round करता है | 49.99 जैसी सुव्यवस्थित संख्या |
| [**Discount codes**](/features/discount-codes) | base price पर percentage reduction | base price में से discount घटाने के बाद की राशि |

<Info>
स्थानीयकृत मूल्य निर्धारण और अनुकूली मुद्रा एक साथ काम करते हैं। जब कोई स्थानीयकृत नियम मेल नहीं खाता, तो उत्पाद अपने आधार मूल्य पर वापस आ जाता है — यदि ग्राहक पहले से ही आपकी आधार मुद्रा में है, तो वह सीधे चार्ज किया जाता है, या यदि नहीं, तो अनुकूली मुद्रा के माध्यम से रूपांतरित होता है।
</Info>

## मुख्य अवधारणाएँ

- **Pricing modes** — कोई product एक समय में ठीक एक mode में होता है, जो उसके `pricing_mode` द्वारा set किया जाता है:
  - `by_currency`: प्रत्येक currency के लिए एक price, country की परवाह किए बिना। EUR में payment करने वाला हर व्यक्ति €9.99 देखता है।
  - `by_country`: किसी country के लिए specific price (भारत में ₹999), तब भी जब कई countries एक ही currency share करते हों।
- **Fixed amounts, in the smallest unit** — किसी rule का `amount` currency की smallest unit में एक integer होता है, ठीक API में हर जगह की तरह: `99900` ₹999.00 है, `999` €9.99 है। यह आपके द्वारा set की गई price है, converted value कभी नहीं।
- **A matched rule wins over automatic pricing** — जब कोई localized rule किसी line पर लागू होता है, तो उस line के लिए [Purchasing Power Parity](/features/purchasing-power-parity) और [Charm Pricing](/features/charm-pricing) दोनों skip कर दिए जाते हैं। Customer आपके द्वारा set की गई राशि का unchanged payment करता है।
- **When no rule matches** — Product अपना existing behavior बनाए रखता है: आपकी base currency में customers सीधे base price pay करते हैं; बाकी सभी को [Adaptive Currency](/features/adaptive-currency) के माध्यम से convert किया जाता है।
- **Fees are inclusive when a rule matches** — Customer **ठीक वही amount pay करता है** जो आपने set की है। [Adaptive Currency](/features/adaptive-currency#choose-who-bears-the-fee) की FX fee आप absorb करते हैं (उस transaction के लिए fees-inclusive मानी जाती है), customer से ऊपर से add नहीं की जाती; इसलिए आपकी बताई गई local price ही हमेशा charged price होती है।

## API के माध्यम से प्रबंधन करें

स्थानीयकृत मूल्य निर्धारण पूरी तरह से API के माध्यम से उपलब्ध है। पहले उत्पाद की मूल्य निर्धारण मोड सेट करें, फिर नियम संलग्न करें।

### मूल्य निर्धारण मोड सेट करें

`pricing_mode` सेट करें जब आप उत्पाद बनाते हैं (या एक मौजूदा अपडेट करते हैं)। `null` का अर्थ है केवल आधार, मौजूदा व्यवहार।

<CodeGroup>

```typescript theme={null}
import DodoPayments from 'dodopayments';

const client = new DodoPayments({
  bearerToken: process.env.DODO_PAYMENTS_API_KEY,
  environment: 'test_mode',
});

const product = await client.products.update('pdt_premium_plan', {
  pricing_mode: 'by_country',
});
```

```python theme={null}
import os
from dodopayments import DodoPayments

client = DodoPayments(
    bearer_token=os.environ.get("DODO_PAYMENTS_API_KEY"),
    environment="test_mode",
)

product = client.products.update(
    "pdt_premium_plan",
    pricing_mode="by_country",
)
```

```go theme={null}
package main

import (
	"context"
	"os"

	"github.com/dodopayments/dodopayments-go"
	"github.com/dodopayments/dodopayments-go/option"
)

func main() {
	client := dodopayments.NewClient(
		option.WithBearerToken(os.Getenv("DODO_PAYMENTS_API_KEY")),
	)

	_, err := client.Products.Update(
		context.TODO(),
		"pdt_premium_plan",
		dodopayments.ProductUpdateParams{
			PricingMode: dodopayments.F(dodopayments.PricingModeByCountry),
		},
	)
	if err != nil {
		panic(err)
	}
}
```

</CodeGroup>

### एक स्थानीयकृत कीमत जोड़ें

उत्पाद के लिए एक नियम जोड़ें। `by_country` मोड में `country_code` आवश्यक है; `by_currency` मोड में इसे छोड़ दिया जाना चाहिए।

<CodeGroup>

```typescript theme={null}
// ₹999.00 for customers in India
const localizedPrice = await client.products.localizedPrices.create('pdt_premium_plan', {
  currency: 'INR',
  country_code: 'IN',
  amount: 99900,
});
```

```python theme={null}
# ₹999.00 for customers in India
localized_price = client.products.localized_prices.create(
    "pdt_premium_plan",
    currency="INR",
    country_code="IN",
    amount=99900,
)
```

```go theme={null}
// ₹999.00 for customers in India
localizedPrice, err := client.Products.LocalizedPrices.New(
	context.TODO(),
	"pdt_premium_plan",
	dodopayments.ProductLocalizedPriceNewParams{
		Currency:    dodopayments.F(dodopayments.CurrencyInr),
		CountryCode: dodopayments.F(dodopayments.CountryCodeIn),
		Amount:      dodopayments.F(int64(99900)),
	},
)
```

</CodeGroup>

`by_currency` उत्पाद के लिए, `country_code` को छोड़ दें। उदाहरण के लिए, सभी EUR में भुगतान करने वाले के लिए एक फ्लैट `€9.99` (`currency: 'EUR'`, `amount: 999`)।

### सूची, अपडेट, और संग्रहित करें

आप केवल एक नियम के `amount` को अपडेट कर सकते हैं; मुद्रा और देश एक बार बनाने के बाद तय रहते हैं। संग्रहण एक आइडेम्पोटेंट सॉफ़्ट-डिलीट है, इसलिए नियम मेल नहीं खाता लेकिन आपके इतिहास में रहता है।

<CodeGroup>

## यह चेकआउट पर कैसे लागू होता है

स्थानीयकृत मूल्य निर्धारण प्रति कार्ट लाइन पर हल किया जाता है, और केवल उन उत्पादों के लिए जिन पर `pricing_mode` सेट है। Dodo Payments अनुरोध से दो संकेत पढ़ता है: ग्राहक का **बिलिंग देश**, और एक वैकल्पिक **`billing_currency`** (जब छोड़ा जाता है, तो एक मुद्रा बिलिंग देश से व्युत्पन्न होती है)।

- **देश के द्वारा**: बिलिंग देश से मेल खाने वाले नियम की खोज करता है। अगर एक मौजूद है, तो ग्राहक को उस मुद्रा में नियम की राशि चार्ज की जाती है।
- **मुद्रा के द्वारा**: ग्राहक की मुद्रा से मेल खाने वाले नियम की खोज करता है (`billing_currency`, या उनके देश से व्युत्पन्न मुद्रा)। अगर एक मौजूद है, तो ग्राहक को उस मुद्रा में नियम की राशि चार्ज की जाती है।
- **कोई मेल नहीं, या कोई `pricing_mode` नहीं**: आधार कीमत लागू होती है, सीधे तब चार्ज की जाती है जब ग्राहक की मुद्रा आधार मुद्रा के बराबर होती है, अन्यथा [अनुकूली मुद्रा](/features/adaptive-currency) के माध्यम से रूपांतरित होती है।

प्रत्येक कार्ट लाइन को स्वयं हल किया जाता है, इसलिए आप एक उत्पाद को स्थानीयकृत कर सकते हैं और अन्य को एक ही चेकआउट में आधार मूल्य निर्धारण पर छोड़ सकते हैं। यदि कोई भी लाइन स्थानीयकृत नियम से मेल खाती है, तो पूरे लेन-देन को फीस-सहित के लिए मजबूर किया जाता है (देखें [मुख्य अवधारणाएँ](#core-concepts))।

## Subscription Plan में बदलावों पर इसका प्रभाव

Localized pricing आपके subscribers के साथ तब लागू होती है जब वे plans बदलते हैं। जब कोई existing subscription किसी ऐसे product में [plan बदलती है](/features/subscription#subscription-plan-changes) जिसमें `pricing_mode` है, तो नए plan की price checkout जैसे ही rules के अनुसार निर्धारित होती है, जिसमें subscription पर पहले से lock किया गया billing country और currency उपयोग होता है:

- **By Country**: subscription के billing country से match करने वाला rule लागू होता है। यदि rule की currency उस currency से अलग है जिसमें subscription का billing होता है, तो rule की amount को live FX rates पर convert किया जाता है — rule को लागू किया जाता है, छोड़ा नहीं जाता।
- **By Currency**: customer से billing के लिए उपयोग की जा रही currency से match करने वाला rule लागू होता है, और customer से ठीक rule की amount charge की जाती है।
- **कोई match नहीं, या कोई `pricing_mode` नहीं**: नए plan की base price लागू होती है, और आवश्यकता होने पर [Adaptive Currency](/features/adaptive-currency) के माध्यम से convert की जाती है — checkout जैसा ही fallback।

यह उन सभी स्थानों पर लागू होता है जहां से plan change शुरू किया जा सकता है: [Change Plan API](/api-reference/subscriptions/change-plan), [Customer Portal](/features/customer-portal) के self-service plan changes, और billing period के अंत के लिए scheduled changes।

- **Previews सटीक होते हैं।** [Preview Change Plan](/api-reference/subscriptions/preview-change-plan) वही localized amount लौटाता है जिसे वास्तविक change पर charge किया जाएगा।
- **Renewals localized price बनाए रखते हैं।** Change के बाद नया plan अपनी localized amount पर renew होता है — और fees-inclusive बना रहता है — ठीक उसी तरह जैसे उस price पर बनाई गई subscription।
- **Proration वास्तविक amounts का उपयोग करता है।** Upgrade पर unused time का credit उस amount पर आधारित होता है जो customer ने पुराने plan के लिए वास्तव में paid किया था, जबकि नए plan की pricing उसके localized rule से निर्धारित होती है।
- **Scheduled changes schedule किए जाने के समय price lock करते हैं।** Billing period के अंत के लिए scheduled change, scheduling के समय calculated amount charge करता है, भले ही इस बीच आप rule को edit कर दें।
- **Billing currency कभी नहीं बदलती।** Plan change कभी उस currency को switch नहीं करता जिसमें subscription settle होती है; किसी अन्य currency में मौजूद rule को FX के माध्यम से subscription की currency में convert किया जाता है।
- **Add-ons localized नहीं होते।** नए plan पर add-on prices हमेशा अपनी base pricing का उपयोग करती हैं।

## महत्वपूर्ण व्यवहार

| व्यवहार | विवरण |
| :--- | :--- |
| **Tax से पहले की amounts** | Localized amount tax से *पहले* की price होती है। Tax-exclusive products के लिए checkout पर tax अलग से जोड़ा जाता है, इसलिए localized amount final total नहीं होती। [Tax-Inclusive Pricing](/features/tax-inclusive-pricing) देखें। |
| **Pay What You Want के लिए नहीं** | Localized rules [Pay What You Want](/features/pay-what-you-want) products पर कभी लागू नहीं होते, जहां customer amount चुनता है। |
| **By-currency base से अलग होता है** | `by_currency` rule में product की base currency से अलग currency का उपयोग होना चाहिए। |
| **प्रत्येक market के लिए एक rule** | किसी product में प्रत्येक currency (by-currency) या प्रत्येक country (by-country) के लिए अधिकतम एक active rule हो सकता है। |
| **सभी product types** | One-time, subscription और usage-based products पर लागू होता है — इसमें वह स्थिति भी शामिल है जब कोई existing subscriber [plan बदलता है](#how-it-applies-on-subscription-plan-changes)। |

<Info>
Localized rule changes अपने अलग webhooks emit नहीं करते। Resolved amount resulting payment या subscription पर ठीक किसी अन्य price की तरह दिखाई देती है।
</Info>

## सर्वोत्तम प्रथाएं

- **एक उचित base price रखें।** यह हर उस market के लिए fallback है जहाँ कोई rule नहीं है, और इसे Adaptive Currency के माध्यम से convert किया जाता है।
- **साफ़ numbers type करें।** Fixed amount का मुख्य उद्देश्य ₹999, €9.99 या ¥1000 जैसी tidy price है, FX result नहीं। प्रत्येक currency में automatic rounding के लिए [Charm Pricing](/features/charm-pricing) देखें।
- **काम के अनुसार mode चुनें।** Purchasing-power pricing के लिए `by_country` का उपयोग करें; जब प्रत्येक currency zone के लिए एक price पर्याप्त हो, तब `by_currency` का उपयोग करें।
- **Promotions के लिए archive करें, दोबारा create न करें।** किसी rule को archive करने से history सुरक्षित रखते हुए market base/adaptive पर वापस आ जाता है; ज़रूरत के अनुसार बाद में इसे recreate या re-price करें।
- **कुल राशि का advertising करने से पहले tax line पर ध्यान दें।** Tax-exclusive products के लिए customer localized amount *plus* tax pay करता है, इसलिए ads में इसे final price के रूप में quote न करें।
