## Overview

Test mode lets you simulate payments without processing real transactions. All test credentials only work in test mode — never use them in production.

<CardGroup cols={3}>
<Card title="No Real Charges" icon="shield-check">
Test transactions don't process actual payments or affect real accounts.
</Card>

<Card title="Full API Access" icon="code">
All API endpoints work identically in test and live modes.
</Card>

<Card title="Webhook Testing" icon="webhook">
Webhooks fire for test transactions just like production.
</Card>
</CardGroup>

<Warning>
Test credentials only work in test mode. Attempting to use them in live mode will result in payment failures.
</Warning>

### Como Testar Falha de Renovação

<Steps>
<Step title="Create a test subscription">
Crie uma assinatura com suas chaves de API de teste usando um cartão de teste de **sucesso** (por exemplo, `4242 4242 4242 4242`). A cobrança inicial deve ser bem-sucedida e a assinatura deve se tornar ativa.
</Step>

<Step title="Swap in the failure card via Customer Portal">
Abra o [Portal do Cliente](/features/customer-portal), encontre a assinatura que você acabou de criar e clique em **Atualizar Método de Pagamento**. Insira o cartão de teste de falha `4000 0000 0000 0341` (Validade: `12/34`, CVC: `123`) e salve-o como método de pagamento da assinatura.
</Step>

<Step title="Advance the next billing date (optional)">
Para acionar a renovação imediatamente, em vez de esperar o ciclo de faturamento natural, use a API de Atualização de Assinatura para definir `next_billing_date` para o horário UTC atual. O valor deve ser um timestamp UTC ISO 8601 / RFC 3339 (o sufixo `Z` é necessário).

```http
PATCH /subscriptions/{subscription_id}
{
  "next_billing_date": "2026-05-03T00:00:00Z"
}
```

Veja os detalhes na referência [API de Atualização de Assinaturas](/api-reference/subscriptions/patch-subscriptions#body-next-billing-date-one-of-0).
</Step>

<Step title="Verify the failure">
Na próxima tentativa de cobrança:

- A cobrança de renovação é recusada no cartão de falha
- A assinatura muda para o status **Em Espera**
- Um evento webhook `payment.failed` é enviado
- O cliente pode retornar ao Portal do Cliente para atualizar o método de pagamento e tentar novamente
</Step>
</Steps>

<Warning>
Este cartão é especificamente para testar falhas de renovação. A cobrança será recusada na próxima data de faturamento, permitindo que você teste a lógica de tentativa de pagamento, notificações ao cliente e tratamento de falhas.
</Warning>

## Testar UPI

O teste UPI usa identificadores especiais de VPA (Endereço de Pagamento Virtual) que simulam diferentes resultados de pagamento.

| Status | ID UPI |
| :----- | :----- |
| Sucesso | `success@upi` |
| Falha | `failure@upi` |

### Requisitos para Teste de UPI

- O país de faturamento deve ser definido como `IN`
- A moeda deve ser `INR`
- Para comerciantes não indianos: Moeda Adaptativa deve estar ativada

Para documentação completa de UPI, incluindo testes de mandato do RBI para assinaturas, consulte a página [Métodos de Pagamento na Índia](/features/payment-methods/india).

### Teste Afterpay

<Steps>
<Step title="Select Afterpay">
Escolha Afterpay como o método de pagamento no checkout e clique em Pagar.
</Step>

<Step title="Test successful payment">
Use qualquer endereço de email e endereço de entrega válidos para pagamentos bem-sucedidos.
</Step>

<Step title="Test failed authentication">
Para simular uma falha, feche a janela modal do Afterpay na página de redirecionamento. O pagamento muda de `requires_customer_action` para `requires_payment_method`.
</Step>
</Steps>

<Note>
Afterpay requer um valor mínimo de transação de **$50.01** para aparecer como opção de pagamento.
</Note>

Para obter a documentação completa de BNPL, incluindo os testes B2B do Billie, consulte a página [Buy Now Pay Later](/features/payment-methods/bnpl).

## Testar carteiras digitais

### Apple Pay

<Steps>
<Step title="Enable test mode">
Use suas chaves de teste da API do Dodo Payments.
</Step>

<Step title="Add a card to Apple Wallet">
Adicione um cartão real à sua Apple Wallet. No modo de teste, o cartão não será cobrado.
</Step>

<Step title="Complete test purchase">
Abra o checkout em um dispositivo Apple e conclua o fluxo do Apple Pay.
</Step>
</Steps>

<Warning>
O Apple Pay requer HTTPS. Ele não aparecerá em `localhost` sem a configuração adequada de SSL. A verificação do domínio também deve estar concluída.
</Warning>

### Google Pay

<Steps>
<Step title="Join the test card group">
[Participe do grupo de cartões de teste do Google Pay](https://groups.google.com/g/googlepay-test-mode-stub-data) para que os cartões de teste sejam adicionados automaticamente à sua carteira.
</Step>

<Step title="Enable test mode">
Use suas chaves de teste da API do Dodo Payments.
</Step>

<Step title="Complete test purchase">
Selecione um dos cartões de teste no Google Pay para concluir a transação.
</Step>
</Steps>

### Amazon Pay, Cash App Pay e RevolutPay

Use suas chaves de teste da API e siga o fluxo padrão de checkout. As transações de teste são simuladas sem cobranças reais.

Para obter a documentação completa sobre carteiras digitais, incluindo a verificação de domínio do Apple Pay, consulte a página [Digital Wallets](/features/payment-methods/digital-wallets).

## Testar ACH Direct Debit

ACH Direct Debit pode ser testado no Test Mode inserindo dados bancários de teste no checkout.

<Steps>
<Step title="Enable test mode">
Use suas chaves de teste da API do Dodo Payments.
</Step>

<Step title="Set currency and billing address">
Defina a moeda de cobrança como `USD` e o país do endereço de cobrança como `US`. ACH não é oferecido fora dessa combinação.
</Step>

<Step title="Use a one-time payment">
ACH não está disponível em checkouts de assinaturas, portanto teste-o com um pagamento único.
</Step>

<Step title="Enter the test bank details">
Insira um dos pares de routing number e account number de teste abaixo e confirme se o seu webhook handler recebe o status final do pagamento — os pagamentos ACH são confirmados de forma assíncrona, e não no checkout.
</Step>
</Steps>

### Contas bancárias de teste

Use o routing number `110000000` com qualquer um destes account numbers:

| Account Number | Comportamento |
| :------------- | :------- |
| `000123456789` | O pagamento é bem-sucedido. |
| `000222222227` | O pagamento falha por falta de fundos. |
| `000111111113` | O pagamento falha porque a conta está encerrada. |
| `000555555559` | O pagamento é bem-sucedido e, em seguida, gera uma contestação. |
| `000000000009` | O pagamento permanece em processamento indefinidamente. |

Para ver a lista completa de contas de teste, consulte a página [ACH Direct Debit](/features/payment-methods/ach#testing).

## Testar métodos europeus

Os métodos de pagamento europeus (iDEAL, Bancontact, EPS, Multibanco) podem ser testados no Test Mode.

<Steps>
<Step title="Enable test mode">
Use suas chaves de API de teste do Dodo Payments.
</Step>

<Step title="Set billing address">
Defina o país do endereço de cobrança para corresponder ao método de pagamento:
- `NL` para iDEAL
- `BE` para Bancontact
- `AT` para EPS
- `PT` para Multibanco
</Step>

<Step title="Set currency">
Os métodos europeus exigem a moeda EUR.
</Step>

<Step title="Complete test flow">
Siga o fluxo simulado de autenticação bancária no ambiente de teste.
</Step>
</Steps>

### IBANs de teste para SEPA Direct Debit

SEPA Direct Debit exige EUR e um endereço de cobrança na Zona do Euro. Use estes IBANs de teste para forçar um resultado específico:

| Test IBAN | Comportamento |
| :-------- | :------- |
| `DE89370400440532013000` | O pagamento é bem-sucedido. |
| `DE62370400440532013001` | O pagamento falha. |
| `DE35370400440532013002` | O pagamento é bem-sucedido e, em seguida, é contestado imediatamente. |
| `DE65370400440002222227` | O pagamento falha por falta de fundos. |

Para ver a lista completa de IBANs de teste, incluindo valores por país, consulte a página [Europe](/features/payment-methods/europe#sepa-test-ibans).

Para obter a documentação completa sobre os métodos de pagamento europeus, consulte a página [Europe](/features/payment-methods/europe).

## Práticas recomendadas de teste

<AccordionGroup>
<Accordion title="Test all payment scenarios">
Não teste apenas pagamentos bem-sucedidos. Teste recusas, cancelamentos e casos extremos, como falta de fundos.
</Accordion>

<Accordion title="Verify webhook handling">
Garanta que seus endpoints de webhook processem corretamente todos os tipos de evento, especialmente `payment.succeeded`, `payment.failed` e eventos de assinatura.

Use o [Dodo Payments CLI](/developer-resources/sdks/cli#webhooks) para testar webhooks localmente:
- `dodo wh listen` encaminha webhooks de teste ativos para o seu servidor local
- `dodo wh trigger` envia payloads simulados para todos os tipos de evento de webhook compatíveis
</Accordion>

<Accordion title="Test on real devices">
Para Apple Pay e Google Pay, teste em dispositivos iOS e Android reais. Simuladores não reproduzem completamente o comportamento das carteiras digitais.
</Accordion>

<Accordion title="Test regional methods with correct addresses">
Métodos de pagamento regionais (UPI, iDEAL etc.) exigem endereços de cobrança correspondentes. Um endereço de cobrança dos EUA não exibirá o iDEAL.
</Accordion>

<Accordion title="Verify minimum amounts">
Os métodos BNPL exigem um mínimo de $50.01. Teste se eles aparecem ou ficam ocultos corretamente com base no total do carrinho.
</Accordion>
</AccordionGroup>
