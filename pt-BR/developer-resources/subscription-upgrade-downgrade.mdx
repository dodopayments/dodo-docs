## What is a subscription upgrade or downgrade?

Changing plans lets you move a customer between subscription tiers or quantities. Use it to:
- Align pricing with usage or features
- Move from monthly to annual (or vice versa)
- Adjust quantity for seat-based products

<Info>
Plan changes can trigger an immediate charge depending on the proration mode you choose.
</Info>

## When to use plan changes

- Upgrade when a customer needs more features, usage, or seats
- Downgrade when usage decreases
- Migrate users to a new product or price without cancelling their subscription

## Prerequisites

Before implementing subscription plan changes, ensure you have:

- A Dodo Payments merchant account with active subscription products
- API credentials (API key and webhook secret key) from the dashboard
- An existing active subscription to modify
- Webhook endpoint configured to handle subscription events

<Info>
For detailed setup instructions, see our [Integration Guide](/developer-resources/integration-guide#dashboard-setup).
</Info>

## Step-by-Step Implementation Guide

Follow this comprehensive guide to implement subscription plan changes in your application:

<Steps>
<Step title="Understand Plan Change Requirements">
Before implementing, determine:
- Which subscription products can be changed to which others
- What proration mode fits your business model
- How to handle failed plan changes gracefully
- Which webhook events to track for state management

<Tip>
Test plan changes thoroughly in test mode before implementing in production.
</Tip>
</Step>

<Step title="Choose Your Proration Strategy">
Select the billing approach that aligns with your business needs:

<Tabs>
<Tab title="prorated_immediately">
Best for: SaaS applications wanting to charge fairly for unused time
- Calculates exact prorated amount based on remaining cycle time
- Charges a prorated amount based on unused time remaining in the cycle
- Provides transparent billing to customers
</Tab>

<Tab title="difference_immediately">
Best for: Clear upgrade/downgrade scenarios
- Upgrade: Charge immediate difference (e.g., $30→$80 = charge $50)
- Downgrade: Credit remaining value for future renewals
- Simplifies billing logic and customer communication
</Tab>

<Tab title="full_immediately">
Melhor para: Quando você deseja redefinir o ciclo de faturamento
- Cobra o valor total do novo plano imediatamente
- Ignora o tempo restante do plano antigo
- Útil para transições de anual para mensal
</Tab>

- Nenhuma cobrança ou crédito calculado
- Cliente muda para o novo plano imediatamente sem ajustes de faturamento
- Ciclo de faturamento permanece inalterado

<Step title="Implement the Change Plan API">
Use a API de Mudança de Plano para modificar os detalhes da assinatura:

<ParamField path="subscription_id" type="string" required>
O ID da assinatura ativa a ser modificada.
</ParamField>

<ParamField path="product_id" type="string" required>
O novo ID do produto para trocar a assinatura.
</ParamField>

<ParamField path="quantity" type="integer" default="1">
Número de unidades para o novo plano (para produtos baseados em assentos).
</ParamField>

<ParamField path="proration_billing_mode" type="string" required>
Como lidar com o faturamento imediato: `prorated_immediately`, `full_immediately`, `difference_immediately` ou `do_not_bill`.
</ParamField>

<ParamField path="addons" type="array">
Complementos opcionais para o novo plano. Deixar em branco remove qualquer complemento existente.
</ParamField>

<ParamField path="on_payment_failure" type="string">
Controla o comportamento quando o pagamento pela troca de plano falha:
- `prevent_change`: Mantenha a assinatura no plano atual até que o pagamento seja bem-sucedido
- `apply_change` (padrão): Aplique a troca de plano imediatamente, independentemente do resultado do pagamento

Se não especificado, usa a configuração padrão no nível empresarial.
</ParamField>

<ParamField path="discount_code" type="string">
Código de desconto opcional para aplicar ao novo plano. Se fornecido, valida e aplica o desconto à troca de plano. Se não fornecido e a assinatura tiver um desconto existente com `preserve_on_plan_change=true`, o desconto existente será preservado (se aplicável ao novo produto).
</ParamField>
</Step>

<Step title="Handle Webhook Events">
Configure o manuseio do webhook para rastrear os resultados da troca de plano:

- `subscription.active`: Mudança de plano bem-sucedida, assinatura atualizada
- `subscription.plan_changed`: Plano de assinatura alterado (atualização/redução/atualização do complemento)
- `subscription.on_hold`: Cobrança pela mudança de plano falhou, assinatura pausada
- `payment.succeeded`: Cobrança imediata pela mudança de plano bem-sucedida
- `payment.failed`: Cobrança imediata falhou

<Warning>
Sempre verifique as assinaturas do webhook e implemente o processamento de eventos idempotente.
</Warning>
</Step>

<Step title="Update Your Application State">
Com base nos eventos do webhook, atualize sua aplicação:
- Conceda/revogue funcionalidades com base no novo plano
- Atualize o painel do cliente com os detalhes do novo plano
- Envie e-mails de confirmação sobre as mudanças de plano
- Registre alterações de cobrança para auditoria
</Step>

<Step title="Test and Monitor">
Teste sua implementação minuciosamente:
- Teste todos os modos de prorrateamento com diferentes cenários
- Verifique se o manuseio do webhook funciona corretamente
- Monitore taxas de sucesso da troca de plano
- Configure alertas para mudanças de plano falhadas

<Check>
Sua implementação de troca de plano de assinatura está agora pronta para uso em produção.
</Check>
</Step>
</Steps>

## Gerenciando Complementos

Ao alterar planos de assinatura, você também pode modificar complementos:

```javascript
// Add addons to the new plan
await client.subscriptions.changePlan('sub_123', {
  product_id: 'prod_new',
  quantity: 1,
  proration_billing_mode: 'difference_immediately',
  addons: [
    { addon_id: 'addon_123', quantity: 2 }
  ]
});

// Remove all existing addons
await client.subscriptions.changePlan('sub_123', {
  product_id: 'prod_new',
  quantity: 1,
  proration_billing_mode: 'difference_immediately',
  addons: [] // Empty array removes all existing addons
});
```

<Info>
Complementos são incluídos no cálculo de prorrateamento e serão cobrados de acordo com o modo de prorrateamento selecionado.
</Info>

| Cenário | Comportamento |

## Modos de Prorrateamento

Escolha como cobrar o cliente ao mudar de plano:

#### `prorated_immediately`
- Cobra pela diferença parcial no ciclo atual
- Se estiver em teste, cobra imediatamente e muda para o novo plano agora
- Redução: pode gerar um crédito proporcional aplicado a futuras renovações

#### `full_immediately`
- Cobra o valor total do novo plano imediatamente
- Ignora o tempo restante do antigo plano

<Info>
Créditos criados por reduções usando <code>difference_immediately</code> são específicos da assinatura e distintos de direitos de <a href="/features/credit-based-billing">Faturamento Baseado em Crédito</a>. Eles se aplicam automaticamente a renovações futuras da mesma assinatura e não são transferíveis entre assinaturas.
</Info>

#### `difference_immediately`
- Atualização: cobra imediatamente a diferença de preço entre os planos antigo e novo
- Redução: adiciona o valor restante como crédito interno à assinatura e aplica automaticamente nas renovações

#### `do_not_bill`
- Nenhuma cobrança ou crédito é calculado
- Cliente muda para o novo plano imediatamente sem ajustes de faturamento
- Ciclo de faturamento permanece inalterado
- Ideal para migrações por cortesia, trocas de planos gratuitos ou absorção de diferenças de custo

| Funcionalidade | `prorated_immediately` | `difference_immediately` | `full_immediately` | `do_not_bill` |
|---------|----------------------|------------------------|-------------------|--------------|
| **Cobrança de Atualização** | Diferença proporcional para os dias restantes | Diferença de preço total entre planos | Preço total do novo plano | Sem cobrança |
| **Crédito de Redução** | Crédito proporcional para os dias restantes | Diferença de preço total como crédito | Sem crédito | Sem crédito |
| **Ciclo de Faturamento** | Inalterado | Inalterado | Redefinido para hoje | Inalterado |
| **Comportamento de Teste** | Termina o teste, cobra imediatamente | Termina o teste, cobra imediatamente | Termina o teste, cobra valor total | Termina o teste, sem cobrança |
| **Melhor para** | Cobrança justa baseada no tempo | Matemática simples de atualizações/reduções | Redefinição de ciclos de faturamento | Migrações gratuitas ou trocas por cortesia |
| **Complexidade** | Média (cálculo de dias) | Baixa (subtração simples) | Baixa (cobrança total) | Nenhuma |

```mermaid
flowchart TD
    A{Need fair day-by-day billing?} -->|Yes| B[prorated_immediately]
    A -->|No| C{Need to reset billing cycle?}
    C -->|Yes| D[full_immediately]
    C -->|No| E{Skip billing entirely?}
    E -->|Yes| F[do_not_bill]
    E -->|No| G[difference_immediately]
```

### Como cada modo processa o faturamento

```mermaid
flowchart LR
    A[Plan Change] --> B{Proration Mode}
    B -->|prorated| C[Calculate remaining days]
    C --> D[Charge prorated diff]
    D --> E[Keep billing date]
    B -->|difference| F[Price difference]
    F -->|Upgrade| G[Charge diff]
    F -->|Downgrade| H[Add credit]
    G --> E
    H --> E
    B -->|full| I[Charge full price]
    I --> J[Reset billing date]
```

<Tip>
Escolha `prorated_immediately` para contabilidade justa de tempo; escolha `full_immediately` para reiniciar o faturamento; use `difference_immediately` para atualizações simples e crédito automático em reduções; ou use `do_not_bill` para trocar planos sem nenhum ajuste de faturamento.
</Tip>

## Lidando com Falhas de Pagamento

Controle o que acontece quando um pagamento de troca de plano falha usando o parâmetro `on_payment_failure`.

### Modos de Falha de Pagamento

<Tabs>
<Tab title="prevent_change (Recommended for critical upgrades)">
**Comportamento**: Mantenha a assinatura no plano atual até que o pagamento seja bem-sucedido.

- A troca de plano é marcada como "pendente"
- O cliente mantém acesso ao plano atual
- A assinatura muda para o estado `active` apenas após o pagamento bem-sucedido
- Útil quando você deseja garantir o pagamento antes de conceder funcionalidades avançadas

```javascript
await client.subscriptions.changePlan('sub_123', {
  product_id: 'prod_pro',
  quantity: 1,
  proration_billing_mode: 'prorated_immediately',
  on_payment_failure: 'prevent_change'
});
```

</Tab>

<Tab title="apply_change (Default)">
**Comportamento**: Aplique a mudança de plano imediatamente, independentemente do resultado do pagamento.

- A troca de plano é aplicada mesmo que o pagamento falhe
- Cliente ganha acesso imediato ao novo plano
- A assinatura pode mudar para `on_hold` se o pagamento falhar
- Bom para atualizações não críticas ou quando você confia no cliente

```javascript
await client.subscriptions.changePlan('sub_123', {
  product_id: 'prod_pro',
  quantity: 1,
  proration_billing_mode: 'prorated_immediately',
  on_payment_failure: 'apply_change' // This is the default
});
```

</Tab>
</Tabs>

<Info>
Se não especificado, o parâmetro `on_payment_failure` usa a configuração padrão no nível empresarial configurada no painel.
</Info>

### Quando Usar Cada Modo

| Cenário | Modo Recomendado | Razão |
|----------|------------------|--------|
| Atualizando para funcionalidades premium | `prevent_change` | Garantir pagamento antes de conceder acesso |
| Aumento de quantidade (mais assentos) | `prevent_change` | Prevenir uso sem pagamento |
| Reduzindo planos | `apply_change` | Cliente está reduzindo o gasto |
| Clientes corporativos confiáveis | `apply_change` | Menor risco de não pagamento |
| Conversão de teste para pagamento | `prevent_change` | Momento crítico de pagamento |

## Lidando com webhooks

Acompanhe o estado da assinatura por meio de webhooks para confirmar alterações de plano e pagamentos.

### Tipos de eventos a serem tratados
- `subscription.active`: assinatura ativada
- `subscription.plan_changed`: plano de assinatura alterado (atualização/redutação/mudanças de complemento)
- `subscription.on_hold`: cobrança falhou, assinatura pausada
- `subscription.renewed`: renovação bem-sucedida
- `payment.succeeded`: pagamento por mudança de plano ou renovação bem-sucedido
- `payment.failed`: pagamento falhou

## Melhores Práticas

Siga estas recomendações para mudanças confiáveis de plano de assinatura:

### Estratégia de Mudança de Plano
- **Teste minuciosamente**: Sempre teste mudanças de plano em modo de teste antes da produção
- **Escolha a prorrateamento cuidadosamente**: Selecione o modo de prorrateamento que esteja alinhado com seu modelo de negócios
- **Lide com falhas de forma eficaz**: Implemente manuseio adequado de erros e lógica de re-tentativa
- **Monitore taxas de sucesso**: Monitore taxas de sucesso/falha das mudanças de plano e investigue problemas

### Implementação de Webhook
- **Verifique assinaturas**: Sempre valide assinaturas de webhook para garantir autenticidade
- **Implemente idempotência**: Lide com eventos duplicados de webhook de forma eficaz
- **Processe de forma assíncrona**: Não bloqueie respostas de webhook com operações pesadas
- **Log tudo**: Mantenha logs detalhados para depuração e propósitos de auditoria

### Experiência do Usuário
- **Comunique claramente**: Informe os clientes sobre mudanças de faturamento e tempo
- **Forneça confirmações**: Envie confirmações por e-mail para mudanças de plano bem-sucedidas
- **Lide com casos extremos**: Considere períodos de teste, prorrateações e pagamentos falhos
- **Atualize a UI imediatamente**: Reflita mudanças de plano na interface de sua aplicação

## Problemas Comuns e Soluções

Resolva problemas típicos encontrados durante mudanças de planos de assinatura:

<AccordionGroup>
<Accordion title="Charge created but subscription not updated">
**Sintomas**: Chamada de API bem-sucedida, mas assinatura permanece no plano antigo

**Causas comuns**:
- Processamento do webhook falhou ou foi atrasado
- Estado da aplicação não atualizado após receber webhooks
- Problemas de transação de banco de dados durante atualização de estado

**Soluções**:
- Implemente manuseio robusto de webhook com lógica de re-tentativa
- Use operações idempotentes para atualizações de estado
- Adicione monitoramento para detectar e alertar sobre eventos de webhook perdidos
- Verifique se o endpoint do webhook é acessível e está respondendo corretamente
</Accordion>

<Accordion title="Credits not applied after downgrade">
**Sintomas**: Cliente reduz, mas não vê saldo de crédito

**Causas comuns**:
- Expectativas do modo de prorrateamento: reduções creditam a diferença total do preço do plano com `difference_immediately`, enquanto `prorated_immediately` cria um crédito proporcional com base no tempo restante no ciclo
- Créditos são específicos da assinatura e não são transferíveis entre assinaturas
- Saldo de crédito não visível no painel do cliente

**Soluções**:
- Use `difference_immediately` para reduções quando desejar créditos automáticos
- Explique aos clientes que créditos se aplicam a futuras renovações da mesma assinatura
- Implemente portal do cliente para mostrar saldos de crédito
- Verifique a visualização da próxima fatura para ver créditos aplicados
</Accordion>

<Accordion title="Webhook signature verification fails">
**Sintomas**: Eventos de webhook rejeitados devido a assinatura inválida

**Causas comuns**:
- Chave secreta do webhook incorreta
- Corpo da solicitação bruta modificado antes da verificação de assinatura
- Algoritmo de verificação de assinatura incorreto

**Soluções**:
- Verifique se você está usando o `DODO_WEBHOOK_SECRET` correto do painel
- Leia o corpo da solicitação bruta antes de qualquer middleware de análise de JSON
- Use a biblioteca padrão de verificação de webhook para sua plataforma
- Teste a verificação de assinatura de webhook no ambiente de desenvolvimento
</Accordion>

<Accordion title="Plan change fails with 422 error">
**Sintomas**: API retorna erro 422 Entidade Não Processável

**Causas comuns**:
- ID de assinatura ou ID de produto inválido
- Assinatura não está em estado ativo
- Parâmetros obrigatórios ausentes
- Produto não disponível para mudanças de plano

**Soluções**:
- Verifique se a assinatura existe e está ativa
- Verifique se o ID do produto é válido e disponível
- Certifique-se de que todos os parâmetros obrigatórios são fornecidos
- Revise a documentação da API para requisitos de parâmetro
</Accordion>

<Accordion title="Immediate charge fails during plan change">
**Sintomas**: Troca de plano iniciada, mas cobrança imediata falha

**Causas comuns**:
- Fundos insuficientes no método de pagamento do cliente
- Método de pagamento expirado ou inválido
- Banco recusou a transação
- Detecção de fraude bloqueou a cobrança

**Soluções**:
- Lide adequadamente com eventos de webhook `payment.failed`
- Notifique o cliente para atualizar o método de pagamento
- Implemente lógica de re-tentativa para falhas temporárias
- Considere permitir mudanças de plano com cobranças imediatas falhas
</Accordion>

<Accordion title="Subscription on hold after plan change">
**Sintomas**: Troca de plano falha e assinatura muda para o estado `on_hold`

**O que acontece**:
Quando uma troca de plano falha, a assinatura é automaticamente colocada no estado `on_hold`. A assinatura não será renovada automaticamente até que o método de pagamento seja atualizado.

**Solução**: Atualize o método de pagamento para reativar a assinatura

Para reativar uma assinatura do estado `on_hold` após uma troca de plano falha:

1. **Atualize o método de pagamento** usando a API de Atualização de Método de Pagamento
2. **Criação automática de cobrança**: A API cria automaticamente uma cobrança para os valores devidos
3. **Geração de fatura**: Uma fatura é gerada para a cobrança
4. **Processamento de pagamento**: O pagamento é processado usando o novo método de pagamento
5. **Reativação**: Após o pagamento bem-sucedido, a assinatura é reativada para o estado `active`

<CodeGroup>

  }

## Tratamento de Erros

Trate erros comuns da API de forma eficaz na sua implementação:

### Códigos de Status HTTP

<AccordionGroup>
<Accordion title="200 OK">
Solicitação de mudança de plano processada com sucesso. A assinatura está sendo atualizada e o processamento de pagamento começou.
</Accordion>

<Accordion title="400 Bad Request">
Parâmetros de solicitação inválidos. Verifique se todos os campos obrigatórios são fornecidos e formatados corretamente.
</Accordion>

<Accordion title="401 Unauthorized">
Chave de API inválida ou ausente. Verifique se sua `DODO_PAYMENTS_API_KEY` está correta e tem as permissões adequadas.
</Accordion>

<Accordion title="404 Not Found">
ID de assinatura não encontrado ou não pertence à sua conta.
</Accordion>

<Accordion title="422 Unprocessable Entity">
A assinatura não pode ser alterada (por exemplo, já cancelada, produto não disponível, etc.).
</Accordion>

<Accordion title="500 Internal Server Error">
Erro do servidor ocorreu. Tente novamente após um breve intervalo.
</Accordion>
</AccordionGroup>

{
  "error": {
    "code": "subscription_not_found",
    "message": "The subscription with ID 'sub_123' was not found",
    "details": {
