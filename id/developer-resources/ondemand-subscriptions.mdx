## Ikhtisar

Langganan sesuai permintaan memungkinkan Anda untuk mengotorisasi metode pembayaran pelanggan sekali dan kemudian mengenakan jumlah variabel kapan pun Anda perlu, alih-alih pada jadwal tetap. Fitur ini tersedia untuk semua akun—tidak memerlukan persetujuan.

Gunakan panduan ini untuk:
- Membuat langganan sesuai permintaan (mengotorisasi mandat dengan harga awal opsional)
- Memicu biaya berikutnya dengan jumlah kustom
- Melacak hasil menggunakan webhook

Untuk pengaturan langganan umum, lihat [Panduan Integrasi Langganan](/developer-resources/subscription-integration-guide).

## Prasyarat

- Akun pedagang Dodo Payments dan kunci API
- Rahasia webhook yang dikonfigurasi dan endpoint untuk menerima peristiwa
- Produk langganan dalam katalog Anda

<Tip>
Jika Anda ingin pelanggan menyetujui mandat melalui checkout yang dihosting, set `payment_link: true` dan berikan `return_url`.
</Tip>

## Cara kerja sesuai permintaan

1. Anda membuat langganan dengan objek `on_demand` untuk mengautorisasi metode pembayaran dan jika perlu, mengumpulkan biaya awal.
2. Setelah itu, Anda membuat biaya terhadap langganan tersebut dengan jumlah kustom menggunakan endpoint biaya khusus.
3. Anda mendengarkan webhook (misalnya, `payment.succeeded`, `payment.failed`) untuk memperbarui sistem Anda.

## Buat langganan sesuai permintaan

Endpoint: [POST /checkouts](/api-reference/checkout-sessions/create)

Bidang permintaan kunci (badan):  
Silakan temukan di [Buat Sesi Checkout](/api-reference/checkout-sessions/create)

### Buat langganan sesuai permintaan

<Tabs>
<Tab title="Node.js SDK">

```javascript
import DodoPayments from 'dodopayments';

const client = new DodoPayments({
  bearerToken: process.env.DODO_PAYMENTS_API_KEY,
  environment: 'test_mode', // defaults to 'live_mode'
});

async function main() {
  const subscription = await client.checkoutSessions.create({
    product_cart: [{ product_id: 'pdt_123', quantity: 1 }],
    billing_address:  { city: 'SF', country: 'US', state: 'CA', street: '1 Market St', zipcode: '94105' },
    customer: { customer_id: 'cus_123' },
    return_url: 'https://example.com/billing/success',
    subscription_data: {
        on_demand: {
            mandate_only: true // set false to collect an initial charge
            // product_price: 1000, // optional: charge $10.00 now if mandate_only is false
            // product_currency: 'USD',
            // product_description: 'Custom initial charge',
            // adaptive_currency_fees_inclusive: false,
        }
    }
  });

  console.log(subscription.checkout_url);
}

main().catch(console.error);
```

## Kenakan biaya langganan sesuai permintaan

Setelah mandat diotorisasi, buat biaya sesuai kebutuhan.

Endpoint: [POST /subscriptions/\{subscription_id\}/charge](/api-reference/subscriptions/create-charge)

Bidang permintaan kunci (badan):

<AccordionGroup>
  <Accordion title="Parameter badan permintaan biaya">
    <ParamField body="product_price" type="integer" required>
      Jumlah yang akan dikenakan biaya (dalam unit mata uang terkecil). Contoh: untuk mengenakan biaya $25.00, kirim <code>2500</code>.
    </ParamField>

    <ParamField body="product_currency" type="string">
      Override mata uang opsional untuk biaya ini.
    </ParamField>

    <ParamField body="product_description" type="string">
      Override deskripsi opsional untuk biaya ini.
    </ParamField>

    <ParamField body="adaptive_currency_fees_inclusive" type="boolean">
      Jika true, termasuk biaya mata uang adaptif dalam <code>product_price</code>. Jika false, biaya ditambahkan di atasnya.
    </ParamField>

    <ParamField body="metadata" type="object">
      Metadata tambahan untuk pembayaran. Jika diabaikan, metadata langganan digunakan.
    </ParamField>
  </Accordion>
</AccordionGroup>

<Tabs>
<Tab title="Node.js SDK">

```javascript
import DodoPayments from 'dodopayments';

const client = new DodoPayments({ bearerToken: process.env.DODO_PAYMENTS_API_KEY });

async function chargeNow(subscriptionId) {
  const res = await client.subscriptions.charge(subscriptionId, { product_price: 2500 });
```

## Pengulangan pembayaran

Sistem deteksi penipuan kami mungkin memblokir pola pengulangan yang agresif (dan dapat menandainya sebagai pengujian kartu potensial). Ikuti kebijakan pengulangan yang aman.

<Warning>
Pola pengulangan yang mendadak dapat ditandai sebagai penipuan atau pengujian kartu yang dicurigai oleh sistem risiko dan pemroses kami. Hindari pengulangan yang terkelompok; ikuti jadwal penundaan dan panduan penyelarasan waktu di bawah ini.
</Warning>

### Prinsip untuk kebijakan pengulangan yang aman

- **Mekanisme backoff**: Gunakan backoff eksponensial antara percobaan ulang.
- **Batas percobaan ulang**: Batasi total percobaan ulang (maksimal 3–4 percobaan).
- **Penyaringan cerdas**: Coba ulang hanya pada kegagalan yang dapat dicoba ulang (misalnya, kesalahan jaringan/penerbit, dana tidak cukup); jangan pernah coba ulang penolakan keras.
- **Pencegahan pengujian kartu**: Jangan coba ulang kegagalan seperti `DO_NOT_HONOR`, `STOLEN_CARD`, `LOST_CARD`, `PICKUP_CARD`, `FRAUDULENT`, `AUTHENTICATION_FAILURE`.
- **Variasi metadata (opsional)**: Jika Anda mempertahankan sistem percobaan ulang sendiri, bedakan percobaan ulang melalui metadata (misalnya, `retry_attempt`).

### Jadwal pengulangan yang disarankan (langganan)

- **Percobaan ke-1**: Segera setelah Anda membuat biaya
- **Percobaan ke-2**: Setelah 3 hari
- **Percobaan ke-3**: Setelah 7 hari lagi (total 10 hari)
- **Percobaan ke-4 (akhir)**: Setelah 7 hari lagi (total 17 hari)

Langkah terakhir: jika masih belum dibayar, tandai langganan sebagai tidak dibayar atau batalkan, berdasarkan kebijakan Anda. Beri tahu pelanggan selama jendela untuk memperbarui metode pembayaran mereka.

### Hindari pengulangan mendadak; sesuaikan dengan waktu otorisasi

- Ikat percobaan ulang dengan cap waktu otorisasi asli untuk menghindari perilaku "ledakan" di seluruh portofolio Anda.
- Contoh: Jika pelanggan memulai percobaan atau mandat pada pukul 1:10 siang ini, jadwalkan percobaan ulang pada pukul 1:10 siang di hari-hari berikutnya sesuai dengan backoff Anda (misalnya, +3 hari → 1:10 siang, +7 hari → 1:10 siang).
- Sebagai alternatif, jika Anda menyimpan waktu pembayaran berhasil terakhir `T`, jadwalkan percobaan berikutnya pada `T + X days` untuk menjaga keselarasan waktu hari.

<Note>
Zona waktu dan DST: gunakan standar waktu yang konsisten untuk penjadwalan dan konversi hanya untuk tampilan untuk mempertahankan interval.
</Note>

### Kode penolakan yang sebaiknya tidak Anda ulangi

- `STOLEN_CARD`
- `DO_NOT_HONOR`
- `FRAUDULENT`
- `PICKUP_CARD`
- `AUTHENTICATION_FAILURE`
- `LOST_CARD`

<Note>
Untuk daftar lengkap alasan penolakan dan apakah mereka dapat diperbaiki oleh pengguna, lihat dokumentasi
[Kegagalan Transaksi](/api-reference/transaction-failures).
</Note>

<Tip>
Hanya coba ulang pada masalah lunak/sementara (misalnya, `insufficient_funds`, `issuer_unavailable`, `processing_error`, waktu tunggu jaringan). Jika penolakan yang sama terulang, hentikan percobaan ulang lebih lanjut.
</Tip>

### Pedoman implementasi (tanpa kode)

- Gunakan penjadwal/antrian yang mempertahankan cap waktu yang tepat; hitung percobaan berikutnya pada offset waktu-hari yang tepat (misalnya, `T + 3 days` pada HH:MM yang sama).
- Pertahankan dan rujuk cap waktu pembayaran berhasil terakhir `T` untuk menghitung percobaan berikutnya; jangan kumpulkan beberapa langganan pada saat yang sama.
- Selalu evaluasi alasan penolakan terakhir; hentikan percobaan ulang untuk penolakan keras dalam daftar yang diabaikan di atas.
- Batasi percobaan ulang bersamaan per pelanggan dan per akun untuk mencegah lonjakan yang tidak disengaja.
- Komunikasikan secara proaktif: email/SMS kepada pelanggan untuk memperbarui metode pembayaran mereka sebelum percobaan berikutnya yang dijadwalkan.
- Gunakan metadata hanya untuk observabilitas (misalnya, `retry_attempt`); jangan pernah mencoba untuk "menghindari" sistem penipuan/risiko dengan memutar bidang yang tidak signifikan.

## Lacak hasil dengan webhook

Implementasikan penanganan webhook untuk melacak perjalanan pelanggan. Lihat [Implementasi Webhook](/developer-resources/integration-guide#implementing-webhooks).

- **subscription.active**: Mandat diotorisasi dan langganan diaktifkan
- **subscription.failed**: Pembuatan gagal (misalnya, kegagalan mandat)
- **subscription.on_hold**: Langganan ditangguhkan (misalnya, status tidak dibayar)
- **payment.succeeded**: Biaya berhasil
- **payment.failed**: Biaya gagal

<Tip>
Untuk alur berdasarkan permintaan, fokus pada `payment.succeeded` dan `payment.failed` untuk mencocokkan biaya berbasis penggunaan.
</Tip>

## Pengujian dan langkah selanjutnya

<Steps>
<Step title="Buat dalam mode uji">
Gunakan kunci API uji Anda untuk membuat langganan dengan `payment_link: true`, lalu buka tautan dan selesaikan mandat.
</Step>
<Step title="Pemicu biaya">
Panggil endpoint biaya dengan jumlah kecil `product_price` (misalnya, `100`) dan verifikasi Anda menerima `payment.succeeded`.
</Step>
<Step title="Live">
Berpindahlah ke kunci API langsung Anda setelah Anda memvalidasi acara dan pembaruan status internal.
</Step>
</Steps>

## Pemecahan masalah

- **422 Permintaan Tidak Valid**: Pastikan `on_demand.mandate_only` disediakan pada saat pembuatan dan `product_price` disediakan untuk biaya.
- **Kesalahan mata uang**: Jika Anda mengganti `product_currency`, pastikan itu didukung untuk akun dan pelanggan Anda.
- **Tidak ada webhook yang diterima**: Verifikasi URL webhook dan konfigurasi rahasia tanda tangan Anda.
