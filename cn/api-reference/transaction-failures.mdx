## 概述

Dodo Payments API 提供详细的交易失败原因，帮助您理解为什么支付尝试未成功。这些失败原因在不同的支付方式和提供商之间是标准化的，使您能够在应用程序中实现一致的错误处理。

每个交易失败响应包括：
- 一个特定的失败原因代码
- 一个可读的错误信息
- 可用时关于失败的额外上下文
- 错误是否可以由用户纠正或需要系统干预

- `error_code` — 下表中的标准化失败原因。
- `error_message` — 面向**您**（商户）编写的易读说明。当 `error_code` 是下列标准化代码之一时，这里显示的是标题加建议操作，而不是支付处理商返回的原始文本。
- `retry_attempt` — 对于原始扣款为 `0`，对于每次计划中的订阅续费重试为 `1` 或更高。

## 交易失败原因

### 商户文案与客户文案

每个标准化失败代码都对应两条不同的消息，以便向正确的受众展示适当详细程度的信息：

| 受众 | 显示位置 | 内容 |
|----------|------------------|--------------|
| **您** | 付款中的 `error_message`、仪表板付款详情页，以及商户付款失败邮件 | 实际原因和建议操作，例如 *"持卡人尚未激活该卡。请客户通过其银行激活卡片，然后重试。"* |
| **您的客户** | 结账失败页面、[Customer Portal](/features/customer-portal) 以及 [催收](/features/recovery/subscription-dunning) 邮件 | 客户可以据此采取行动的简短易懂说明，例如 *"您的卡片尚未激活。请通过您的银行激活卡片，然后重试。"* |

<Note>
Customer Portal 在 `error_message` 中返回面向客户的措辞，而 merchant API 会针对同一笔付款返回面向商户的措辞。两者中的 `error_code` 完全相同。
</Note>

## 软拒绝与硬拒绝

每个失败代码都属于两类之一。这一区分决定了您应重试相同的支付方式，还是要求客户更换支付方式。

| 拒绝类型 | 含义 | 处理方式 | 示例 |
|--------------|---------------|------------|----------|
| **软拒绝** | 暂时性或可纠正的问题——同一张卡可能在稍后重试时成功，或客户修正输入后成功。 | 可以安全重试（等待一段时间后，或客户更正详细信息后）。 | `INSUFFICIENT_FUNDS`、`GENERIC_DECLINE`、`CARD_VELOCITY_EXCEEDED`、`PROCESSING_ERROR`、`NETWORK_ERROR`、`NETWORK_TIMEOUT`、`TRY_AGAIN_LATER` |
| **硬拒绝** | 终止性拒绝——重试同一张卡不会改变结果。 | **不要**重试同一张卡。请客户使用其他支付方式或联系其银行。 | `STOLEN_CARD`、`LOST_CARD`、`PICKUP_CARD`、`DO_NOT_HONOR`、`FRAUDULENT`、`INVALID_ACCOUNT` |

对于订阅续费，Dodo Payments 会自动应用这一规则：软拒绝由 [Subscription Payment Retries](/features/recovery/payment-retries) 重新尝试，而硬拒绝会立即结束重试链，最好通过 [Subscription Dunning](/features/recovery/subscription-dunning) 进行处理。

<Warning>
**绝不要向客户透露 `STOLEN_CARD`、`LOST_CARD`、`PICKUP_CARD` 或 `FRAUDULENT` 的真实原因。** 公开这些信息可能会向欺诈者泄露线索。始终向客户显示通用的拒绝消息（例如 *"您的卡片被拒绝。请联系您的银行或使用其他卡片。"*），并且只在内部记录具体代码。

Dodo Payments 已在其控制的界面上执行此规则：对于这四个代码，结账、Customer Portal 和催收邮件始终回退到通用拒绝消息，而您自己的文案会保留真实原因。在任何将 merchant API 返回的 `error_message` 展示给客户的地方，都应应用相同规则。
</Warning>

## 交易失败原因

下表列出了每个失败代码、其拒绝类型、客户是否可以解决、描述以及建议操作。

| 失败代码 | 类型 | 用户错误 | 描述 | 建议操作 |
|--------------|------|------------|-------------|--------------------|
| `AUTHENTICATION_FAILURE` | 软 | 是 | 交易期间身份验证失败 | 请客户重试并完成 3DS 身份验证，或使用其他卡片 |
| `AUTHENTICATION_REQUIRED` | 软 | 是 | 需要额外身份验证才能完成交易 | 提示客户完成 3DS 身份验证。对于订阅续费，请客户返回并完成身份验证 |
| `AUTHENTICATION_TIMEOUT` | 软 | 是 | 身份验证过程超时 | 请客户重试并及时完成身份验证 |
| `CARD_DECLINED` | 软 | 否 | 发卡银行未说明具体原因而拒绝了该卡（通用拒绝） | 请客户重试、联系其银行或使用其他卡片 |
| `CARD_NOT_ACTIVATED` | 软 | 是 | 持卡人尚未激活该卡 | 请客户通过其银行激活卡片，然后重试 |
| `CARD_VELOCITY_EXCEEDED` | 软 | 是 | 短时间内尝试了过多交易 | 请客户等待后稍后重试，或联系其银行了解限额 |
| `CUSTOMER_CANCELLED` | 软 | 是 | 客户取消了交易 | 客户准备好后，请其重新开始结账 |
| `DO_NOT_HONOR` | 硬 | 否 | 发卡银行明确拒绝了交易（ISO 8583 代码 05——不予承兑）；网络将其视为终止性拒绝 | 请客户联系其银行；不要重试同一张卡 |
| `EXPIRED_CARD` | 硬 | 是 | 卡片已过期 | 请客户使用有效期有效的卡片 |
| `FRAUDULENT` | 硬 | 是 | 交易被标记为可能存在欺诈 | 向客户显示通用拒绝消息——不要透露原因。请其使用其他卡片 |
| `GENERIC_DECLINE` | 软 | 否 | 交易因未指定原因被拒绝 | 请客户联系其银行或尝试其他卡片 |
| `INCORRECT_CVC` | 软 | 是 | 提供的 CVC 代码不正确 | 请客户重新输入正确的 CVC |
| `INCORRECT_NUMBER` | 软 | 是 | 卡号输入不正确 | 请客户重新输入正确的卡号 |
| `INSUFFICIENT_FUNDS` | 软 | 是 | 账户余额不足，无法完成交易 | 请客户使用其他支付方式，或在资金到账后重试 |
| `INVALID_ACCOUNT` | 硬 | 是 | 提供的账户详细信息无效 | 请客户联系其银行或使用其他卡片 |
| `INVALID_AMOUNT` | 软 | 是 | 交易金额无效 | 与客户核实金额和任何购买限额 |
| `INVALID_CARD_NUMBER` | 软 | 是 | 卡号格式无效 | 请客户重新输入有效的卡号 |
| `INVALID_CARD_OWNER` | 软 | 是 | 持卡人信息无效 | 请客户更正持卡人姓名 |
| `INVALID_CVC` | 软 | 是 | CVC 格式无效 | 请客户重新输入有效的 CVC |
| `INVALID_EXPIRY_YEAR` | 软 | 是 | 卡片有效期年份无效 | 请客户输入有效的有效期 |
| `INVALID_PIN` | 软 | 是 | 提供的 PIN 不正确 | 请客户重新输入正确的 PIN |
| `INVALID_REQUEST` | 软 | 是 | 交易请求包含无效数据 | 检查支付请求字段，并使用有效数据重新提交 |
| `INVALID_UPI_ID` | 软 | 是 | 提供的 UPI ID 无效 | 请客户输入有效的 UPI ID |
| `LIMIT_EXCEEDED` | 软 | 是 | 交易超出卡片或账户限额 | 请客户联系其银行了解限额，或使用其他方式 |
| `LIVE_MODE_TEST_CARD` | 硬 | 是 | 在 live mode 中使用了测试卡 | 使用真实卡片——在 live mode 中重试测试卡始终会失败 |
| `LOST_CARD` | 硬 | 是 | 卡片已被报告丢失 | 向客户显示通用拒绝消息——不要透露原因。请其使用其他卡片 |
| `MANDATE_INVALID` | 软 | 是 | 支付 mandate 无效 | 请客户重新设置支付 mandate |
| `MANDATE_REQUIRED` | 软 | 是 | 此交易需要 mandate | 设置 mandate，并请客户在扣款前授权 |
| `MANDATE_REQUIRED_SYSTEM` | 硬 | 否 | 系统要求此交易类型使用 mandate | 确保在扣款前完成 mandate 设置流程 |
| `NETWORK_ERROR` | 软 | 否 | 交易期间发生网络错误 | 暂时性错误——短暂延迟后重试付款 |
| `NETWORK_TIMEOUT` | 软 | 否 | 网络请求超时 | 暂时性错误——短暂延迟后重试付款 |
| `ORDER_ALREADY_EXISTS` | 软 | 否 | 此交易已存在订单（重复创建订单） | 重试前检查现有订单的状态；如果问题持续，请联系支持团队 |
| `ORDER_CREATION_FAILED` | 软 | 否 | 创建交易订单失败 | 暂时性/系统错误——重试付款；如果问题持续，请联系支持团队 |
| `PAYMENT_METHOD_PROVIDER_DECLINED` | 硬 | 是 | 支付方式提供商拒绝了交易 | 请客户联系其提供商或使用其他支付方式 |
| `PAYMENT_METHOD_UNSUPPORTED` | 硬 | 是 | 此支付方式不支持该交易 | 请客户使用受支持的支付方式 |
| `PICKUP_CARD` | 硬 | 是 | 卡片已被报告丢失或被盗，并被标记为需要收回 | 向客户显示通用拒绝消息——不要透露原因。请其使用其他卡片 |
| `PROCESSING_ERROR` | 软 | 否 | 处理交易时发生错误 | 暂时性错误——重试付款；如果问题持续，请客户联系其银行 |
| `PROVIDER_UNSUPPORTED` | 硬 | 否 | 支付提供商不支持此交易类型 | 请客户使用其他支付方式 |
| `REENTER_TRANSACTION` | 软 | 是 | 需要重新输入交易 | 请客户重试付款 |
| `REVOCATION_OF_AUTHORIZATION` | 硬 | 是 | 交易授权已被撤销 | 请客户使用其他支付方式 |
| `STOLEN_CARD` | 硬 | 是 | 卡片已被报告被盗 | 向客户显示通用拒绝消息——不要透露原因。请其使用其他卡片 |
| `SUBSCRIPTION_NOT_ACTIVE` | 硬 | 否 | 订阅未处于活动状态，因此无法处理周期性扣款 | 在再次尝试扣款前重新激活订阅（例如，更新支付方式） |
| `TRANSACTION_NOT_ALLOWED` | 硬 | 是 | 此卡片或账户不允许该交易 | 请客户联系其银行以允许此交易类型，或使用其他卡片 |
| `TRANSACTION_NOT_APPROVED` | 硬 | 是 | 交易未获批准 | 请客户联系其银行或尝试其他卡片 |
| `TRY_AGAIN_LATER` | 软 | 否 | 应稍后重试交易 | 暂时性错误——稍后重试付款 |
| `UNKNOWN_ERROR` | 软 | 否 | 发生未知错误 | 重试付款；如果问题持续，请联系支持团队 |

<Note>
**用户错误**表示付款拒绝是否可以由客户解决。当 `Yes` 时，客户可以采取措施修复问题（例如输入正确的卡片详细信息）。当 `No` 时，拒绝源于系统级问题或银行限制，客户无法直接解决。
</Note>

<Info>
当发卡银行自身的风险引擎将持卡人标记为高风险客户时，即使与商户或交易详细信息无关，卡片也可能被拒绝。这类拒绝通常会显示为通用代码，例如 `DO_NOT_HONOR`、`GENERIC_DECLINE`、`CARD_DECLINED`、`TRANSACTION_NOT_APPROVED` 或 `FRAUDULENT`。在这些情况下，银行不会分享具体原因，Dodo Payments 和商户也无法推翻该决定。请客户联系其银行解决这一标记，或使用其他卡片或支付方式。
</Info>

## 以编程方式处理失败

从 `payment.failed` webhook 或 payment object 中读取 `error_code`，将其映射到上面的建议操作，并决定是否重试。对于订阅续费，软拒绝会自动为您重试——请参阅 [Subscription Payment Retries](/features/recovery/payment-retries)。

对于 API 层和业务逻辑错误（例如 `PAYMENT_NOT_SUCCEEDED` 或 `REFUND_WINDOW_EXPIRED`），这些错误并非卡片拒绝，请参阅 [错误代码](/api-reference/error-codes) 参考。
