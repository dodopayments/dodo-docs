## 步骤 2：为代币使用创建计量器

计量器汇总传入的使用事件，并将其转换为信用扣除。在创建计划产品之前，您需要这个，因为在产品创建的步骤 3 中您将附加它。

1. 在仪表板侧边栏中，转到 **产品 → 计量器**
2. 点击 **创建计量器**

填写：

**计量器名称**: `Token Usage Meter`

**事件名称**: `api.tokens_used` *(这必须与您的应用发送的内容完全匹配)*

**聚合类型**: `Sum` ——我们将每个事件的代币计数汇总

**超过属性**: `tokens` ——每个事件上的元数据键，其值将被汇总

**测量单位**: `tokens`

事件名称区分大小写。`api.tokens_used` ≠ `Api.Tokens.Used` ——选择一个并坚持使用。


保存计量器并复制其 ID ——你在附加到产品时会引用它。

计量器创建完成。现在我们可以在配置产品时将其连接到信用。


## 步骤 3：创建计划产品

两个计划都需要是 **Usage Based Billing** 产品，而不是简单的订阅——计量器只能附加到 UBB 产品，您需要计量器在客户调用您的 API 时自动扣除信用。UBB 产品仍支持循环基价（`$29` / `$99`）；在此基础上的使用通过信用计费。

### 初级计划 ($29/月 —— 10M 代币，无超额使用)

1. 转到 **产品 → 创建产品**
2. 选择 **Usage Based Billing** 作为定价类型
3. 填写：

**产品名称**: `NeuralAPI Starter`

**描述**: `10 million API tokens per month. Perfect for individual developers and small projects.`

**固定价格**: `29.00` (循环基价——即使在任何使用之前也按月计费)

**计费周期**: `Monthly`

**货币**: `USD`

在 **选择计量器** 部分，点击 **+** 并添加 `Token Usage Meter`。然后在计量器上：

1. 切换 **在信用中计费使用** 开
2. **信用权益**: 选择 `API Tokens`
3. **每信用的计量单位**: `1` ——事件中的每个代币映射到 1 个扣除的信用
4. **免费阈值**: `0` ——信用分配本身是客户的“免费层”我们不需要额外的免费带

这就是使传入的 `api.tokens_used` 事件实际从客户余额中扣除的连接。

在附加计费计量器后，仍在产品上，滚动到显示的信用配置部分：

**每个计费周期发行的信用**: `10000000`

**允许超额使用**: **禁用** —— 初级客户在代币用尽时被阻止

**导入默认信用设置**: 启用 —— 使用信用权益的 30 天到期

点击 **保存** 并复制产品 ID。

初级计划：$29/月基价，10M 代币/周期，零限制，自动通过计量器扣除。

### Pro 计划 ($99/月 —— 40M 代币，启用超额使用)

与初级一样，只是数字更大：

**产品名称**: `NeuralAPI Pro`

**描述**: `40 million API tokens per month with overage. Built for production applications.`

**固定价格**: `99.00`

**计费周期**: `Monthly`

**货币**: `USD`

与 Starter 相同：添加 `Token Usage Meter`，切换 **在信用中计费使用** 开，选择 `API Tokens`，**每信用的计量单位** `1`，**免费阈值** `0`。

配置信用发放，此时启用超额使用：

**每个计费周期发行的信用**: `40000000`

**导入默认信用设置**: **禁用** —— 我们需要为每个产品定制超额设置

**允许超额使用**: **启用**

**每单位价格**: `0.000005` 美元/代币（即，每千代币 $0.005，或每百万代币 $5——高于计划的有效每代币率以阻止溢出）

**超额使用行为**: `Bill overage at billing` ——超额使用在下一个发票中收费，然后余额重置

保存产品并复制产品 ID。

Pro 计划：$99/月基价，40M 代币/周期，超额使用 $0.005/1K 代币，自动通过计量器扣除。

## 步骤 4：创建代币充值包

充值包是一次性购买，为现有客户的余额提供 5,000,000 代币。

1. 转到 **产品 → 创建产品**
2. 选择 **单次支付** 作为定价类型
3. 填写：

**产品名称**: `Token Top-Up Pack`

**描述**: `Instantly add 5 million tokens to your NeuralAPI balance.`

**价格**: `19.00`

**货币**: `USD`

1. 在 **权益** 部分，点击 **附加** 在 **信用** 旁边
2. 选择 `API Tokens`
3. 设置 **发行的信用**: `5000000`
4. **禁用** *导入默认信用设置* —— 我们想覆盖默认的 30 天到期
5. 设置 **信用到期**: `365 days`
6. 保存产品

复制产品 ID。

为何充值包到期时间更长？订阅信用每 30 天重置，因为这是周期。充值包是*预付购买*——客户提前支付 $19，合理地期望这些代币能持续超过一个月。365 天匹配 OpenAI、AWS 和 Anthropic 的实际预付信用运作，同时仍然限制您的责任，以防客户无限期地储存。

配置的充值包——购买后授予 5,000,000 代币，有效期 365 天。

## 步骤 7：连接 Webhook

Webhooks 让您的服务器对余额变化做出反应——您将使用它们在客户达到零之前发送“余额不足”邮件。

Webhooks 需要一个公共 URL。对于本地开发，使用 [ngrok](https://ngrok.com) 或任何隧道：

复制 `https://...ngrok-free.app` URL。

1. 在仪表板中，转到 **开发者 → Webhooks → 添加端点**
2. **URL**: `https://your-tunnel.ngrok-free.app/webhooks/dodo`
3. 至少订阅：
   - `credit.added`
   - `credit.deducted`
   - `credit.overage_charged`
4. 保存并复制 **签名秘密**
5. 将其粘贴到 `.env` 作为 `DODO_PAYMENTS_WEBHOOK_KEY`，然后重启 `npm run dev`

SDK 的 `dodo.webhooks.unwrap()` 验证 `webhook-id`, `webhook-timestamp` 和 `webhook-signature` 标头使用您的签名秘密。您不需要手动滚动 HMAC 验证——而且您不应该，因为 Dodo Payments 使用 [标准 Webhooks](https://www.standardwebhooks.com/)，它签署 `id.timestamp.body` 而不仅仅是主体。

## 故障排除

**可能的原因：**
- 计量器的事件名称与您正在发送的 `event_name` 不匹配（`api.tokens_used` 区分大小写）
- 计量器未链接到产品上的 `API Tokens` 信用——转到产品的计量器配置并确认 **在信用中计费使用** 是启用的
- `metadata.tokens` 键与计量器的“超过属性”字段不匹配
- 客户的授予已过期（检查客户的信用历史）

**要检查的内容：**
1. **产品 → 计量器**：打开计量器并确认其显示在产品附加的已链接信名称
2. 计量器上的 **事件** 标签——摄取的事件在扣除之前应显示在此处
3. **客户 → \[客户\] → 信用**：分类帐条目应在一两分钟内出现

**可能的原因：**
- 客户尚未完成结账——信用仅在成功付款后发布
- 您使用了错误的 `customer_id` 进行查询（使用仪表板上的 `cus_...` ID，而不是您自己的数据库 ID）
- `CREDIT_ENTITLEMENT_ID` 在 `.env` 中与附加到产品的信用不匹配

**要检查的内容：**
打开 **客户 → \[客户\] → 信用**。如果没有信用出现在那里，则产品权益未附加或支付未完成。

**可能的原因：**
- 超额使用未在 **Pro 产品的信用附加** 中启用（信用级别设置只是默认值）
- 客户实际上是初级计划，而不是 Pro
- 超额使用限制设置为 0

**要检查的内容：**
编辑 Pro → 权益 → 信用 → 确认 **允许超额使用** 启用和 **每单位价格** 是 `0.000005` （= 每百万代币 $5；双重检查前导零——字段接受的是每代币价格，而不是每千代币价格）。

**可能的原因：**
- 正文解析顺序：`express.json()` 应用于 `/webhooks/dodo` 之前 `express.raw()` ——SDK 需要请求的**原始字节**，而不是解析的 JSON
- `DODO_PAYMENTS_WEBHOOK_KEY` 中的签名秘密错误
- 反向代理正在重写标头

**要检查的内容：**
确认 `app.use('/webhooks/dodo', express.raw(...))` 行出现在 `app.use(express.json())` 之前在 `server.ts` 中。

**准备投入生产？** 加强这些：
- **`/credits/:customerId` 和 `/api/generate` 上的身份验证** —— 目前任何人都可以用任何客户 ID 访问这些。认证用户并在服务器端查找*他们的*客户 ID。
- **稳定的 `event_id`s** —— 示例使用 `Date.now() + random`。在生产中，使用您的请求 ID，以便重试是幂等的（Dodo Payments 通过 `event_id` 取消重复）。
- **持久化客户↔用户映射** —— 在第一次结账后在您的数据库中存储 `customer_id`，这样您就不需要手动粘贴步骤。
- **决定订阅结束时会发生什么。** 计划信用保留在客户的分类帐中，直到其自然到期（从发行开始算起 30 天），充值信用则在 365 天内有效——但本食谱的 `/api/generate` 仅检查*余额*，不检查订阅状态。因此已取消的客户仍然可以消费其剩余的代币。这是对消费者友好的默认设置。如果你想要更严格的访问控制，可以 (a) 监听 `subscription.cancelled` webhook，并根据订阅状态限制 `/api/generate`，或者 (b) 调用 Dodo 的分类帐 API 以在取消时抵扣未使用的计划信用，而留出充值信用不变。
- **监控使用计费仪表板**，以便及早发现计量异常。

<Accordion title="Balance always shows 0 or 'customer not found'">
**Possible causes:**
- The customer hasn't completed checkout yet — credits are only issued after a successful payment
- You're querying with the wrong `customer_id` (use the `cus_...` ID from the dashboard, not your own DB ID)
- The `CREDIT_ENTITLEMENT_ID` in `.env` doesn't match the credit attached to the product

**What to check:**
Open **Customers → \[Customer\] → Credits**. If no credits appear there, the product entitlement wasn't attached or the payment didn't complete.
</Accordion>

<Accordion title="Overage not working for Pro plan customers">
**Possible causes:**
- Overage wasn't enabled on the **Pro product's credit attachment** (the credit-level setting is just a default)
- The customer is actually on Starter, not Pro
- Overage limit was set to 0

**What to check:**
Edit Pro → Entitlements → Credits → confirm **Allow Overage** is on and **Price Per Unit** is `0.000005` (= $5 per million tokens; double-check the leading zeros — the field takes per-token price, not per-1K).
</Accordion>

<Accordion title="`Webhook verification failed` in logs">
**Possible causes:**
- Body parsing order: `express.json()` was applied to `/webhooks/dodo` before `express.raw()` — the SDK needs the **raw bytes** of the request, not parsed JSON
- Wrong signing secret in `DODO_PAYMENTS_WEBHOOK_KEY`
- Reverse proxy is rewriting headers

**What to check:**
Confirm the `app.use('/webhooks/dodo', express.raw(...))` line comes *before* `app.use(express.json())` in `server.ts`.
</Accordion>
</AccordionGroup>

<Info>
**Going to production?** Tighten these:
- **Auth on `/credits/:customerId` and `/api/generate`** — currently anyone can hit these with any customer ID. Authenticate users and look up *their* customer ID server-side.
- **Stable `event_id`s** — the example uses `Date.now() + random`. In production, use your request ID so retries are idempotent (Dodo Payments deduplicates by `event_id`).
- **Persist the customer↔user mapping** — store `customer_id` in your DB after the first checkout so you don't need a manual paste step.
- **Decide what happens when a subscription ends.** Plan credits remain in the customer's ledger until their natural expiry (30 days from issuance) and top-up credits stay valid for 365 days — but the cookbook's `/api/generate` only checks *balance*, not subscription status. So a cancelled customer can still consume their remaining tokens. That's the consumer-friendly default. If you want stricter access control, either (a) listen to the `subscription.cancelled` webhook and gate `/api/generate` on subscription status, or (b) call Dodo's ledger API to debit unused plan credits on cancel while leaving top-up credits intact.
- **Monitor the Usage Billing dashboard** to catch metering anomalies early.
</Info>
