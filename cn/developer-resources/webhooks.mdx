Webhooks 在 Dodo Payments 账户中发生特定事件时提供实时通知。使用 webhooks 来自动化工作流程、更新数据库、发送通知，并保持系统同步。

<Info>
我们的 webhook 实现遵循 [Standard Webhooks](https://standardwebhooks.com/) 规范，确保与行业最佳实践和现有 webhook 库兼容。
</Info>

## Integration Connectors

您无需自行构建 webhook receiver，也可以使用 integration connectors 将 webhook events 直接路由到第三方服务。这样便无需为常见平台编写和维护自定义 webhook handlers。

### Connectors 的工作方式

Connector 会执行转换，将 Dodo Payments event 转换为目标服务所需的格式。您需要提供的详细信息取决于目标服务：

| Connector 类型 | 您需要提供的内容 | 目标服务 |
|----------------|------------------|--------------|
| **Incoming webhook URL** | 在供应商自己的 dashboard 中创建的 webhook URL。无需 API key。 | [Slack](/integrations/slack)、[Discord](/integrations/discord)、[Microsoft Teams](/integrations/microsoft-teams)、[Zapier](/integrations/zapier)、[Windmill](/integrations/windmill) |
| **Vendor API** | API key。目标 URL 来自 connector template。 | [Resend](/integrations/resend)、[SendGrid](/integrations/sendgrid)、[Segment](/integrations/segment)、[Customer.io](/integrations/customer-io)、[HubSpot](/integrations/hubspot)、[Close CRM](/integrations/close-crm)、[Loops](/integrations/loops) |

Dashboard 中的 connector picker 会显示当前对您的 business 可用的完整集合。因此，请将上表视为提供分步设置说明的目标服务列表，而非完整清单。有关各目标服务在接收 events 后可以执行的操作，请参阅 [External Integrations](/integrations/introduction)。

### 设置 Connector

创建或编辑 endpoint 时选择一个 connector，侧边面板会显示针对该目标服务编写的设置说明，例如如何在 Slack 中创建 incoming webhook URL，或在哪里查找 Resend API key。保存前，请运行 connector transformation test，以确认 event 已正确转换为目标服务所需的格式。

<Tip>
使用 connector 可在无需编写代码的情况下连接受支持的目标服务。如果需要自定义逻辑，请改用带有 [transformation](#transformations) 的标准 endpoint。
</Tip>

## Webhook Delivery

### 超时

Webhooks 对 connection 和 read operations 均设有 **15 秒超时窗口**。请确保 endpoint 快速响应，以避免超时。

<Tip>
通过立即使用 `200` status code 确认收到 webhook，然后在后台异步处理实际业务。
</Tip>

### 自动重试

如果 webhook delivery 失败，Dodo Payments 会自动采用 exponential backoff 进行重试，以避免系统过载。

| Attempt | Delay | Description |
|---------|------------------------------|-------------|
| 1 | Immediately | 第一次重试会立即进行 |
| 2 | 5 seconds | 短暂延迟后进行第二次尝试 |
| 3 | 5 minutes | 增加 backoff 后进行第三次尝试 |
| 4 | 30 minutes | 继续 backoff 后进行第四次尝试 |
| 5 | 2 hours | 延长延迟后进行第五次尝试 |
| 6 | 5 hours | 使用更长延迟进行第六次尝试 |
| 7 | 10 hours | 使用最大延迟进行第七次尝试 |
| 8 | 10 hours | **最后一次尝试** - 如果仍然失败，则将 webhook 标记为失败 |

<Info>
**每个 webhook event 最多重试 8 次**。例如，如果 webhook 在成功前失败三次，则从第一次尝试开始计算，总 delivery 时间约为 35 分钟 5 秒。
</Info>

<Tip>
您可以随时使用 Dodo Payments dashboard 手动重试单条消息，或批量恢复所有失败的消息。
</Tip>

### 幂等性

每个 webhook event 都包含唯一的 `webhook-id` header。使用此标识符实现幂等性，防止重复处理。

```javascript
// Example: Storing webhook IDs to prevent duplicate processing
const processedWebhooks = new Set();

app.post('/webhook', (req, res) => {
  const webhookId = req.headers['webhook-id'];
  
  if (processedWebhooks.has(webhookId)) {
    return res.status(200).json({ received: true });
  }
  
  processedWebhooks.add(webhookId);
  // Process the webhook...
});
```

<Warning>
请始终实现幂等性检查。由于存在重试，您可能会多次收到同一个 event。
</Warning>

### Event Ordering

由于重试或网络状况，Webhook events 可能会乱序到达。请设计系统，使其能够按任意顺序处理 events。

<Info>
无论 webhook event 最初何时发出，您收到的始终是 **delivery 时最新的 payload**。
</Info>

## 保护 Webhooks

为确保 webhooks 的安全性，请始终验证 payloads 并使用 HTTPS。

### 验证 Signatures

每个 webhook request 都包含 `webhook-signature` header，该 header 是 webhook payload 和 timestamp 的 HMAC SHA256 signature，并使用您的 secret key 进行签名。

#### SDK verification（推荐）

所有官方 SDK 都内置了用于安全验证和解析传入 webhooks 的 helpers。有两种方法可用：

* `unwrap()`：使用 webhook secret key 验证 signatures
* `unsafe_unwrap()`：不验证 signatures，直接解析 payloads

<Tip>
  初始化 Dodo Payments client 时，通过 `DODO_PAYMENTS_WEBHOOK_KEY` 提供 webhook secret。
</Tip>

<CodeGroup>

```typescript TypeScript/Node.js
import DodoPayments from 'dodopayments';
import express from 'express';

const app = express();
app.use(express.raw({ type: 'application/json' }));

const client = new DodoPayments({
  bearerToken: process.env.DODO_PAYMENTS_API_KEY,
  environment: process.env.DODO_PAYMENTS_ENVIRONMENT,
  webhookKey: process.env.DODO_PAYMENTS_WEBHOOK_KEY,
});

app.post('/webhook', async (req, res) => {
  try {
    const unwrapped = client.webhooks.unwrap(req.body.toString(), {
      headers: {
        'webhook-id': req.headers['webhook-id'] as string,
        'webhook-signature': req.headers['webhook-signature'] as string,
        'webhook-timestamp': req.headers['webhook-timestamp'] as string,
      },
    });
    res.json({ received: true });
  } catch (error) {
    res.status(401).json({ error: 'Invalid signature' });
  }
});
```

```python Python
from fastapi import FastAPI, Request, HTTPException
from dodopayments import DodoPayments
import os

app = FastAPI()
client = DodoPayments(
    bearer_token=os.getenv("DODO_PAYMENTS_API_KEY"),
    environment=os.getenv("DODO_PAYMENTS_ENVIRONMENT"),
    webhook_key=os.getenv("DODO_PAYMENTS_WEBHOOK_KEY"),
)

@app.post("/webhook")
async def handle_webhook(request: Request):
    try:
        unwrapped = client.webhooks.unwrap(
            await request.body(),
            headers={
                "webhook-id": request.headers.get("webhook-id", ""),
                "webhook-signature": request.headers.get("webhook-signature", ""),
                "webhook-timestamp": request.headers.get("webhook-timestamp", ""),
            },
        )
        return {"received": True}
    except Exception:
        raise HTTPException(status_code=401, detail="Invalid signature")
```

```go Go
import (
	"context"
	"io"
	"net/http"
	"os"
	"github.com/dodopayments/dodopayments-go"
	"github.com/dodopayments/dodopayments-go/option"
)

func webhookHandler(w http.ResponseWriter, r *http.Request) {
	client := dodopayments.NewClient(
		option.WithBearerToken(os.Getenv("DODO_PAYMENTS_API_KEY")),
		option.WithEnvironment(os.Getenv("DODO_PAYMENTS_ENVIRONMENT")),
		option.WithWebhookKey(os.Getenv("DODO_PAYMENTS_WEBHOOK_KEY")),
	)
	rawBody, _ := io.ReadAll(r.Body)
	if _, err := client.Webhooks.Unwrap(context.Background(), rawBody, map[string]string{
		"webhook-id":       r.Header.Get("webhook-id"),
		"webhook-signature": r.Header.Get("webhook-signature"),
		"webhook-timestamp": r.Header.Get("webhook-timestamp"),
	}); err != nil {
		http.Error(w, "Invalid signature", http.StatusUnauthorized)
		return
	}
	w.WriteHeader(http.StatusOK)
}
```

</CodeGroup>

#### 手动 verification（替代方案）

如果您不使用 SDK，可以按照 Standard Webhooks spec 自行验证 signatures：

1. 将 `webhook-id`、`webhook-timestamp` 和精确的原始字符串化 `payload` 用句点（`.`）连接，构建 signed message。
2. 使用 Dashboard 中的 webhook secret key，计算该字符串的 HMAC SHA256。
3. 将计算出的 signature 与 `webhook-signature` header 进行比较。如果匹配，则 webhook 是有效的。

<Info>
  我们遵循 Standard Webhooks specification。您可以使用其 libraries 验证 signatures：[https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries](https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries)。有关 event payload formats，请参阅 [Webhook Payload](/developer-resources/webhooks/intents/payment)。
</Info>

### 响应 Webhooks

* 您的 webhook handler 必须返回 `2xx status code`，以确认收到 event。
* 任何其他 response 都会被视为失败，并且 webhook 将被重试。

### 最佳实践

<AccordionGroup>
<Accordion title="Use HTTPS endpoints only" icon="lock">
  始终为 webhook endpoints 使用 HTTPS URLs。HTTP endpoints 容易受到中间人攻击，并会暴露 webhook data。
</Accordion>

<Accordion title="Respond immediately" icon="bolt">
  收到 webhook 后立即返回 `200` status code。异步处理 event，以避免超时。
  

  ```javascript
  app.post('/webhook', async (req, res) => {
    // Acknowledge receipt immediately
    res.status(200).json({ received: true });
    
    // Process asynchronously
    processWebhookAsync(req.body).catch(console.error);
  });
  ```

</Accordion>

<Accordion title="Handle duplicate events" icon="rotate">
  使用 `webhook-id` header 实现幂等性，从而安全地多次处理同一个 event 且不产生副作用。
</Accordion>

<Accordion title="Secure your webhook secret" icon="key">
  使用 environment variables 或 secrets manager 安全地存储 webhook secret。切勿将 secrets 提交到 version control。
</Accordion>
</AccordionGroup>

## Webhook Payload Structure

了解 webhook payload structure 有助于正确解析和处理 events。

### Request Format

```http
POST /your-webhook-url
Content-Type: application/json
```

### Headers

<ParamField header="webhook-id" type="string" required>
此 webhook event 的唯一标识符。使用它进行幂等性检查。
</ParamField>

<ParamField header="webhook-signature" type="string" required>
用于验证 webhook authenticity 的 HMAC SHA256 signature。
</ParamField>

<ParamField header="webhook-timestamp" type="string" required>
发送 webhook 时的 Unix timestamp（以秒为单位）。
</ParamField>

### Request Body

<ResponseField name="business_id" type="string" required>
您的 Dodo Payments business identifier。
</ResponseField>

<ResponseField name="type" type="string" required>
触发此 webhook 的 event type（例如 `payment.succeeded`、`subscription.active`）。
</ResponseField>

<ResponseField name="timestamp" type="string" required>
Event 发生时间的 ISO 8601 格式 timestamp。
</ResponseField>

<ResponseField name="data" type="object" required>
包含 event 详细信息的 event-specific payload。

<Expandable title="Data object properties">
  <ResponseField name="payload_type" type="string">
  Resource 类型，可能是：`Payment`、`Subscription`、`Refund`、`Dispute`、`LicenseKey`、`CreditLedgerEntry`、`CreditBalanceLow`、`AbandonedCheckout`、`DunningAttempt`、`EntitlementGrant` 或 `Payout`。
  </ResponseField>
  
  Additional fields 会因 event type 而异。完整 schemas 请参阅 event-specific documentation。
</Expandable>
</ResponseField>

### 示例 Payload

```json
{
  "business_id": "string",
  "type": "payment.succeeded | payment.failed |...",
  "timestamp": "2024-01-01T12:00:00Z",
  "data": {
    "payload_type": "Payment | Subscription | Refund | Dispute | LicenseKey | CreditLedgerEntry | CreditBalanceLow | AbandonedCheckout | DunningAttempt | EntitlementGrant | Payout",
    // ... event-specific fields (see below)
  }
}
```

### Implementation Example

以下是一个完整的 Express.js implementation，展示 webhook verification 和 handling：

<CodeGroup>

```typescript Express.js Webhook Handler
import { Webhook } from "standardwebhooks";
import express from "express";

const app = express();
app.use(express.json());

const webhook = new Webhook(process.env.DODO_WEBHOOK_SECRET);

app.post('/webhook/dodo-payments', async (req, res) => {
  try {
    // Extract webhook headers
    const webhookHeaders = {
      "webhook-id": req.headers["webhook-id"] as string,
      "webhook-signature": req.headers["webhook-signature"] as string,
      "webhook-timestamp": req.headers["webhook-timestamp"] as string,
    };

    // Verify the webhook signature
    const payload = JSON.stringify(req.body);
    await webhook.verify(payload, webhookHeaders);
    
    // Acknowledge receipt immediately
    res.status(200).json({ received: true });
    
    // Process webhook asynchronously
    processWebhookAsync(req.body).catch(console.error);
    
  } catch (error) {
    console.error('Webhook verification failed:', error);
    res.status(400).json({ error: 'Invalid signature' });
  }
});

async function processWebhookAsync(data: any) {
  // Handle the webhook event based on type
  switch (data.type) {
    case 'payment.succeeded':
      await handlePaymentSucceeded(data);
      break;
    case 'subscription.active':
      await handleSubscriptionActive(data);
      break;
    // Add more event handlers...
  }
}
```

```javascript Testing Webhooks Locally

dodo wh listen
```

CLI 会与 Dodo Payments 建立 WebSocket connection，并将每个 webhook event 转发到本地 endpoint（例如 `http://localhost:3000/webhook`），同时保留包括 signature headers 在内的所有 headers，以便进行 verification testing。

<Info>
该 listener 仅适用于 **test mode** API keys。运行 `dodo login`，并在使用此命令前选择 Test Mode。
</Info>

### 触发 Mock Webhook Events

向任意 endpoint 发送 mock webhook payloads，无需创建真实 transactions：

```bash
dodo wh trigger
```

此 interactive tool 允许您选择 event type，并向 endpoint 发送逼真的 mock payload。它会循环运行，方便您在一次 session 中测试多个 events。

trigger command 覆盖 Dodo Payments delivery 的全部 46 种 event types，包括 subscription、payment、refund、dispute、license key、payout、credit、abandoned checkout、dunning 和 entitlement grant 系列 — exact list 请参阅 [Supported Webhook Events](/developer-resources/sdks/cli#supported-webhook-events)。

<Warning>
来自 `dodo wh trigger` 的 mock webhook payloads 未签名。仅在 testing 期间，在 webhook handler 中使用 `unsafe_unwrap()`，而不是 `unwrap()`。
</Warning>

## Advanced Settings

**Advanced** 标签页提供额外的 configuration options，用于精细调整 webhook endpoint behavior。

### Rate Limiting（Throttling）

控制 webhook events 发送到 endpoint 的速率，避免系统过载。

<Steps>
<Step title="Open Advanced Tab">
    在 endpoint details page 中，点击 **Advanced** 标签页。
</Step>

<Step title="Configure Rate Limit">
    在 “Rate Limit (throttling)” 部分，点击 **Edit** 修改 rate limit settings。
    
    <Info>
    默认情况下，webhooks 不应用 rate limit，这意味着 events 会在发生后立即 delivery。
    </Info>
</Step>

<Step title="Set Your Limit">
    配置所需的 rate limit，以控制 webhook delivery frequency 并防止系统过载。
</Step>
</Steps>

<Tip>
当 webhook handler 需要时间处理 events，或您希望将多个 events 批量处理时，可以使用 rate limiting。
</Tip>

### 自定义 Headers

向发送到 endpoint 的所有 webhook requests 添加自定义 HTTP headers。这对于 authentication、routing 或添加 metadata 很有用。

<Steps>
<Step title="Add Headers">
    在 “Custom Headers” 部分，为每个 custom header 输入 **Key** 和 **Value**。
</Step>

<Step title="Add Multiple Headers">
    根据需要点击 **+** 按钮添加更多 custom headers。
</Step>
</Steps>

您的 custom headers 会包含在发送到此 endpoint 的所有 webhook requests 中。

### Transformations

Transformations 允许您修改 webhook payload，并可选择将其重定向到其他 URL。此强大功能可以：

- 在处理前修改 payload structure
- 根据内容将 webhooks 路由到不同 endpoints
- 从 payload 添加或移除 fields
- 转换 data formats

<Steps>
<Step title="Enable Transformations">
    切换 **Enabled** 开关以启用 transformation feature。
</Step>

<Step title="Configure Transformation">
    点击 **Edit transformation**，使用 JavaScript 定义 transformation rules。
</Step>

<Step title="Test Transformation">
    使用 transformation test interface 验证 transformation 在上线前是否正常工作。
</Step>
</Steps>

<Warning>
Transformations 可能会影响 webhook delivery performance。请充分测试，并保持 transformation logic 简单高效。
</Warning>

<Tip>
Transformations 特别适用于：
- 在不同 data formats 之间转换
- 根据特定 criteria 过滤 events
- 向 payload 添加计算字段
- 将 events 路由到不同 microservices
</Tip>

## 监控 Webhook Logs

**Logs** 标签页全面展示 webhook delivery status，帮助您有效监控、调试和管理 webhook events。

<Steps>
<Step title="Navigate to Logs Tab">
    进入 **Developer → Webhooks**，打开 **Logs** 标签页。
</Step>

<Step title="Browse Delivery History">
    查看所有 webhook delivery attempts 的表格，其中包含 Event type、Message ID、Event ID、Sent at、Attempted at、Response code 和 Duration 列。
</Step>

<Step title="Search and Filter">
    使用搜索栏按 ID 或 event type 查找特定 messages。按 status（Succeeded、Failed、Pending 等）筛选，以专注于需要调查的 events。
</Step>

<Step title="View Message Details">
    点击任意 message 打开 message detail page，其中显示：
    - 完整的 webhook payload
    - 每次 delivery attempt 及其 response code 和 duration
    - 每次 attempt 的 timestamp
    - endpoint 返回的任何 error messages

    每次 attempt 都带有 **Replay** 操作，因此您可以在不离开页面的情况下重新驱动该条 message。
</Step>
</Steps>

## Activity Monitoring

进入 **Developer → Webhooks**，打开 **Activity** 标签页，查看所有 endpoints 的 delivery performance。

**Delivery activity** 会按时间绘制 attempts；根据时间窗口，分组方式为 **Attempts per 5 minutes**、**Attempts per hour** 或 **Attempts per day**。每个柱状条会按 outcome 拆分，悬停在某个分段上可查看 status、attempts 数量及其占总数的比例。在 endpoint 中，**Overview** 标签页的 **Delivery stats (last 24h)** 会汇总过去一天的相同信息。

<Tip>
**Endpoints** 标签页中的 **Error rate (24h)** 列可以让您快速了解哪些 endpoints 需要关注，无需先打开它们。
</Tip>

## Replay 和恢复 Messages

重新驱动 message 的方式取决于需要处理的数量：

- **一条 message** — 从 **Logs** 标签页打开它，并在 attempt 上使用 **Replay** 操作。无需打开 endpoint。
- **一系列 messages** — 打开 endpoint，因为批量模式每次只作用于一个 endpoint。

### 批量 Replay

从 **Developer → Webhooks** 打开 endpoint。共有三种模式，每种模式仅作用于该 endpoint。您设置的范围取决于所选模式：

| Mode | What it does | What you set |
|------|--------------|--------------|
| **Recover failed messages** | Replay 此 endpoint 上所有 delivery 失败的 messages。 | 起始点：**8 hours ago**、**Yesterday**、**3 days ago**、**Last week** 或 **2 weeks ago** |
| **Replay missing messages** | Replay 从未 dispatch 到此 endpoint 的 messages，例如 endpoint 新订阅某个 event type 后的 messages。 | 相同的起始点 |
| **Bulk replay messages** | 根据所选 filters replay 匹配的 messages，包括已成功 delivery 的 messages。 | **Since** 和 **Until** 边界，默认为最近两周；还可选 event types、channel 或 tag |

<Steps>
<Step title="Open More Actions">
    在 endpoint 中打开 **More actions**，选择上述三种模式之一。
</Step>

<Step title="Set the Range">
    按照表格中的说明，填写该模式要求的范围。
</Step>

<Step title="Start the Run">
    根据所选模式，点击 **Recover** 或 **Replay**。
</Step>
</Steps>

每次运行都会显示在 endpoint 的 **Overview** 标签页中的 **Replay history** 下，其中包含模式、时间范围、status 以及重新发送的 messages 数量。

## Email Alerts

当发送到某个 endpoint 的 webhook deliveries 失败时接收 email notification，以便在问题形成积压之前及时处理。

<Steps>
<Step title="Navigate to Settings Tab">
  进入 **Developer → Webhooks**，打开 **Settings** 标签页。
</Step>

<Step title="Find Email Alerting">
  找到 **Email alerting** card。
</Step>

<Step title="Configure Email Addresses">
  输入应接收 alerts 的 addresses。多个 addresses 请用逗号分隔；留空则关闭 alerts。
</Step>

<Step title="Save">
  点击 **Save** 应用更改。
</Step>
</Steps>

<Tip>
启用 email alerts，以便及早发现 webhook delivery problems，并保持可靠的 integrations。
</Tip>
