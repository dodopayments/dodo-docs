<Info>
权限将成功付款或活跃订阅转化为实际访问权限：您的客户邮箱中的许可证密钥、您的应用检测的功能标志、Discord角色、GitHub仓库、Notion模板、Framer混编链接、Telegram聊天邀请或可下载文件包。随着付款生命周期的变化，Dodo Payments会自动发放、跟踪和撤销这些访问权限。
</Info>

## 什么是权限？

一个**权限**是您交付给客户的某种可重复使用的定义：例如Pro许可证密钥、“Patrons”Discord角色、您私人GitHub仓库的访问权限、可下载的电子书包。您可以将权限附加到产品上，Dodo Payments会负责其余的工作。

当客户购买产品时，Dodo Payments 会创建一个 **授权**，即向单个客户发放该权益。授权会经历一组有限的状态：在交付进行期间为 `Pending`，客户获得访问权限后为 `Delivered`，交付无法完成时为 `Failed`，访问权限被撤销时为 `Revoked`。

<Tip>
权限控制**履行**（客户是否有访问权限？）。信用控制**消费**（他们能使用多少？）。两者都可以附加到同一产品上。查看[基于信用的计费](/features/credit-based-billing)了解关于信用的信息。
</Tip>

## 授予的工作原理

授予由您已经收到的webhook的相同支付和订阅事件驱动。您无需自己调用授予API进行购买。Dodo Payments根据基础支付生命周期自动创建和撤销授予。

### 授予生命周期

<Steps>
<Step title="Created">
付款完成或订阅变为活跃状态时，会创建一项授予。Feature flags 会直接跳转到 `Delivered`。当权益使用 `fulfillment_mode: auto`（默认值）时，License keys 也会直接跳转到 `Delivered`；在 `fulfillment_mode: manual` 下，授予会在 `Pending` 中创建，在你通过 [Fulfill License Key Grant](/api-reference/entitlements/fulfill-license-key) 提供密钥之前不会包含密钥。其他所有集成都从 `Pending` 开始。基于 OAuth 的集成（Discord、GitHub、Notion）会提供一个 `oauth_url`，客户必须访问该地址才能完成授权；对于新创建的授予，此字段为 `null`；客户从交付邮件或 Customer Portal 开始接受流程后，该字段会被填充。平台直连集成（Telegram、Framer、Digital Files）只会在交付配置期间短暂处于 `Pending`，随后转为 `Delivered`。
</Step>

<Step title="Delivered">
交付完成后（生成 License Key、分配角色、授予存储库访问权限、解析文件链接或完成 OAuth），授权会转为 `Delivered`，并设置 `delivered_at`。
</Step>

<Step title="Failed">
如果集成调用返回不可重试的错误（OAuth token 被撤销、权限被拒绝或文件不再存在），授权会转为 `Failed`。`error_code` 和 `error_message` 字段会记录原因。
</Step>

<Step title="Revoked">
当访问权限被撤销时（订阅取消、退款发放或商户发起撤销），授权会转为 `Revoked`。`revocation_reason` 字段会记录触发原因。
</Step>
</Steps>

### 事件驱动的授予行为

| 事件 | 行为 |
|---|---|
| `payment.succeeded`（一次性付款） | 为每项附加的权益发放一项授予。 |
| `payment.succeeded`（订阅关联付款） | 不执行任何操作。授予由下方的订阅事件驱动。 |
| `subscription.active` | 为所有附加但尚未拥有授予的权益发放授予。重新发放此前因同一订阅被撤销的授予。 |
| `subscription.renewed` | 不执行任何操作。现有授予会在续订期间持续存在。 |
| `subscription.on_hold` | 撤销所有已交付和待处理的授予。`revocation_reason: subscription_on_hold`。 |
| `subscription.paused` | 撤销所有已交付和待处理的授予。`revocation_reason: SubscriptionPaused`。 |
| `subscription.unpaused` | 重新发放此前因同一订阅被撤销的授予，其行为与 `subscription.active` 完全相同。 |
| `subscription.cancelled` | 全部撤销。`revocation_reason: subscription_cancelled`。 |
| `subscription.expired` | 全部撤销。`revocation_reason: subscription_expired`。 |
| `subscription.plan_changed` | 撤销所有当前授予，然后为新方案的权益发放授予。`revocation_reason: plan_changed`。 |
| `refund.succeeded`（一次性付款） | 撤销该付款对应的授予。`revocation_reason: refund`。 |
| 手动 API 撤销 | 使用 `revocation_reason: manual` 撤销。订阅续订时不会自动重新发放手动撤销的授予。 |
| License key disabled | 对于 License key 授予，停用底层密钥会使用 `revocation_reason: license_key_disabled` 撤销该授予。重新启用密钥后，该授予会自动重新激活。 |
| 检测到平台状态偏移 | 如果集成的平台端状态不同步（例如手动移除了 Discord 角色、GitHub App 失去仓库访问权限，或协调检查发现目标缺失），系统会使用 `revocation_reason: platform_external` 撤销该授予。在底层平台问题解决之前，订阅续订时不会自动重新发放。 |

<Note>
订阅驱动的授予为每个 `(entitlement, customer, subscription)` 幂等；续订和重新激活不会创建重复的授予。一时间授予对于每个 `(entitlement, customer, payment)` 也是幂等的。
</Note>

## 创建您的第一个权限

<Steps>
<Step title="Open Entitlements">
在您的Dodo Payments仪表板中转到**权限**并单击**+**创建一个新的权限。
</Step>

<Step title="Pick an integration">
选择集成类型：License Key、Digital Files、Feature Flag、Discord、GitHub、Telegram、Figma、Framer 或 Notion。对于平台集成，如果你尚未连接账户，请先连接。
</Step>

<Step title="Configure delivery">
填写集成特定的字段。例如，GitHub要求提供仓库和权限级别；Discord要求提供服务器和可选角色；许可证密钥要求提供激活限制和到期时间。

</Step>
</Steps>

## 客户体验

### 电子邮件和客户门户

客户在购买后收到包含许可证密钥、下载链接、OAuth邀请链接或平台邀请的交付电子邮件，这取决于产品上的权限。相同的详细信息可以从[客户门户](/features/customer-portal)的订单历史中无限期获取。

### 基于OAuth的交付

Discord、GitHub 和 Notion 的订阅者访问权限要求客户授权 Dodo Payments 向其授予访问权限。在客户通过电子邮件或 Customer Portal 中的链接完成 OAuth 流程之前，这些授权会一直处于 `Pending` 状态。客户完成授权后，授权会转为 `Delivered`，并立即配置平台访问权限。

### 撤销

撤销的授予在平台级别被移除：Discord角色被移除，GitHub协作者被移除，许可证密钥被禁用。客户可以在客户门户中看到更改的反映。

<Warning>
对于数字文件，撤销会阻止继续访问预签名URL，但不会使客户已经下载的副本失效。计划内容时请相应考虑。
</Warning>

## 管理授予

从仪表板打开任何权限以查看其授予。授予详细信息面板显示总授予数、状态筛选器、客户信息、交付日期和撤销操作。

您还可以通过编程方式管理授予：

<CodeGroup>

```typescript TypeScript theme={null}
import DodoPayments from 'dodopayments';

const client = new DodoPayments({
  bearerToken: process.env['DODO_PAYMENTS_API_KEY'],
});

// List grants for an entitlement
const grants = await client.entitlements.grants.list('ent_abc123', {
  status: 'Delivered',
});

// Revoke a single grant
await client.entitlements.grants.revoke('entg_xyz789', {
  id: 'ent_abc123',
});
```

```python Python theme={null}
client.entitlements.grants.list(
    "ent_abc123",
    status="Delivered",
)

client.entitlements.grants.revoke(
    "entg_xyz789",
    id="ent_abc123",
)
```

```go Go theme={null}
grants, _ := client.Entitlements.Grants.List(
  ctx, "ent_abc123",
  dodopayments.EntitlementGrantListParams{Status: dodopayments.F("Delivered")},
)

_, _ = client.Entitlements.Grants.Revoke(ctx, "ent_abc123", "entg_xyz789")
```

</CodeGroup>

## Webhooks

Dodo Payments为授予生命周期触发四个webhook事件。订阅这些事件以使您的应用程序与每个客户可以访问的内容保持同步。

| 事件 | 触发时机 |
|---|---|
| `entitlement_grant.created` | 创建新授权时。License-key 授权在 `auto` fulfillment 下以 `Delivered` 到达，在 `manual` fulfillment 下以 `Pending` 到达；其他所有集成均以 `Pending` 到达，并在平台调用成功后转为 `Delivered`（对于基于 OAuth 的集成，则在客户完成授权后转为该状态）。 |
| `entitlement_grant.delivered` | 授权转为已交付状态时。客户现在已获得访问权限。 |
| `entitlement_grant.failed` | 授权无法交付时。检查 `error_code` 和 `error_message`。 |
| `entitlement_grant.revoked` | 访问权限已被撤销时。检查 `revocation_reason`。 |

## 最佳实践

- **每个交付渠道使用一项权益。** 不要在具有不同角色用途的多个产品之间共享同一个 Discord 权益；应为每个角色创建一项权益，以便干净地撤销。
- **先在测试模式下进行测试。** 创建权益，将其附加到测试产品，运行一次结账，并观察授予经过 `Pending → Delivered` 的状态变化。确认取消测试订阅后会撤销该授予。
- **监听 `entitlement_grant.delivered`，而不是 `payment.succeeded`。** 付款可能在履约完成前成功（尤其是 OAuth 流程）。请等待 delivered 事件，然后再在你自己的系统中解锁依赖功能。
- **将 `entitlement_grant.failed` 视为需要采取行动的事件。** 授予失败意味着客户已经付款但未获得访问权限。请将这些情况反馈给支持团队，或触发重新发放。
- **将 `revocation_reason` 映射到你的留存流程。** `subscription_on_hold` 撤销是可恢复的（客户可能会更新其银行卡）。`manual` 撤销则是有意为之。在客户沟通中应区别对待这两种情况。
