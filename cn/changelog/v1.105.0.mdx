## 新功能

### 1. **自带处理器（BYOP）**

你现在可以连接你自己的支付处理器——**Stripe**或**Adyen**——根据客户的国家/地区通过该处理器进行支付，同时Dodo Payments仍负责交易顶层的所有服务：产品、订阅、许可密钥和权限、开票、客户门户和分析。未明确路由的国家将回退到Dodo作为完整服务的商家记录（Merchant of Record）。

<Frame>
<img src="/images/byop/overview.png" alt="BYOP设置显示商家记录和自带处理器选项的功能比较" style={{ maxHeight: '500px', width: 'auto' }} />
</Frame>

在仪表板中从**设置 → BYOP**进行设置：选择一个处理器，连接你的账户，定义每个国家的路由规则，并添加你自己的发票发行人详细信息。

**BYOP路由的变化**

- **你是商家记录（Merchant of Record）。** Dodo **不**计算或收取BYOP交易的税款——你的发票发行人详细信息（企业名称、税号和地址）将替代发票和退款收据上的Dodo块。
- **争议和退款由你的处理器处理。** BYOP争议在Dodo仪表板中是只读的，因为接收/挑战在Stripe或Adyen中进行。
- 支付通过Hyperswitch路由，当前仅支持**信用卡和借记卡**。

**对于开发者**

现在支付和争议响应包含`is_byop`和`payment_provider`区分符（`stripe`、`adyen`或`dodo`），使你可以识别每笔交易的路由方式。字段是附加的——商家记录的流量仍继续报告`payment_provider: dodo`。

了解更多：[自带处理器](/features/byop) | [与Stripe的BYOP](/features/byop/stripe) | [与Adyen的BYOP](/features/byop/adyen)

### 2. **官方Rust SDK发布**

官方**Dodo Payments Rust SDK**现已作为`dodopayments`软件包在crates.io上发布。发布行与Dodo Payments API版本系列对齐，`v1.105.0`作为第一个公开API行发布，`v1.106.0`已通过最新的OpenAPI再生发布。

使用Cargo安装：

```bash
cargo add dodopayments
```

SDK需要**Rust 1.75+**并为使用Tokio和reqwest的异步Rust应用构建。它包括：

- Dodo Payments API表面上强类型的请求和响应模型。
- 用于从环境中读取的`Client::from_env()`。
- 类型化的分页帮助器，包括用于列表端点的`get_next_page()`和`into_stream()`。
- 可配置的环境和超时，包括测试模式支持。
- 用于PDF样式响应（如发票、支付发票和退款发票）的二进制响应解码。
- 符合人体工程学Rust调用站点的流畅资源链构建API。

了解更多：[Rust SDK](/developer-resources/sdks/rust) | [Crates.io](https://crates.io/crates/dodopayments) | [GitHub](https://github.com/dodopayments/dodopayments-rust)

### 3. **新支付方式：韩国钱包和Przelewy24**

现在提供四种新的本地支付方式，扩展了在韩国和波兰的覆盖范围。

**韩国（KRW）**— 在KRW结账时出现三种韩国钱包：

| 方法 | API 类型 | 订阅 |
|--------|----------|---------------|
| **Kakao Pay** | `kakao_pay` | 是 |
| **Naver Pay** | `naver_pay` | 是 |
| **PAYCO** | `payco` | 否（仅一次性） |

韩国钱包要求开票国家为`KR`和`KRW`开票——如果你的产品定价为其他货币，启用自适应货币，以便以KRW开票。

**波兰（PLN）**— **Przelewy24 (P24)**，波兰领先的在线支付方式，现在以`PLN`结算（不是欧元）并支持一次性支付。在`allowed_payment_method_types`中传递`przelewy24`。

了解更多：[韩国支付方式](/features/payment-methods/south-korea) | [欧洲支付方式](/features/payment-methods/europe) | [支付方式概览](/features/payment-methods)

### 4. **每个Webhook有效载荷上的`brand_id`**

每个webhook事件有效载荷现在都包含`brand_id`，因此你可以将支付、订阅、退款、争议、许可密钥、信用账目、权限授予、拖欠尝试和遗弃结账与特定品牌对应起来。对于没有品牌的实体，`brand_id`将回退到企业的主要品牌。

不需要集成更改——该字段是附加的，会自动出现在现有的webhook端点。

了解更多：[多个品牌](/features/multi-brands) | [Webhook事件](/developer-resources/webhooks/intents/webhook-events-guide)

### 5. **十进制货币处理**

货币处理已重做，以便金额按照每种货币的正确精度计算和显示，而不是假设所有地方都使用两位小数。**16种零小数点货币**——包括**JPY**、**KRW**、**VND**、**CLP**、**XAF**和**XOF**——现在能够在支付、发票、支付、电子邮件和分析中准确处理，并且显示（自适应货币）转换贯穿前后都精度感知。

这消除了一个类别的舍入和显示错误，为未来的额外精度打下了基础。

## 改进

### 6. **更高的产品权限和信用限额**

- 每个产品的**产品权限**从**20提到50**。
- **信用权限**（附加到产品的信用）从**3提到5**。

了解更多：[权限](/features/entitlements/introduction) | [基于信用的计费](/features/credit-based-billing)

### 7. **变更计划预览中的签名客户积分**

变更计划预览现在返回`customer_credits`作为**签名**值：**负值**表示扣减积分以抵扣费用（升级时常见），**正值**表示添加积分（从降级补偿退款或充值），清楚表明积分是正在使用还是授予。

了解更多：[订阅升级和降级](/developer-resources/subscription-upgrade-downgrade)

### 8. **`card_last_four` 和 `card_network` 在列表支付中**

**列表支付**响应现在在每笔支付中包含`card_last_four`和`card_network`，使您无需单独获取每笔支付，即可在列表中显示卡片详细信息。

了解更多：[列表支付](/api-reference/payments/get-payments)

### 9. **品牌化的ACR和催款邮件**

废弃购物车恢复（ACR）和订阅催款恢复邮件现在使用相关的**品牌的名称和徽标**，而不是业务默认，因此恢复体验与客户购买的品牌匹配。

</Frame>

了解更多：[订阅催款](/features/recovery/subscription-dunning) | [废弃购物车恢复](/features/recovery/abandoned-cart-recovery)

### 10. **改进的税号验证**

结账时的税号验证扩展了**符号检测和注册查找**（通过税号专业集成），减少了对有效ID的误拒。企业验证表单现在包括**国家选择器**以防止税号验证错误，文件上传更可靠，带有**进度指示器**和一个单一的整合错误吐司。

### 11. **分析改进**

仪表板分析现在包括更正的订阅MRR、活跃订阅数量和留存/流失计算。

<Frame>
<img src="/images/analytics/revenue-breakdown.png" alt="收入分析与总/净切换和MRR细分" style={{ maxHeight: '500px', width: 'auto' }} />
</Frame>

- **页面级分析**—新的切片展示每个结账页面的收入和折扣表现。
- 收入视图中的**总/净收入切换**和**MRR细分**。
- 图表工具提示现在显示货币和百分比单位，包括零值点。

### 12. **仪表板和店面优化**

- 产品列表中添加了**品牌过滤器**，将过滤器合并到一个按钮中，并且品牌是懒加载的。
- **产品集合、附加组件和信用表单**根据创建/编辑/复制流程进行了重新设计。
- **支付设置页面**重新设计，具有恢复失败的支付为成功的能力。
- 交易和争议表中展示了**支付提供商徽标**（Stripe / Adyen / Dodo）。
- **店面**店铺横幅文案已优化。

### 其他修复和改进

- 韩国和其他一些货币（VND、PYG、XOF、XAF）现在在结账时默认为本币。
- 平台各处的次要错误修复和稳定性改进。
