<Info>
Payment Retries는 점진적인 back-off 일정에 따라 실패한 구독 **갱신** 결제를 자동으로 다시 시도합니다. 재시도가 성공하면 고객의 조치나 integration 작업 없이 구독이 자동으로 재활성화됩니다.
</Info>

## Payment Retries란?

구독 갱신 결제가 실패하면 구독은 **보류 중** 상태가 됩니다. Payment Retries를 활성화하면 Dodo Payments 고객의 기존 결제 수단으로 스마트한 일정에 따라 자동으로 다시 청구하며, 결제가 성공하거나 복구 기간이 종료될 때까지 계속 시도합니다.

만료된 카드 보류, 충전된 잔액이 부족한 경우, 일시적인 네트워크 오류 등 일시적 실패로 인해 손실된 수익을 고객에게 이메일을 보내거나 무언가를 업데이트하도록 요청하지 않고 회수합니다.

<Note>
Payment Retries는 구독 **갱신** 결제에만 적용됩니다. 최초 결제(mandate 설정), 일회성 결제, 플랜 변경 요금 및 온디맨드 요금은 이 기능으로 재시도되지 않습니다.
</Note>

## Payment Retries 작동 방식

<Steps>
<Step title="Renewal fails">
구독 갱신 결제가 실패하고 구독이 `on_hold` 상태로 전환됩니다.
</Step>

<Step title="Retryability check">
실패의 error code를 확인합니다. **Soft decline**(잔액 부족, 일반적인 decline, 처리 또는 네트워크 오류 등)은 재시도할 수 있습니다. **Hard decline**은 재시도해도 결과가 달라지지 않으므로 retry chain이 즉시 종료됩니다.
</Step>

<Step title="Scheduled retry">
Decline이 재시도 가능하고 recovery window가 허용하는 경우 다음 시도가 예약됩니다. 재시도는 점진적인 back-off 일정에 따라 고객의 기존 결제 수단을 대상으로 off-session 방식으로 실행됩니다.
</Step>

<Step title="Recovery">
첫 번째 재시도가 성공하면 구독은 `active`로 돌아가고 다음 결제일은 정상적으로 갱신됩니다. 재시도가 한 번도 성공하지 않은 채 window가 종료되면 재시도가 중지되고 구독은 보류 중 상태로 유지됩니다.
</Step>
</Steps>

## Payment Retries 구성

대시보드의 **Settings → Recovery**에서 Payment Retries를 활성화하고 구성하세요.

<Frame caption="Payment Retries settings under Settings → Recovery">
<img src="/images/recovery/payment-retries-settings.png" alt="Enable Payment Retries 토글이 켜져 있고 Recovery window (days) 필드가 13으로 설정된 Recovery Settings 페이지" style={{ maxHeight: '500px', width: 'auto' }} />
</Frame>

| Setting | Description | Default |
|---------|-------------|---------|
| **Enable Payment Retries** | 실패한 구독 갱신 결제를 자동으로 재시도하여 수익을 회수합니다. | Off (opt-in) |
| **Recovery window (days)** | 실패한 결제를 포기하기 전까지 재시도를 계속할 기간입니다. **1~30** 사이여야 합니다. | 13 |

**recovery window**는 실패한 갱신 invoice가 생성된 시점을 기준으로 계산됩니다. 누적된 back-off 지연이 window 내에 포함되는 경우에만 재시도가 예약됩니다.

## 재시도 일정

재시도 간격은 점진적으로 늘어납니다. 각 시도가 recovery window 내에 포함되는 경우 최대 **8회 시도**가 실행됩니다:

| Attempt | Delay after previous attempt | Approx. time since failure |
|---------|------------------------------|----------------------------|
| 1 | 12시간 | 12시간 |
| 2 | 24시간 | 36시간 |
| 3 | 48시간 | ~3.5일 |
| 4 | 72시간 | ~6.5일 |
| 5 | 96시간 | ~10.5일 |
| 6 | 120시간 | ~15.5일 |
| 7 | 7일 | ~22.5일 |
| 8 | 7일 | ~29.5일 |

<Tip>
**13일**(기본값)의 recovery window는 1~5번째 시도를 포함합니다(5번째 시도는 실패 후 약 10.5일 뒤에 실행됩니다). 더 늦고 간격이 넓은 시도(6~8번째)를 실행하려면 window를 최대 30일까지 늘리세요.
</Tip>

## 구독 상태 전환

| Event | Subscription status |
|-------|---------------------|
| 갱신 결제 실패 | `active` → `on_hold` |
| 재시도 실패 | `on_hold` 상태 유지(window가 허용하면 다음 재시도 예약) |
| 재시도 성공 | `on_hold` → `active`, 다음 결제일 갱신 |
| Recovery window 소진 | `on_hold` 상태 유지 |
| 구독 취소 | 예약된 재시도가 즉시 중지됨(terminal — 추가 시도 없음) |

<Note>
재시도가 아직 예약된 상태에서 구독이 취소되면 retry chain이 즉시 종료되고 추가 시도는 실행되지 않습니다. 그 외의 비활성 상태(`on_hold`, `expired`, `pending`, `failed`)는 계속 재시도됩니다. 해당 상태의 미결제 갱신 invoice가 고객이 이미 사용한 기간에 대한 부채를 나타내기 때문입니다.
</Note>

이러한 전환은 표준 subscription webhook event를 생성하므로, 별도의 retry 처리를 구현하지 않고도 이를 기반으로 entitlement 로직을 실행할 수 있습니다:

| Event | Fires when |
|-------|-----------|
| `subscription.on_hold` | 갱신이 실패하고 구독이 보류 중 상태가 될 때 |
| `subscription.active` | 재시도가 성공하고 구독이 재활성화될 때 |

## 재시도 가능 및 재시도 불가 실패

| Failure type | Examples | Retried? |
|--------------|----------|----------|
| **Soft decline** | 잔액 부족, 일반적인 decline, 카드 사용 한도 초과, 처리 오류, 네트워크 오류/timeout, 나중에 다시 시도 | 예 |
| **Hard decline** | 도난/분실 카드, 유효하지 않은 카드, do-not-honor, 폐쇄된 계정 및 기타 terminal decline | 아니요 — chain이 즉시 종료됨 |

<Info>
Hard decline을 재시도해도 결과가 달라지지 않으므로 hard decline이 확인되는 즉시 retry chain이 종료됩니다. 이러한 경우 고객에게 결제 수단을 업데이트하도록 요청하려면 Payment Retries를 [Subscription Dunning](/features/recovery/subscription-dunning)과 함께 사용하세요.
</Info>

## Payment Retries와 Dunning 비교

Payment Retries와 [Subscription Dunning](/features/recovery/subscription-dunning)은 서로 보완적인 복구 도구입니다:

| | Payment Retries | Subscription Dunning |
|--|-----------------|----------------------|
| **Mechanism** | 기존 결제 수단으로 조용히 다시 청구 | 고객에게 결제 수단 업데이트 이메일 전송 |
| **Customer action** | 필요 없음 | 고객이 portal에서 결제 수단 업데이트 |
| **Best for** | 자체적으로 해결되는 일시적/soft decline | 교체가 필요한 만료되었거나 유효하지 않은 카드 |

두 기능을 모두 활성화하면 가장 폭넓은 복구 범위를 확보할 수 있습니다. 자동 재시도는 일시적인 실패를 처리하고, dunning은 결제 수단을 실제로 업데이트해야 하는 고객을 다시 유도합니다.
