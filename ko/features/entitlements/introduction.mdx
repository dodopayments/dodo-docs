## Entitlements란 무엇인가요?

**Entitlement**는 고객에게 제공하는 항목의 재사용 가능한 정의입니다: Pro 라이선스 키, "Patrons" Discord 역할, 프라이빗 GitHub 저장소에 대한 액세스, 다운로드 가능한 전자책 번들. Dodo Payments는 entitlements를 제품에 연결한 후 나머지를 처리합니다.

고객이 제품을 구매하면 Dodo Payments는 **grant**를 생성합니다. grant는 단일 고객에게 해당 entitlement를 발급한 것입니다. grant는 다음과 같은 몇 가지 상태를 거칩니다. 배송이 진행 중일 때는 `Pending`, 고객이 액세스 권한을 얻으면 `Delivered`, 배송을 완료할 수 없으면 `Failed`, 액세스 권한이 철회되면 `Revoked`입니다.

<Tip>
Entitlements는 **fulfillment**(고객이 액세스 가능한가?)를 통제하고, Credits는 **consumption**(얼마나 사용할 수 있는가?)을 통제합니다. 둘 다 같은 제품에 첨부할 수 있습니다. 크레딧에 대한 자세한 내용은 [Credit-Based Billing](/features/credit-based-billing)을 참조하세요.
</Tip>

## 승인 방식

승인은 이미 웹후크로 받는 동일한 결제와 구독 이벤트에 의해 구동됩니다. 구매에 대해 승인 API를 직접 호출할 필요가 없습니다. Dodo Payments는 기본 결제 생명주기에 따라 자동으로 승인과 취소를 생성합니다.

### 승인 생명주기

<Steps>
<Step title="Created">
결제 완료 또는 subscription 활성화 시 grant가 생성됩니다. Feature flags는 `Delivered`로 바로 이동합니다. entitlement가 `fulfillment_mode: auto`(기본값)를 사용하는 경우 License keys도 `Delivered`로 바로 이동합니다. `fulfillment_mode: manual`에서는 grant가 `Pending`에서 생성되며, [Fulfill License Key Grant](/api-reference/entitlements/fulfill-license-key)를 통해 키를 제공할 때까지 키가 없습니다. 다른 모든 integration은 `Pending`에서 시작합니다. OAuth 기반 integration(Discord, GitHub, Notion)은 customer가 방문하여 동의를 완료해야 하는 `oauth_url`를 노출합니다. 새로 생성된 grant에서는 이 필드가 `null`이며, customer가 delivery email 또는 customer portal에서 accept flow를 시작하면 값이 채워집니다. Platform-direct integration(Telegram, Framer, Digital Files)은 delivery가 provision되는 짧은 동안만 `Pending`에 머문 후 `Delivered`로 전환됩니다.
</Step>

<Step title="Delivered">
Delivery가 완료되면(license key가 생성되고, role이 할당되고, repository access가 부여되고, file link가 확인되고, OAuth가 완료되면) grant는 `Delivered`로 전환되고 `delivered_at`가 설정됩니다.
</Step>

<Step title="Failed">
integration 호출에서 재시도할 수 없는 오류가 반환되면(철회된 OAuth token, 거부된 permission, 더 이상 존재하지 않는 file) grant는 `Failed`로 전환됩니다. `error_code` 및 `error_message` 필드에 그 이유가 기록됩니다.
</Step>

<Step title="Revoked">
액세스 권한이 철회되면(subscription이 취소되거나, refund가 발행되거나, merchant가 철회를 시작한 경우) grant는 `Revoked`로 전환됩니다. `revocation_reason` 필드에 해당 트리거가 기록됩니다.
</Step>
</Steps>

### 이벤트별 승인 동작

| Event | Behavior |
|---|---|
| `payment.succeeded` (one-time payment) | 연결된 각 entitlement에 대해 grant 하나를 발급합니다. |
| `payment.succeeded` (subscription-linked payment) | No-op입니다. grant는 아래 subscription event에 의해 관리됩니다. |
| `subscription.active` | 연결된 entitlement 중 아직 grant가 없는 항목에 대해 grant를 발급합니다. 동일한 subscription에 대해 이전에 revoke된 grant는 다시 발급합니다. |
| `subscription.renewed` | No-op입니다. 기존 grant는 renewal 동안 유지됩니다. |
| `subscription.on_hold` | delivered 및 pending 상태의 모든 grant를 revoke합니다. `revocation_reason: subscription_on_hold`. |
| `subscription.paused` | delivered 및 pending 상태의 모든 grant를 revoke합니다. `revocation_reason: SubscriptionPaused`. |
| `subscription.unpaused` | `subscription.active`와 동일하게, 동일한 subscription에 대해 이전에 revoke된 grant를 다시 발급합니다. |
| `subscription.cancelled` | 모두 revoke합니다. `revocation_reason: subscription_cancelled`. |
| `subscription.expired` | 모두 revoke합니다. `revocation_reason: subscription_expired`. |
| `subscription.plan_changed` | 현재 grant를 모두 revoke한 후 새 plan의 entitlement에 대한 grant를 발급합니다. `revocation_reason: plan_changed`. |
| `refund.succeeded` (one-time payment) | 해당 payment의 grant를 revoke합니다. `revocation_reason: refund`. |
| Manual API revoke | `revocation_reason: manual`를 사용하여 revoke합니다. Manual revoke는 subscription renewal 시 자동으로 다시 발급되지 않습니다. |
| License key disabled | License-key grant의 경우, 기반 key를 비활성화하면 `revocation_reason: license_key_disabled`와 함께 grant가 revoke됩니다. key를 다시 활성화하면 grant는 자동으로 재활성화됩니다. |
| Platform drift detected | integration의 platform 측 상태가 동기화 상태에서 벗어나면(Discord role이 수동으로 제거되거나, GitHub App이 repository access를 잃거나, reconciliation pass에서 target 누락을 감지하는 경우) `revocation_reason: platform_external`와 함께 grant가 revoke됩니다. 기반 platform 문제가 해결될 때까지 subscription renewal 시 자동으로 다시 발급되지 않습니다. |

<Note>
구독 기반 승인은 `(entitlement, customer, subscription)`마다 비절개적입니다; 갱신 및 재활성화로 인해 중복 승인이 생성되지 않습니다. 일회성 승인은 `(entitlement, customer, payment)`마다 비절개적입니다.
</Note>

## 고객 경험

### 이메일 및 고객 포털

고객은 구매 후 제품의 자격에 적용되는 라이선스 키, 다운로드 링크, OAuth 초대 링크 또는 플랫폼 초대가 포함된 전달 이메일을 받습니다. 동일한 세부 정보는 주문 기록 하의 [고객 포털](/features/customer-portal)에서 무기한으로 제공됩니다.

### OAuth 기반 전달

Discord, GitHub, Notion subscriber access를 사용하려면 고객이 Dodo Payments에 액세스 권한 부여를 승인해야 합니다. 이러한 grant는 고객이 email 또는 customer portal의 링크를 사용해 OAuth flow를 완료할 때까지 `Pending` 상태로 유지됩니다. 고객이 승인하면 grant는 `Delivered`로 전환되고 platform access가 즉시 provision됩니다.

### 취소

취소된 승인은 플랫폼 수준에서 제거됩니다: Discord 역할이 제거되고, GitHub 협력자가 제거되고, 라이선스 키가 비활성화됩니다. 고객은 고객 포털에서 변경 사항을 확인할 수 있습니다.

<Warning>
디지털 파일의 경우, 취소는 서명된 URL에 대한 접근을 앞으로 제거하지만 고객이 이미 다운로드한 복사본을 무효화하지는 않습니다. 따라서 계획 내용을 적절히 제한하세요.
</Warning>

## 승인 관리

대시보드에서 자격을 열면 해당 승인들을 볼 수 있습니다. 승인 세부 정보 패널에는 총 승인 수, 상태 필터, 고객 정보, 전달 날짜, 및 취소 조치가 표시됩니다.

승인을 프로그래밍 방식으로 관리할 수 있습니다:

<CodeGroup>

```typescript TypeScript theme={null}
import DodoPayments from 'dodopayments';

const client = new DodoPayments({
  bearerToken: process.env['DODO_PAYMENTS_API_KEY'],
});

// List grants for an entitlement
const grants = await client.entitlements.grants.list('ent_abc123', {
  status: 'Delivered',
});

// Revoke a single grant
await client.entitlements.grants.revoke('entg_xyz789', {
  id: 'ent_abc123',
});
```

```python Python theme={null}
client.entitlements.grants.list(
    "ent_abc123",
    status="Delivered",
)

client.entitlements.grants.revoke(
    "entg_xyz789",
    id="ent_abc123",
)
```

```go Go theme={null}
grants, _ := client.Entitlements.Grants.List(
  ctx, "ent_abc123",
  dodopayments.EntitlementGrantListParams{Status: dodopayments.F("Delivered")},
)

_, _ = client.Entitlements.Grants.Revoke(ctx, "ent_abc123", "entg_xyz789")
```

</CodeGroup>

## 웹후크

Dodo Payments는 승인 생명주기에 대해 네 개의 웹후크 이벤트를 발생시킵니다. 이 이벤트에 가입하여 각 고객이 접근할 수 있는 내용을 애플리케이션과 동기화하세요.

| Event | 실행 시점 |
|---|---|
| `entitlement_grant.created` | 새 grant가 생성될 때 실행됩니다. License-key grant는 `auto` fulfillment에서 `Delivered`로 도착하고, `manual` fulfillment에서는 `Pending`로 도착합니다. 그 외 모든 integration은 `Pending`로 도착하며, platform 호출이 성공하면(또는 OAuth 기반 integration의 경우 고객이 승인하면) `Delivered`로 전환됩니다. |
| `entitlement_grant.delivered` | grant가 delivered로 전환될 때 실행됩니다. 이제 고객이 액세스할 수 있습니다. |
| `entitlement_grant.failed` | grant를 delivered할 수 없을 때 실행됩니다. `error_code` 및 `error_message`를 확인하세요. |
| `entitlement_grant.revoked` | 액세스 권한이 철회될 때 실행됩니다. `revocation_reason`를 확인하세요. |

전체 페이로드 스키마, 샘플 이벤트 및 `revocation_reason` 참조를 보세요.

## 모범 사례

- **각 delivery channel마다 entitlement 하나를 사용하세요.** 서로 다른 role 의도를 가진 product 간에 하나의 Discord entitlement를 공유하지 마세요. 깔끔한 revoke를 위해 role마다 하나씩 생성하세요.
- **먼저 test mode에서 테스트하세요.** entitlement를 생성하고, test product에 연결한 다음 checkout을 실행하여 grant가 `Pending → Delivered`를 거쳐 전환되는 과정을 확인하세요. test subscription을 취소하면 grant가 revoke되는지 확인하세요.
- **`entitlement_grant.delivered`를 수신하고 `payment.succeeded`는 수신하지 마세요.** 특히 OAuth flow에서는 fulfilment가 완료되기 전에 payment가 성공할 수 있습니다. 자체 시스템에서 종속 기능을 unlock하기 전에 delivered event를 기다리세요.
