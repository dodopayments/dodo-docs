Dodo Paymentsは、世界中の顧客にサービスを提供するために、幅広い支払い方法をサポートしています。すべてのリストされた支払い方法は、マーチャントアカウントが確認され、ライブモードが有効になると自動的に利用可能になります。

<Info>
**自動アクティベーション:** あなたの側で追加の設定は必要ありません。すべての支払い方法はDodo Paymentsによって事前に設定され、管理されています。オプションで、以下に説明するAPI設定を使用して、チェックアウト時に表示される方法を制限することができます。
</Info>

<Accordion title="UPIおよびRupay（インド）" id="upi-and-rupay-india">
  インドの主要な支払いオプションを受け入れます：

  - **UPI** – 顧客はQRコードをスキャンするか、アプリ（Google Pay、PhonePe、Paytm、CRED）を使用して即時の非接触型銀行振込を行います
  - **Rupayカード** – インドの国内カードネットワークを介した安全なクレジットおよびデビット支払い

  ### RBI準拠の命令によるサブスクリプション

  UPIおよびインドのカードのサブスクリプションは、特定の命令要件に従ってRBI（インド準備銀行）の規制の下で運営されます：

  #### 命令の制限

  命令の種類と金額は、サブスクリプションの定期的な料金に依存します：

  - **₹15,000未満の料金:** ₹15,000 INRのオンデマンド命令を作成します。サブスクリプション金額は、サブスクリプションの頻度に応じて定期的に請求され、命令の制限まで請求されます。
  - **₹15,000以上の料金:** 正確なサブスクリプション金額のためにサブスクリプション命令（またはオンデマンド命令）を作成します。

  #### アップグレードおよびダウングレードの考慮事項

  <Warning>
  **重要:** サブスクリプションのアップグレードまたはダウングレード時には、命令の制限を慎重に考慮してください：

  - アップグレード/ダウングレードにより、料金金額が₹15,000を超え、既存のオンデマンド支払い制限を超える場合、取引料金が失敗する可能性があります。
  - その場合、顧客は支払い方法を更新する必要があるか、正しい制限で新しい命令を確立するためにサブスクリプションを再度変更する必要があります。
  </Warning>

  #### 高額料金の承認

  ₹15,000以上のサブスクリプション料金について：

  - 顧客は、取引を承認するように銀行から促されます。
  - 顧客が取引を承認しない場合、取引は失敗し、サブスクリプションは保留されます。

  #### 48時間の処理遅延

  <Info>
  **処理タイムライン:** インドのカードおよびUPIサブスクリプションの定期的な料金は、独自の処理パターンに従います：

  - 料金は、サブスクリプションの頻度に応じて予定された日に**開始**されます。
  - 顧客の口座からの実際の**控除**は、支払い開始から**48時間**後にのみ行われます。
  - この48時間のウィンドウは、銀行APIの応答に応じて最大**2-3時間**延長される場合があります。
  </Info>

  #### 命令のキャンセルウィンドウ

  48時間の処理ウィンドウ中：

  - 顧客は銀行アプリを介して命令をキャンセルできます。
  - 顧客がこの期間中に命令をキャンセルした場合、サブスクリプションは**アクティブ**のままになります（これはインドのカードおよびUPI自動支払いサブスクリプションに特有のエッジケースです）。
  - ただし、実際の控除が失敗する可能性があり、その場合、サブスクリプションは**保留**されます。

  <Warning>
  **エッジケースの処理:** 料金開始時に顧客に特典、クレジット、またはサブスクリプションの使用を提供する場合、この48時間のウィンドウを適切にアプリケーションで処理する必要があります。考慮すべき点：

  - 支払い確認まで特典のアクティベーションを遅らせる
  - グレース期間または一時的なアクセスを実装する
  - 命令キャンセルのためのサブスクリプションのステータスを監視する
  - アプリケーションロジックでサブスクリプションの保留状態を処理する
  </Warning>

  <Tip>
  支払い状況の変更を追跡し、48時間のウィンドウ中に命令がキャンセルされた場合のエッジケースを処理するために、サブスクリプションのWebhookを監視してください。
  </Tip>

</Accordion>

## 支払い方法の設定

すべての支払い方法は、顧客の場所と通貨に基づいて自動的に利用可能ですが、`allowed_payment_method_types`パラメータを使用して、チェックアウト時に表示される支払いオプションを制限することができます。

### 支払い方法を設定するタイミング

許可された支払い方法を設定する理由は次のとおりです：

- ビジネス要件に基づいて顧客に表示される支払いオプションを制御する
- 特定の製品タイプや取引フローに対して支払い方法を制限する
- 異なる支払い体験全体で一貫性を維持する
- ターゲットオーディエンスのためにチェックアウト体験を最適化する

### 実装

<Steps>
<Step title="APIリクエストにパラメータを追加">
支払いまたはサブスクリプション作成リクエストに`allowed_payment_method_types`フィールドを含めます：

```json
{
  "allowed_payment_method_types": [
    "credit",
    "debit",
    "apple_pay"
  ]
}
```

</Step>

<Step title="設定をテスト">
指定された支払い方法のみがチェックアウト時に表示されることを確認します。

<Tip>
異なる顧客の場所や通貨で支払い方法の可用性をテストして、設定が期待通りに機能することを確認してください。
</Tip>
</Step>
</Steps>

### ベストプラクティス

<AccordionGroup>
<Accordion title="デフォルトの動作">
`allowed_payment_method_types`が指定されていない場合、すべての適格な支払い方法は、顧客の場所、通貨、および取引タイプに基づいて利用可能になります。このパラメータは、支払い方法を制限する必要がある場合にのみ使用してください。
</Accordion>

<Accordion title="地域の考慮事項">
支払い方法を選択する際には、ターゲット市場を考慮してください。地域特有のオプション（インドのUPIやオランダのiDEALなど）を含めることで、これらの市場でのコンバージョン率を大幅に向上させることができます。
</Accordion>

<Accordion title="監視と最適化">
顧客が最も頻繁に使用する支払い方法を追跡し、実際の使用パターンやコンバージョンデータに基づいて許可された方法を調整します。
</Accordion>
</AccordionGroup>

### 重要な考慮事項

支払い方法の可用性は、複数の要因に依存します：
- **顧客の場所**: 一部の支払い方法は地域特有です
- **マーチャント設定**: アカウントの設定と機能
- **通貨**: サポートされる支払い方法は通貨によって異なります
- **取引タイプ**: 一部の方法はサブスクリプションをサポートしていないか、最小金額があります

<Note>
`allowed_payment_method_types`に支払い方法を追加しても、それが表示されることは保証されません - これらの要因に基づいても適格である必要があります。
</Note>

## トラブルシューティング

<AccordionGroup>
<Accordion title="チェックアウトに支払い方法が表示されない">
**考えられる原因:**
- 支払い方法が`allowed_payment_method_types`に含まれていない
- 支払い方法が顧客の場所に対してサポートされていない
- 支払い方法が取引通貨をサポートしていない
- サブスクリプションの場合: 支払い方法が定期的な支払いをサポートしていない
- 取引金額が最小閾値（例：BNPL方法）を下回っている

**解決策:** すべての適格要件が満たされていることを確認し、APIリクエストの設定を確認してください。
</Accordion>

<Accordion title="予期しない支払い方法が表示される">
**考えられる原因:**
- `allowed_payment_method_types`パラメータが正しく渡されていない
- マーチャントダッシュボードに競合する設定がある可能性があります

**解決策:** APIリクエストのペイロードを確認し、パラメータが文字列の配列として正しくフォーマットされていることを確認してください。
</Accordion>

<Accordion title="地域の支払い方法が利用できない">
**考えられる原因:**
- 顧客の場所が支払い方法のサポート地域と一致しない
- 通貨が地域の支払い方法によってサポートされていない
- マーチャントアカウントがその特定の支払い方法に対して有効になっていない可能性があります

**解決策:** 地域および通貨の互換性を確認し、その方法が利用可能であるべきだと考える場合はサポートに連絡してください。
</Accordion>

<Accordion title="インドの支払い方法のサブスクリプションの問題">
**アップグレード/ダウングレード後にサブスクリプション料金が失敗した:**
- 新しい料金金額が既存の命令制限（₹15,000の閾値）を超えている可能性があります
- 顧客は新しい命令を確立するために支払い方法を更新する必要があるかもしれません

**解決策:** 顧客に支払い方法を更新するように促すか、命令制限内に収まるようにサブスクリプション金額を調整してください。

**料金開始後にサブスクリプションが保留される:**
- 顧客が48時間の処理ウィンドウ中に命令をキャンセルした可能性があります
- 顧客が高額料金（≥₹15,000）を承認しなかった可能性があります

**解決策:** 命令キャンセルや支払い失敗のWebhookイベントを監視します。リトライロジックを実装するか、顧客に支払い方法を再確立するように促します。

**支払い控除が遅延している:**
- 通常の動作: インドのカードおよびUPIサブスクリプションは、料金開始と実際の控除の間に48時間の遅延があります
- この遅延は、銀行APIに応じて最大2-3時間延長される場合があります

**解決策:** これは予期される動作です。支払い確認がWebhookを介して受信されるまで、特典やクレジットをアクティブにしないでください。
</Accordion>

<Accordion title="サブスクリプションの支払い方法を更新する">
**支払い方法を更新するタイミング:**
- 顧客のカードが期限切れまたは交換された
- 顧客が別の支払い方法を使用したい
- サブスクリプションが失敗した支払いのために`on_hold`状態にある
- 何らかの理由で支払い方法を変更する必要がある

**アクティブなサブスクリプションの場合:**
アクティブなサブスクリプションの支払い方法を更新すると、将来の更新のために支払い方法が単に更新されます。即時の料金は作成されません。

**保留中のサブスクリプションの場合:**
サブスクリプションが`on_hold`状態にある場合（更新の失敗やプラン変更料金の失敗による）、支払い方法を更新すると：
- 残りの未払い金のために自動的に料金が作成されます
- 料金の請求書が生成されます
- 新しい支払い方法を使用して支払いが処理されます
- 支払いが成功した場合、サブスクリプションが`active`状態に再アクティブ化されます

<CodeGroup>

```javascript Node.js
  return_url: 'https://example.com/return'

await client.subscriptions.updatePaymentMethod('sub_123', {
  type: 'existing',
  payment_method_id: 'pm_abc123'
});

// For on_hold subscription - automatically creates charge
const response = await client.subscriptions.updatePaymentMethod('sub_123', {
  type: 'new',
  return_url: 'https://example.com/return'
});

if (response.payment_id) {
  // Charge created for remaining dues
  // Redirect customer to response.payment_link
  // Monitor webhooks: payment.succeeded → subscription.active
}
```
