Webhooksは、Dodo Paymentsアカウントで特定のイベントが発生した際に、リアルタイム通知を提供します。Webhooksを使用してワークフローの自動化、データベースの更新、通知の送信、システムの同期を行えます。

<Info>
当社のWebhook実装は[Standard Webhooks](https://standardwebhooks.com/)仕様に準拠しており、業界のベストプラクティスおよび既存のWebhookライブラリとの互換性を確保しています。
</Info>

## はじめに

<Info>
Dodo Payments の webhooks portal は、ネイティブなダッシュボードエクスペリエンスとして再構築されました。既存のエンドポイント、署名シークレット、signature verification、イベント名、webhook payload は変更されていません。統合作業は必要ありません。
</Info>

<Note>
**各機能の場所**

- **Developer → Webhooks の下** — **Endpoints**、**Event catalog**、**Logs**、**Activity**、**Settings** タブ。
- **個別のエンドポイント上** — 配信統計、署名シークレット、**Replay history** を含む **Overview** タブ、さらに **Testing**、**Advanced** タブと一括 replay アクション。
- **メッセージ上** — **Logs** タブから開くと、エンドポイントを開かずに各配信試行を個別に replay できます。
</Note>

<Steps>
<Step title="Access Webhook Settings">
    Dodo Payments Dashboard に移動し、**Developer → Webhooks** を開きます。
</Step>

<Step title="Create Webhook Endpoint">
    **Add endpoint** をクリックして、エンドポイント作成用のサイドシートを開きます。
</Step>

<Step title="Enter Endpoint URL or Choose Integration">
    webhook event を受信する URL を入力するか、integration connector を選択して、イベントをサードパーティサービス（Slack、Discord、Zapier、Resend など）へルーティングします。
</Step>

<Step title="Select Events to Receive">
    エンドポイントが listen する特定のイベントを選択します。イベントは、リソースごとにグループ化された検索可能なツリーに整理されています。個別のイベントを選択することも、親リソースを選択して関連するすべてのイベントを受信することもできます。
    
    <Tip>
    選択したイベントだけがエンドポイントへの webhooks をトリガーするため、不要なトラフィックや処理を避けられます。
    </Tip>
</Step>

<Step title="Create Endpoint">
    **Create endpoint** をクリックして設定を保存します。
</Step>

<Step title="Get Secret Key">
    webhook signing secret は、エンドポイントの **Overview** タブに表示されます。受信した webhooks の真正性を検証するために使用します。
    
    <Warning>
    webhook secret key は安全に管理し、クライアント側のコードや公開リポジトリに決して公開しないでください。
    </Warning>
</Step>

<Step title="Rotate Secret (Optional)">
    必要に応じて、セキュリティを強化するために webhook secret をローテーションできます。**Overview** タブで secret の横にある **Rotate secret** をクリックします。
    
    <Warning>
    secret をローテーションすると、現在の secret は失効し、新しい secret に置き換えられます。古い secret はその後 24 時間のみ有効です。それ以降、古い secret で検証しようとすると失敗します。
    </Warning>
    
    <Info>
    定期的に、または現在の secret が漏えいした疑いがある場合は直ちに secret rotation を実行してください。
    </Info>
</Step>
</Steps>

## Integration Connectors

独自の webhook receiver を構築する代わりに、integration connector を使用して webhook event をサードパーティサービスへ直接ルーティングできます。これにより、一般的なプラットフォーム向けにカスタム webhook handler を記述・保守する必要がなくなります。

### Connector の仕組み

connector は、Dodo Payments event を送信先が想定する形式に変換する処理を実行します。入力する詳細は送信先によって異なります。

| Connector type | What you provide | Destinations |
|----------------|------------------|--------------|
| **Incoming webhook URL** | ベンダー独自のダッシュボードで作成した webhook URL。API key は不要です。 | [Slack](/integrations/slack)、[Discord](/integrations/discord)、[Microsoft Teams](/integrations/microsoft-teams)、[Zapier](/integrations/zapier)、[Windmill](/integrations/windmill) |
| **Vendor API** | API key。送信先 URL は connector template から取得されます。 | [Resend](/integrations/resend)、[SendGrid](/integrations/sendgrid)、[Segment](/integrations/segment)、[Customer.io](/integrations/customer-io)、[HubSpot](/integrations/hubspot)、[Close CRM](/integrations/close-crm)、[Loops](/integrations/loops) |

ダッシュボードの connector picker には、現在ビジネスで利用できるすべての connector が表示されます。そのため、上の表は網羅的な一覧ではなく、手順付きのセットアップ説明がある送信先として扱ってください。各送信先で event を受信した後にできることについては、[External Integrations](/integrations/introduction) を参照してください。

### Connector の設定

エンドポイントの作成または編集時に connector を選択すると、サイドシートに送信先に合わせたセットアップ手順が表示されます。たとえば、Slack で incoming webhook URL を作成する方法や、Resend API key の確認場所などです。保存する前に connector transformation test を実行し、event が送信先向けに正しく変換されることを確認してください。

<Tip>
コードを書かずにサポート対象の送信先へ接続するには connector を使用します。カスタムロジックが必要な場合は、代わりに [transformation](#transformations) を使用した標準エンドポイントを使ってください。
</Tip>

## Subscribed Events の設定

各 webhook endpoint が受信する特定のイベントを設定できます。

<Steps>
<Step title="Navigate to Webhook Endpoints">
    Dodo Payments Dashboard に移動し、**Developer → Webhooks** を開きます。
</Step>

<Step title="Select Your Endpoint">
    設定する webhook endpoint をクリックします。
</Step>

<Step title="Open Event Configuration">
    **Edit** をクリックして、エンドポイント設定用のサイドシートを開きます。
</Step>

<Step title="Browse Event Types">
    イベントタイプセレクターには、利用可能なすべての webhook event がリソースごとにグループ化された検索可能なツリーで表示されます（例: `payment`、`subscription`、`dispute`）。検索バーを使用すると、名前やキーワードから特定のイベントをすばやく見つけられます。
</Step>

<Step title="Select Events">
    受信するイベントの横にあるチェックボックスをオンにします。次の操作ができます。
    - 個別のイベントを選択する（例: `payment.succeeded`、`payment.failed`）
    - 親リソースを選択して関連するすべてのイベントを受信する
    - 必要に応じて特定のイベントを組み合わせる
</Step>

<Step title="Save Configuration">
    **Save** をクリックして変更を適用するか、**Cancel** をクリックして変更を破棄します。
</Step>
</Steps>

<Warning>
すべてのイベントの選択を解除すると、webhook endpoint は通知を一切受信しなくなります。アプリケーションの正常な動作に必要なイベントを少なくとも選択してください。
</Warning>

## Webhook Delivery

### タイムアウト

webhooks には、接続操作と読み取り操作の両方に **15 秒のタイムアウトウィンドウ** があります。タイムアウトを避けるため、エンドポイントがすぐに応答するようにしてください。

<Tip>
webhooks は非同期で処理し、まず `200` status code を直ちに返して受信を確認した後、実際の処理をバックグラウンドで行ってください。
</Tip>

### 自動リトライ

webhook delivery が失敗すると、Dodo Payments は指数バックオフで自動的にリトライし、システムに過剰な負荷がかからないようにします。

| Attempt | Delay | Description |
|---------|------------------------------|-------------|
| 1 | Immediately | 最初のリトライは直ちに実行されます |
| 2 | 5 seconds | 短い遅延の後に 2 回目の試行を実行します |
| 3 | 5 minutes | バックオフを増加させて 3 回目の試行を実行します |
| 4 | 30 minutes | バックオフを継続して 4 回目の試行を実行します |
| 5 | 2 hours | より長い遅延の後に 5 回目の試行を実行します |
| 6 | 5 hours | さらに長い遅延の後に 6 回目の試行を実行します |
| 7 | 10 hours | 最大遅延で 7 回目の試行を実行します |
| 8 | 10 hours | **最後の試行** - 失敗した場合、webhook は失敗としてマークされます |

<Info>
webhook event ごとのリトライは **最大 8 回** です。たとえば、webhook が成功するまでに 3 回失敗した場合、最初の試行からの合計配信時間は約 35 分 5 秒です。
</Info>

<Tip>
Dodo Payments dashboard を使用すると、個別のメッセージを手動でリトライしたり、失敗したすべてのメッセージを一括でいつでも復旧したりできます。
</Tip>

### Idempotency

各 webhook event には一意の `webhook-id` header が含まれます。この識別子を使用して idempotency を実装し、重複処理を防止してください。

```javascript
// Example: Storing webhook IDs to prevent duplicate processing
const processedWebhooks = new Set();

app.post('/webhook', (req, res) => {
  const webhookId = req.headers['webhook-id'];
  
  if (processedWebhooks.has(webhookId)) {
    return res.status(200).json({ received: true });
  }
  
  processedWebhooks.add(webhookId);
  // Process the webhook...
});
```

<Warning>
必ず idempotency checks を実装してください。リトライにより、同じ event を複数回受信する可能性があります。
</Warning>

### イベント順序

リトライやネットワーク状況により、webhook event が順不同で届く場合があります。どの順序のイベントにも対応できるようにシステムを設計してください。

<Info>
webhook event が最初に発生した時点に関係なく、**配信時点での最新の payload** を受信します。
</Info>

## Webhooks のセキュリティ保護

webhooks のセキュリティを確保するため、常に payload を検証し、HTTPS を使用してください。

### 署名の検証

各 webhook request には `webhook-signature` header が含まれます。これは webhook payload と timestamp の HMAC SHA256 signature で、secret key によって署名されています。

#### SDK verification（推奨）

すべての公式 SDK には、受信した webhooks を安全に検証・解析するための built-in helper が含まれています。利用できる方法は 2 つです。

* `unwrap()`: webhook secret key を使用して signature を検証します
* `unsafe_unwrap()`: verification なしで payload を解析します

<Tip>
  Dodo Payments client の初期化時に、`DODO_PAYMENTS_WEBHOOK_KEY` を使用して webhook secret を指定します。
</Tip>

<CodeGroup>

```typescript TypeScript/Node.js
import DodoPayments from 'dodopayments';
import express from 'express';

const app = express();
app.use(express.raw({ type: 'application/json' }));

const client = new DodoPayments({
  bearerToken: process.env.DODO_PAYMENTS_API_KEY,
  environment: process.env.DODO_PAYMENTS_ENVIRONMENT,
  webhookKey: process.env.DODO_PAYMENTS_WEBHOOK_KEY,
});

app.post('/webhook', async (req, res) => {
  try {
    const unwrapped = client.webhooks.unwrap(req.body.toString(), {
      headers: {
        'webhook-id': req.headers['webhook-id'] as string,
        'webhook-signature': req.headers['webhook-signature'] as string,
        'webhook-timestamp': req.headers['webhook-timestamp'] as string,
      },
    });
    res.json({ received: true });
  } catch (error) {
    res.status(401).json({ error: 'Invalid signature' });
  }
});
```

```python Python
from fastapi import FastAPI, Request, HTTPException
from dodopayments import DodoPayments
import os

app = FastAPI()
client = DodoPayments(
    bearer_token=os.getenv("DODO_PAYMENTS_API_KEY"),
    environment=os.getenv("DODO_PAYMENTS_ENVIRONMENT"),
    webhook_key=os.getenv("DODO_PAYMENTS_WEBHOOK_KEY"),
)

@app.post("/webhook")
async def handle_webhook(request: Request):
    try:
        unwrapped = client.webhooks.unwrap(
            await request.body(),
            headers={
                "webhook-id": request.headers.get("webhook-id", ""),
                "webhook-signature": request.headers.get("webhook-signature", ""),
                "webhook-timestamp": request.headers.get("webhook-timestamp", ""),
            },
        )
        return {"received": True}
    except Exception:
        raise HTTPException(status_code=401, detail="Invalid signature")
```

```go Go
import (
	"context"
	"io"
	"net/http"
	"os"
	"github.com/dodopayments/dodopayments-go"
	"github.com/dodopayments/dodopayments-go/option"
)

func webhookHandler(w http.ResponseWriter, r *http.Request) {
	client := dodopayments.NewClient(
		option.WithBearerToken(os.Getenv("DODO_PAYMENTS_API_KEY")),
		option.WithEnvironment(os.Getenv("DODO_PAYMENTS_ENVIRONMENT")),
		option.WithWebhookKey(os.Getenv("DODO_PAYMENTS_WEBHOOK_KEY")),
	)
	rawBody, _ := io.ReadAll(r.Body)
	if _, err := client.Webhooks.Unwrap(context.Background(), rawBody, map[string]string{
		"webhook-id":       r.Header.Get("webhook-id"),
		"webhook-signature": r.Header.Get("webhook-signature"),
		"webhook-timestamp": r.Header.Get("webhook-timestamp"),
	}); err != nil {
		http.Error(w, "Invalid signature", http.StatusUnauthorized)
		return
	}
	w.WriteHeader(http.StatusOK)
}
```

</CodeGroup>

#### Manual verification（代替方法）

SDK を使用していない場合は、Standard Webhooks spec に従って自分で signature を検証できます。

1. `webhook-id`、`webhook-timestamp`、正確な raw stringified `payload` をピリオド（`.`）で区切って連結し、署名対象メッセージを作成します。
2. Dashboard の webhook secret key を使用して、その文字列の HMAC SHA256 を計算します。
3. 計算した signature と `webhook-signature` header を比較します。一致すれば webhook は authentic です。

<Info>
  Standard Webhooks specification に従っています。signature の検証には、[https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries](https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries) の libraries を使用できます。event payload formats については、[Webhook Payload](/developer-resources/webhooks/intents/payment) を参照してください。
</Info>

### ソース IP アドレス

Webhook を認証するために推奨されている方法は、署名検証です。これにより、リクエストが webhook secret を使って署名されたことを証明できますが、ネットワークレベルのチェックではそれを確認できません。

Webhook の配信は、当社の配信インフラストラクチャに属するソース IP アドレスのプールから送信されます。このプールは随時変更されるため、アドレスは統合の固定された特性ではなく、運用上の詳細として扱ってください。

<Warning>
認証メカニズムとしてソース IP allowlist を使用しないでください。allowlist で確認できるのはリクエストの送信元だけであり、それが正規のものか、変更されていないかは確認できません。[Verifying Signatures](#verifying-signatures) の説明に従い、すべてのリクエストで `webhook-signature` header を検証してください。
</Warning>

ファイアウォールの背後にインフラストラクチャがあり、明示的な allowlist が必要な場合は、次の点に注意してください。

- **アドレスを恒久的にハードコードしないでください。** 範囲は時間の経過とともに追加・廃止されるため、古いルールによって配信が気付かないうちにブロックされます。
- ファイアウォールを制限する前に、[support@dodopayments.com](mailto:support@dodopayments.com) から**現在の範囲をリクエスト**してください。最新のリストに基づいて作業できます。
- **変更通知を確認してください。** 配信アドレスが変更される場合、影響を受ける Merchant にはメールで通知します。配信の欠落を避けるため、指定された日付までに更新を適用してください。
- 追加するネットワークルールにかかわらず、**署名検証を有効にしておいてください**。

<Tip>
Serverless および managed hosting platform では、受信 IP フィルタリングを利用できないか、維持することが現実的でない場合がよくあります。これらの環境で適切な制御となるのは署名検証であり、allowlist は必要ありません。
</Tip>

<Info>
ブロックされた配信は、その他の失敗と同様に扱われ、[Automatic Retries](#automatic-retries) に記載されたスケジュールで再試行されます。ファイアウォールルールが原因で配信に失敗した場合は、ルールを修正した後で再送信できます。詳しくは [Replaying and Recovering Messages](#replaying-and-recovering-messages) を参照してください。
</Info>

### Webhook への応答

* webhook handler は、イベントを受信したことを確認するために `2xx status code` を返す必要があります。
* その他のレスポンスは失敗として扱われ、webhook は再試行されます。

### ベストプラクティス

<AccordionGroup>
<Accordion title="Use HTTPS endpoints only" icon="lock">
  webhook endpoint には常に HTTPS URL を使用してください。HTTP endpoint は man-in-the-middle 攻撃に対して脆弱であり、webhook データが公開される可能性があります。
</Accordion>

<Accordion title="Respond immediately" icon="bolt">
  webhook を受信したら、直ちに `200` status code を返してください。タイムアウトを避けるため、イベントは非同期で処理します。
  

  ```javascript
  app.post('/webhook', async (req, res) => {
    // Acknowledge receipt immediately
    res.status(200).json({ received: true });
    
    // Process asynchronously
    processWebhookAsync(req.body).catch(console.error);
  });
  ```

</Accordion>

<Accordion title="Handle duplicate events" icon="rotate">
  `webhook-id` header を使用して idempotency を実装し、副作用なしに同じイベントを複数回安全に処理できるようにしてください。
</Accordion>

<Accordion title="Secure your webhook secret" icon="key">
  webhook secret は、environment variables または secrets manager を使用して安全に保存してください。secret を version control にコミットしないでください。
</Accordion>
</AccordionGroup>

## Webhook Payload の構造

Webhook payload の構造を理解すると、イベントを正しく解析・処理できます。

### リクエスト形式

```http
POST /your-webhook-url
Content-Type: application/json
```

### Headers

<ParamField header="webhook-id" type="string" required>
この webhook event の一意の識別子。idempotency チェックに使用します。
</ParamField>

<ParamField header="webhook-signature" type="string" required>
webhook の信頼性を検証するための HMAC SHA256 signature。
</ParamField>

<ParamField header="webhook-timestamp" type="string" required>
webhook が送信された時刻を表す Unix timestamp（秒単位）。
</ParamField>

### Request Body

<ResponseField name="business_id" type="string" required>
Dodo Payments のビジネス識別子。
</ResponseField>

<ResponseField name="type" type="string" required>
この webhook を発生させたイベントタイプ（例：`payment.succeeded`、`subscription.active`）。
</ResponseField>

<ResponseField name="timestamp" type="string" required>
イベントが発生した時刻を ISO 8601 形式で表した timestamp。
</ResponseField>

<ResponseField name="data" type="object" required>
イベントに関する詳細情報を含む、イベント固有の payload。

<Expandable title="Data object properties">
  <ResponseField name="payload_type" type="string">
  リソースのタイプ。次のいずれかです：`Payment`、`Subscription`、`Refund`、`Dispute`、`LicenseKey`、`CreditLedgerEntry`、`CreditBalanceLow`、`AbandonedCheckout`、`DunningAttempt`、`EntitlementGrant`、または `Payout`。
  </ResponseField>
  
  その他のフィールドはイベントタイプによって異なります。完全なスキーマについては、イベント固有のドキュメントを参照してください。
</Expandable>
</ResponseField>

### Payload の例

```json
{
  "business_id": "string",
  "type": "payment.succeeded | payment.failed |...",
```

### 実装例

webhook の検証と処理を示す、完全な Express.js 実装を次に示します。

<CodeGroup>

```typescript Express.js Webhook Handler
import { Webhook } from "standardwebhooks";
import express from "express";

const app = express();
app.use(express.json());

const webhook = new Webhook(process.env.DODO_WEBHOOK_SECRET);

app.post('/webhook/dodo-payments', async (req, res) => {
  try {
    // Extract webhook headers
    const webhookHeaders = {
      "webhook-id": req.headers["webhook-id"] as string,
      "webhook-signature": req.headers["webhook-signature"] as string,
      "webhook-timestamp": req.headers["webhook-timestamp"] as string,
    };

    // Verify the webhook signature
    const payload = JSON.stringify(req.body);
    await webhook.verify(payload, webhookHeaders);
    
    // Acknowledge receipt immediately
    res.status(200).json({ received: true });
    
    // Process webhook asynchronously
    processWebhookAsync(req.body).catch(console.error);
    
  } catch (error) {
    console.error('Webhook verification failed:', error);
    res.status(400).json({ error: 'Invalid signature' });
  }
});

async function processWebhookAsync(data: any) {
  // Handle the webhook event based on type
  switch (data.type) {
    case 'payment.succeeded':
      await handlePaymentSucceeded(data);
      break;
    case 'subscription.active':
      await handleSubscriptionActive(data);
      break;
    // Add more event handlers...
  }
}
```


## CLI を使用した Webhook のテスト

[Dodo Payments CLI](/developer-resources/sdks/cli) には、terminal を離れることなく local development 中に webhook をテストできる 2 つのコマンドがあります。

### Live Webhook をローカルでリッスンする

test mode account から実際の webhook event を local development server にリアルタイムで転送します。

```bash
dodo wh listen
```

CLI は Dodo Payments への WebSocket 接続を開き、すべての webhook event をローカル endpoint（例：`http://localhost:3000/webhook`）に転送します。検証テスト用の signature headers を含む、すべての headers が保持されます。

<Info>
listener は **test mode** API keys でのみ動作します。このコマンドを使用する前に `dodo login` を実行し、Test Mode を選択してください。
</Info>

### Mock Webhook Event をトリガーする

実際の transaction を作成せずに、任意の endpoint へ mock webhook payload を送信します。

```bash
dodo wh trigger
```

この interactive tool ではイベントタイプを選択し、現実的な mock payload を endpoint に送信できます。ループするため、1 回の session で複数のイベントをテストできます。

trigger command は、Dodo Payments が配信する全 47 種類の event type に対応しています。subscription、payment、refund、dispute、license key、payout、credit、abandoned checkout、dunning、entitlement grant の各ファミリーが含まれます。正確なリストについては [Supported Webhook Events](/developer-resources/sdks/cli#supported-webhook-events) を参照してください。

<Warning>
`dodo wh trigger` からの mock webhook payload には署名がありません。テスト中の webhook handler では、`unwrap()` の代わりに `unsafe_unwrap()` を使用してください。
</Warning>

## Advanced Settings

**Advanced** tab には、webhook endpoint の動作を細かく調整するための追加設定オプションがあります。

### Rate Limiting（Throttling）

システムへの過負荷を防ぐため、webhook event が endpoint に配信される速度を制御します。

<Steps>
<Step title="Open Advanced Tab">
    endpoint details page で **Advanced** tab をクリックします。
</Step>

<Step title="Configure Rate Limit">
    "Rate Limit (throttling)" セクションで **Edit** をクリックし、rate limit settings を変更します。
    
    <Info>
    デフォルトでは webhook に rate limit は適用されないため、イベントは発生するとすぐに配信されます。
    </Info>
</Step>

<Step title="Set Your Limit">
    希望する rate limit を設定し、webhook の配信頻度を制御してシステムの過負荷を防ぎます。
</Step>
</Steps>

<Tip>
webhook handler でイベントの処理に時間が必要な場合や、複数のイベントをまとめて処理したい場合に rate limiting を使用します。
</Tip>

### Custom Headers

endpoint に送信するすべての webhook request に custom HTTP headers を追加します。認証、routing、または metadata の追加に便利です。

<Steps>
<Step title="Add Headers">
    "Custom Headers" セクションで、各 custom header の **Key** と **Value** を入力します。
</Step>

<Step title="Add Multiple Headers">
    必要に応じて **+** ボタンをクリックし、custom header を追加します。
</Step>
</Steps>

custom headers は、この endpoint へのすべての webhook request に含まれます。

### Transformations

Transformations を使用すると、webhook の payload を変更し、必要に応じて別の URL にリダイレクトできます。この強力な機能により、次のことが可能になります。

- 処理前に payload の構造を変更する
- 内容に基づいて webhook を異なる endpoint に routing する
- payload のフィールドを追加または削除する
- data format を変換する

<Steps>
<Step title="Enable Transformations">
    **Enabled** switch をオンにして transformation feature を有効化します。
</Step>

<Step title="Configure Transformation">
    **Edit transformation** をクリックし、JavaScript を使用して transformation rules を定義します。
</Step>

<Step title="Test Transformation">
    transformation test interface を使用して、本番稼働前に transformation が正しく動作することを確認します。
</Step>
</Steps>

<Warning>
Transformations は webhook delivery performance に影響を与える可能性があります。十分にテストし、transformation logic はシンプルかつ効率的に保ってください。
</Warning>

<Tip>
Transformations は特に次の用途に便利です。
- 異なる data format 間で変換する
- 特定の条件に基づいてイベントを filtering する
- payload に計算フィールドを追加する
- イベントを異なる microservices に routing する
</Tip>

## Activity Monitoring

**Developer → Webhooks** に移動し、**Activity** tab を開くと、各 endpoint の delivery performance を確認できます。

**Delivery activity** では、期間に応じて **Attempts per 5 minutes**、**Attempts per hour**、または **Attempts per day** として分類された attempt の推移を表示します。各バーは結果別に分割され、セグメントにカーソルを合わせると status、attempt 数、全体に占める割合が表示されます。endpoint の **Overview** tab にある **Delivery stats (last 24h)** では、過去 1 日分の同じ情報をまとめて確認できます。

<Tip>
**Endpoints** tab の **Error rate (24h)** 列を見ると、endpoint を開く前に対応が必要な endpoint をすぐに把握できます。
</Tip>

## Message の再生と復旧

message を再配信する方法は、必要な数によって異なります。

- **1 件の message** — **Logs** tab から message を開き、attempt の **Replay** action を使用します。endpoint を開く必要はありません。
- **複数の message の範囲** — bulk mode は一度に 1 つの endpoint に対して実行されるため、endpoint を開きます。

### Bulk での再生

**Developer → Webhooks** から endpoint を開きます。3 つの mode が利用でき、それぞれその endpoint だけに対して実行されます。設定する範囲は mode によって異なります。

| Mode | 動作 | 設定内容 |
|------|--------------|--------------|
| **Recover failed messages** | この endpoint への配信に失敗したすべての message を Replay します。 | 開始地点：**8 hours ago**、**Yesterday**、**3 days ago**、**Last week**、または **2 weeks ago** |
| **Replay missing messages** | たとえば新しい event type を subscribe した後など、この endpoint に一度も dispatch されていない message を Replay します。 | 同じ開始地点 |
| **Bulk replay messages** | 選択した filtering に一致する message を Replay します。すでに正常に配信された message も含まれます。 | **Since** と **Until** の範囲（デフォルトは過去 2 週間）、および任意の event type、channel、tag |

<Steps>
<Step title="Open More Actions">
    endpoint で **More actions** を開き、上記 3 つの mode のいずれかを選択します。
</Step>

<Step title="Set the Range">
    table に記載されている、その mode が求める範囲を入力します。
</Step>

<Step title="Start the Run">
    選択した mode に応じて **Recover** または **Replay** をクリックします。
</Step>
</Steps>

各実行は endpoint の **Overview** tab にある **Replay history** に表示され、mode、時間範囲、status、再送信された message 数を確認できます。
