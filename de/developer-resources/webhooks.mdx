Webhooks provide real-time notifications when specific events occur in your Dodo Payments account. Use webhooks to automate workflows, update your database, send notifications, and keep your systems synchronized.

<Info>
Our webhook implementation follows the [Standard Webhooks](https://standardwebhooks.com/) specification, ensuring compatibility with industry best practices and existing webhook libraries.
</Info>

## Getting Started

<Info>
Das Webhooks-Portal von Dodo Payments wurde mit einer nativen Dashboard-Erfahrung neu aufgebaut. Ihre bestehenden Endpoints, Signaturgeheimnisse, Signaturüberprüfung, Ereignisnamen und Webhook-Nutzlasten bleiben unverändert. Es ist keine Integrationsarbeit erforderlich.
</Info>

<Note>
**Wo sich die einzelnen Bereiche befinden.**

- **Unter Developer → Webhooks** — die Tabs **Endpoints**, **Event catalog**, **Logs**, **Activity** und **Settings**.
- **Auf einem einzelnen Endpoint** — der Tab **Overview** mit Zustellungsstatistiken, dem Signaturgeheimnis und dem **Replay history** sowie den Tabs **Testing** und **Advanced** und den Aktionen für die Massenwiederholung.
- **Auf einer Nachricht** — wird über den Tab **Logs** geöffnet. Dort kann jeder Zustellungsversuch einzeln wiederholt werden, ohne den Endpoint zu öffnen.
</Note>

<Steps>
<Step title="Access Webhook Settings">
    Navigieren Sie zum Dodo Payments Dashboard und gehen Sie zu **Developer → Webhooks**.
</Step>

<Step title="Create Webhook Endpoint">
    Klicken Sie auf **Add endpoint**, um das seitliche Fenster zur Endpoint-Erstellung zu öffnen.
</Step>

<Step title="Enter Endpoint URL or Choose Integration">
    Geben Sie die URL ein, unter der Sie Webhook-Ereignisse empfangen möchten, oder wählen Sie einen Integrations-Connector aus, um Ereignisse an einen Drittanbieterdienst (Slack, Discord, Zapier, Resend usw.) weiterzuleiten.
</Step>

<Step title="Select Events to Receive">
    Wählen Sie die spezifischen Ereignisse aus, auf die Ihr Endpoint reagieren soll. Die Ereignisse sind in einem durchsuchbaren, nach Ressourcen gruppierten Baum organisiert. Sie können einzelne Ereignisse oder eine übergeordnete Ressource auswählen, um alle zugehörigen Ereignisse zu empfangen.
    
    <Tip>
    Nur ausgewählte Ereignisse lösen Webhooks an Ihren Endpoint aus. So vermeiden Sie unnötigen Datenverkehr und unnötige Verarbeitung.
    </Tip>
</Step>

<Step title="Create Endpoint">
    Klicken Sie auf **Create endpoint**, um Ihre Konfiguration zu speichern.
</Step>

<Step title="Get Secret Key">
    Ihr Webhook-Signaturgeheimnis wird im Tab **Overview** des Endpoints angezeigt. Sie verwenden es, um die Authentizität empfangener Webhooks zu überprüfen.
    
    <Warning>
    Bewahren Sie Ihren Webhook-Geheimschlüssel sicher auf und legen Sie ihn niemals in clientseitigem Code oder öffentlichen Repositories offen.
    </Warning>
</Step>

<Step title="Rotate Secret (Optional)">
    Bei Bedarf können Sie Ihr Webhook-Geheimnis für zusätzliche Sicherheit rotieren. Klicken Sie im Tab **Overview** neben dem Geheimnis auf **Rotate secret**.
    
    <Warning>
    Durch die Rotation läuft das Geheimnis ab und wird durch ein neues ersetzt. Das alte Geheimnis bleibt nur für die nächsten 24 Stunden gültig. Danach schlägt eine Überprüfung mit dem alten Geheimnis fehl.
    </Warning>
    
    <Info>
    Rotieren Sie das Geheimnis regelmäßig oder sofort, wenn Sie vermuten, dass Ihr aktuelles Geheimnis kompromittiert wurde.
    </Info>
</Step>
</Steps>

## Integrations-Connectoren

Anstatt einen eigenen Webhook-Empfänger zu erstellen, können Sie Webhook-Ereignisse mithilfe von Integrations-Connectoren direkt an Drittanbieterdienste weiterleiten. Dadurch müssen Sie keine benutzerdefinierten Webhook-Handler für gängige Plattformen schreiben und warten.

### Funktionsweise von Connectoren

Ein Connector enthält eine Transformation, die das Dodo Payments-Ereignis in die von der Zielanwendung erwartete Form umwandelt. Welche Angaben Sie machen müssen, hängt vom Ziel ab:

| Connector-Typ | Ihre Angaben | Ziele |
|----------------|------------------|--------------|
| **Incoming webhook URL** | Eine Webhook-URL, die Sie im eigenen Dashboard des Anbieters erstellen. Kein API key. | [Slack](/integrations/slack), [Discord](/integrations/discord), [Microsoft Teams](/integrations/microsoft-teams), [Zapier](/integrations/zapier), [Windmill](/integrations/windmill) |
| **Vendor API** | Ein API key. Die Ziel-URL stammt aus der Connector-Vorlage. | [Resend](/integrations/resend), [SendGrid](/integrations/sendgrid), [Segment](/integrations/segment), [Customer.io](/integrations/customer-io), [HubSpot](/integrations/hubspot), [Close CRM](/integrations/close-crm), [Loops](/integrations/loops) |

Die Connector-Auswahl im Dashboard zeigt die vollständige Liste, die derzeit für Ihr Unternehmen verfügbar ist. Betrachten Sie die obige Tabelle daher als Liste der Ziele mit Schritt-für-Schritt-Anleitungen und nicht als vollständige Aufstellung. Unter [External Integrations](/integrations/introduction) erfahren Sie, welche Funktionen die einzelnen Ziele bieten, sobald sie Ereignisse empfangen.

### Einrichten eines Connectors

Wählen Sie beim Erstellen oder Bearbeiten eines Endpoints einen Connector aus. Das seitliche Fenster zeigt dann für das jeweilige Ziel verfasste Einrichtungsanweisungen an – beispielsweise zum Erstellen einer eingehenden Webhook-URL in Slack oder zum Auffinden Ihres Resend API key. Führen Sie vor dem Speichern den Test der Connector-Transformation aus, um zu bestätigen, dass das Ereignis korrekt für das Ziel umgewandelt wird.

<Tip>
Verwenden Sie einen Connector, um ein unterstütztes Ziel ohne eigenen Code zu erreichen. Wenn Sie benutzerdefinierte Logik benötigen, verwenden Sie stattdessen einen Standard-Endpoint mit einer [Transformation](#transformations).
</Tip>

## Webhook-Zustellung

### Timeouts

Für Webhooks gilt sowohl für Verbindungs- als auch für Lesevorgänge ein **15-sekündiges Timeout-Fenster**. Stellen Sie sicher, dass Ihr Endpoint schnell antwortet, um Timeouts zu vermeiden.

<Tip>
Verarbeiten Sie Webhooks asynchron, indem Sie den Empfang sofort mit einem `200` status code bestätigen und die eigentliche Verarbeitung anschließend im Hintergrund durchführen.
</Tip>

### Automatische Wiederholungen

Wenn eine Webhook-Zustellung fehlschlägt, führt Dodo Payments automatisch Wiederholungen mit exponentiellem Backoff durch, um eine Überlastung Ihres Systems zu verhindern.

| Versuch | Verzögerung | Beschreibung |
|---------|------------------------------|-------------|
| 1 | Sofort | Der erste Wiederholungsversuch erfolgt unmittelbar |
| 2 | 5 Sekunden | Der zweite Versuch erfolgt nach einer kurzen Verzögerung |
| 3 | 5 Minuten | Der dritte Versuch erfolgt mit erhöhtem Backoff |
| 4 | 30 Minuten | Der vierte Versuch setzt den Backoff fort |
| 5 | 2 Stunden | Der fünfte Versuch erfolgt mit verlängerter Verzögerung |
| 6 | 5 Stunden | Der sechste Versuch erfolgt mit längerer Verzögerung |
| 7 | 10 Stunden | Der siebte Versuch erfolgt mit maximaler Verzögerung |
| 8 | 10 Stunden | **Letzter Versuch** – der Webhook wird bei einem Fehlschlag als fehlgeschlagen markiert |

<Info>
**Maximal 8 Wiederholungsversuche** pro Webhook-Ereignis. Wenn ein Webhook beispielsweise dreimal fehlschlägt, bevor er erfolgreich zugestellt wird, beträgt die gesamte Zustellungszeit ab dem ersten Versuch ungefähr 35 Minuten und 5 Sekunden.
</Info>

<Tip>
Verwenden Sie das Dodo Payments Dashboard, um einzelne Nachrichten manuell zu wiederholen oder jederzeit alle fehlgeschlagenen Nachrichten gesammelt wiederherzustellen.
</Tip>

### Idempotenz

Jedes Webhook-Ereignis enthält einen eindeutigen `webhook-id` header. Verwenden Sie diesen Identifier, um Idempotenz zu implementieren und eine doppelte Verarbeitung zu verhindern.

```javascript
// Example: Storing webhook IDs to prevent duplicate processing
const processedWebhooks = new Set();

app.post('/webhook', (req, res) => {
  const webhookId = req.headers['webhook-id'];
  
  if (processedWebhooks.has(webhookId)) {
    return res.status(200).json({ received: true });
  }
  
  processedWebhooks.add(webhookId);
  // Process the webhook...
});
```

<Warning>
Implementieren Sie immer Idempotenzprüfungen. Aufgrund von Wiederholungen kann dasselbe Ereignis mehrfach bei Ihnen eingehen.
</Warning>

### Ereignisreihenfolge

Webhook-Ereignisse können aufgrund von Wiederholungen oder Netzwerkbedingungen in einer anderen Reihenfolge eintreffen. Entwickeln Sie Ihr System so, dass es Ereignisse in beliebiger Reihenfolge verarbeiten kann.

<Info>
Sie erhalten **die zum Zeitpunkt der Zustellung aktuellste Nutzlast**, unabhängig davon, wann das Webhook-Ereignis ursprünglich ausgelöst wurde.
</Info>

## Webhooks absichern

Um die Sicherheit Ihrer Webhooks zu gewährleisten, validieren Sie stets die Nutzlasten und verwenden Sie HTTPS.

### Signaturen überprüfen

Jede Webhook-Anfrage enthält einen `webhook-signature` header, eine HMAC-SHA256-Signatur der Webhook-Nutzlast und des Zeitstempels, die mit Ihrem Geheimschlüssel signiert wurde.

#### SDK verification (recommended)

Alle offiziellen SDKs enthalten integrierte Hilfsfunktionen, um eingehende Webhooks sicher zu validieren und zu parsen. Es stehen zwei Methoden zur Verfügung:

* `unwrap()`: Überprüft Signaturen mithilfe Ihres Webhook-Geheimschlüssels
* `unsafe_unwrap()`: Parst Nutzlasten ohne Überprüfung

<Tip>
  Geben Sie Ihr Webhook-Geheimnis über `DODO_PAYMENTS_WEBHOOK_KEY` an, wenn Sie den Dodo Payments-Client initialisieren.
</Tip>

<CodeGroup>

```typescript TypeScript/Node.js
import DodoPayments from 'dodopayments';
import express from 'express';

const app = express();
app.use(express.raw({ type: 'application/json' }));

const client = new DodoPayments({
  bearerToken: process.env.DODO_PAYMENTS_API_KEY,
  environment: process.env.DODO_PAYMENTS_ENVIRONMENT,
  webhookKey: process.env.DODO_PAYMENTS_WEBHOOK_KEY,
});

app.post('/webhook', async (req, res) => {
  try {
    const unwrapped = client.webhooks.unwrap(req.body.toString(), {
      headers: {
        'webhook-id': req.headers['webhook-id'] as string,
        'webhook-signature': req.headers['webhook-signature'] as string,
        'webhook-timestamp': req.headers['webhook-timestamp'] as string,
      },
    });
    res.json({ received: true });
  } catch (error) {
    res.status(401).json({ error: 'Invalid signature' });
  }
});
```

```python Python
from fastapi import FastAPI, Request, HTTPException
from dodopayments import DodoPayments
import os

app = FastAPI()
client = DodoPayments(
    bearer_token=os.getenv("DODO_PAYMENTS_API_KEY"),
    environment=os.getenv("DODO_PAYMENTS_ENVIRONMENT"),
    webhook_key=os.getenv("DODO_PAYMENTS_WEBHOOK_KEY"),
)

@app.post("/webhook")
async def handle_webhook(request: Request):
    try:
        unwrapped = client.webhooks.unwrap(
            await request.body(),
            headers={
                "webhook-id": request.headers.get("webhook-id", ""),
                "webhook-signature": request.headers.get("webhook-signature", ""),
                "webhook-timestamp": request.headers.get("webhook-timestamp", ""),
            },
        )
        return {"received": True}
    except Exception:
        raise HTTPException(status_code=401, detail="Invalid signature")
```

```go Go
import (
	"context"
	"io"
	"net/http"
	"os"
	"github.com/dodopayments/dodopayments-go"
	"github.com/dodopayments/dodopayments-go/option"
)

func webhookHandler(w http.ResponseWriter, r *http.Request) {
	client := dodopayments.NewClient(
		option.WithBearerToken(os.Getenv("DODO_PAYMENTS_API_KEY")),
		option.WithEnvironment(os.Getenv("DODO_PAYMENTS_ENVIRONMENT")),
		option.WithWebhookKey(os.Getenv("DODO_PAYMENTS_WEBHOOK_KEY")),
	)
	rawBody, _ := io.ReadAll(r.Body)
	if _, err := client.Webhooks.Unwrap(context.Background(), rawBody, map[string]string{
		"webhook-id":       r.Header.Get("webhook-id"),
		"webhook-signature": r.Header.Get("webhook-signature"),
		"webhook-timestamp": r.Header.Get("webhook-timestamp"),
	}); err != nil {
		http.Error(w, "Invalid signature", http.StatusUnauthorized)
		return
	}
	w.WriteHeader(http.StatusOK)
}
```

</CodeGroup>

#### Manuelle Überprüfung (Alternative)

Wenn Sie kein SDK verwenden, können Sie Signaturen selbst gemäß der Standard-Webhooks-Spezifikation überprüfen:

1. Erstellen Sie die signierte Nachricht, indem Sie `webhook-id`, `webhook-timestamp` und die exakt als Zeichenfolge serialisierte `payload` durch Punkte (`.`) getrennt verketten.
2. Berechnen Sie den HMAC SHA256 dieser Zeichenfolge mithilfe Ihres Webhook-Geheimschlüssels aus dem Dashboard.
3. Vergleichen Sie die berechnete Signatur mit dem `webhook-signature` header. Stimmen sie überein, ist der Webhook authentisch.

<Info>
  Wir befolgen die Standard-Webhooks-Spezifikation. Sie können deren Bibliotheken zur Signaturüberprüfung verwenden: [https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries](https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries). Informationen zu den Formaten der Ereignisnutzlasten finden Sie unter [Webhook Payload](/developer-resources/webhooks/intents/payment).
</Info>

### Auf Webhooks antworten

* Ihr Webhook-Handler muss ein `2xx status code` zurückgeben, um den Empfang des Ereignisses zu bestätigen.
* Jede andere Antwort wird als Fehler behandelt und der Webhook wird erneut versucht.

### Best Practices

<AccordionGroup>
<Accordion title="Use HTTPS endpoints only" icon="lock">
  Verwenden Sie für Webhook-Endpoints immer HTTPS-URLs. HTTP-Endpoints sind anfällig für Man-in-the-Middle-Angriffe und legen Ihre Webhook-Daten offen.
</Accordion>

<Accordion title="Respond immediately" icon="bolt">
  Geben Sie unmittelbar nach dem Empfang des Webhooks einen `200` status code zurück. Verarbeiten Sie das Ereignis asynchron, um Timeouts zu vermeiden.
  

  ```javascript
  app.post('/webhook', async (req, res) => {
    // Acknowledge receipt immediately
    res.status(200).json({ received: true });
    
    // Process asynchronously
    processWebhookAsync(req.body).catch(console.error);
  });
  ```

</Accordion>

<Accordion title="Handle duplicate events" icon="rotate">
  Implementieren Sie Idempotenz mithilfe des `webhook-id` header, damit dasselbe Ereignis ohne Seiteneffekte sicher mehrfach verarbeitet werden kann.
</Accordion>

<Accordion title="Secure your webhook secret" icon="key">
  Speichern Sie Ihr Webhook-Geheimnis mithilfe von environment variables oder einem secrets manager sicher. Übertragen Sie Geheimnisse niemals in die Versionsverwaltung.
</Accordion>
</AccordionGroup>

## Struktur der Webhook-Nutzlast

Wenn Sie die Struktur der Webhook-Nutzlast verstehen, können Sie Ereignisse korrekt parsen und verarbeiten.

### Anfrageformat

```http
POST /your-webhook-url
Content-Type: application/json
```

### Header

<ParamField header="webhook-id" type="string" required>
Eindeutiger Identifier für dieses Webhook-Ereignis. Verwenden Sie ihn für Idempotenzprüfungen.
</ParamField>

<ParamField header="webhook-signature" type="string" required>
HMAC-SHA256-Signatur zur Überprüfung der Authentizität des Webhooks.
</ParamField>

<ParamField header="webhook-timestamp" type="string" required>
Unix-Zeitstempel (in Sekunden), zu dem der Webhook gesendet wurde.
</ParamField>

### Anfrage-Body

<ResponseField name="business_id" type="string" required>
Identifier Ihres Dodo Payments-Geschäfts.
</ResponseField>

<ResponseField name="type" type="string" required>
Ereignistyp, der diesen Webhook ausgelöst hat (z. B. `payment.succeeded`, `subscription.active`).
</ResponseField>

<ResponseField name="timestamp" type="string" required>
ISO-8601-formatierter Zeitstempel des Zeitpunkts, zu dem das Ereignis aufgetreten ist.
</ResponseField>

<ResponseField name="data" type="object" required>
Ereignisspezifische Nutzlast mit detaillierten Informationen zum Ereignis.

<Expandable title="Data object properties">
  <ResponseField name="payload_type" type="string">
  Ressourcentyp. Einer von: `Payment`, `Subscription`, `Refund`, `Dispute`, `LicenseKey`, `CreditLedgerEntry`, `CreditBalanceLow`, `AbandonedCheckout`, `DunningAttempt`, `EntitlementGrant` oder `Payout`.
  </ResponseField>
  
  Weitere Felder unterscheiden sich je nach Ereignistyp. Die vollständigen Schemas finden Sie in der ereignisspezifischen Dokumentation.
</Expandable>
</ResponseField>

### Beispielnutzlast

```json
{
  "business_id": "string",
  "type": "payment.succeeded | payment.failed |...",
  "timestamp": "2024-01-01T12:00:00Z",
  "data": {
    "payload_type": "Payment | Subscription | Refund | Dispute | LicenseKey | CreditLedgerEntry | CreditBalanceLow | AbandonedCheckout | DunningAttempt | EntitlementGrant | Payout",
    // ... event-specific fields (see below)
  }
}
```

### Implementierungsbeispiel

Hier sehen Sie eine vollständige Express.js-Implementierung zur Überprüfung und Verarbeitung von Webhooks:

<CodeGroup>

```typescript Express.js Webhook Handler
import { Webhook } from "standardwebhooks";
import express from "express";

const app = express();
app.use(express.json());

const webhook = new Webhook(process.env.DODO_WEBHOOK_SECRET);

app.post('/webhook/dodo-payments', async (req, res) => {
  try {
    // Extract webhook headers
    const webhookHeaders = {
      "webhook-id": req.headers["webhook-id"] as string,
      "webhook-signature": req.headers["webhook-signature"] as string,
      "webhook-timestamp": req.headers["webhook-timestamp"] as string,
    };

    // Verify the webhook signature
    const payload = JSON.stringify(req.body);
    await webhook.verify(payload, webhookHeaders);
    
    // Acknowledge receipt immediately
    res.status(200).json({ received: true });
    
    // Process webhook asynchronously
    processWebhookAsync(req.body).catch(console.error);
    
  } catch (error) {
    console.error('Webhook verification failed:', error);
    res.status(400).json({ error: 'Invalid signature' });
  }
});

async function processWebhookAsync(data: any) {
  // Handle the webhook event based on type
  switch (data.type) {
    case 'payment.succeeded':
      await handlePaymentSucceeded(data);
      break;
    case 'subscription.active':
      await handleSubscriptionActive(data);
      break;
    // Add more event handlers...
  }
}
```

```javascript Testing Webhooks Locally
const webhookId = crypto.randomUUID();
const payload = {
  business_id: "biz_test123",
  type: "payment.succeeded",
  timestamp: timestamp.toISOString(),
  data: {
    payload_type: "Payment",
    payment_id: "pay_test456",
    amount: 2999
  }
};

// Sign the payload
const webhookSecret = process.env.DODO_WEBHOOK_SECRET;
const webhookInstance = new Webhook(webhookSecret);
const payloadString = JSON.stringify(payload);
const signature = webhookInstance.sign(webhookId, timestamp, payloadString);

// Send test webhook
const response = await axios.post('http://localhost:3000/webhook/dodo-payments', payload, {
  headers: {
    "webhook-id": webhookId,
    "webhook-timestamp": Math.floor(timestamp.getTime() / 1000),
    "webhook-signature": signature,
    "Content-Type": "application/json"
  }
});

console.log("Test webhook sent successfully:", response.data);
```

</CodeGroup>

<Tip>
Testen Sie Ihren Webhook-Handler gründlich über die Dashboard-Testoberfläche, bevor Sie Produktionsereignisse verarbeiten. So können Sie Probleme frühzeitig erkennen und beheben.
</Tip>

## Webhooks mit der CLI testen

Die [Dodo Payments CLI](/developer-resources/sdks/cli) stellt zwei Befehle zum Testen von Webhooks während der lokalen Entwicklung bereit, ohne dass Sie Ihr Terminal verlassen müssen.

### Live-Webhooks lokal empfangen

Leiten Sie echte Webhook-Ereignisse in Echtzeit von Ihrem Konto im Testmodus an Ihren lokalen Entwicklungsserver weiter:

```bash
dodo wh listen
```

Die CLI öffnet eine WebSocket-Verbindung zu Dodo Payments und leitet jedes Webhook-Ereignis an Ihren lokalen Endpoint weiter (z. B. `http://localhost:3000/webhook`). Dabei bleiben alle Header einschließlich der Signatur-Header für Testzwecke erhalten.

<Info>
Der Listener funktioniert nur mit **test mode** API keys. Führen Sie `dodo login` aus und wählen Sie vor der Verwendung dieses Befehls Test Mode aus.
</Info>

### Mock-Webhook-Ereignisse auslösen

Senden Sie Mock-Webhook-Nutzlasten an einen beliebigen Endpoint, ohne echte Transaktionen zu erstellen:

```bash
dodo wh trigger
```

Mit diesem interaktiven Tool können Sie einen Ereignistyp auswählen und eine realistische Mock-Nutzlast an Ihren Endpoint senden. Das Tool läuft in einer Schleife, sodass Sie mehrere Ereignisse in einer Sitzung testen können.

Der Trigger-Befehl deckt alle 46 Ereignistypen ab, die Dodo Payments zustellt, einschließlich der Familien für Abonnements, Zahlungen, Rückerstattungen, Streitfälle, Lizenzschlüssel, Auszahlungen, Guthaben, abgebrochene Checkouts, Mahnverfahren und Berechtigungsvergabe. Die genaue Liste finden Sie unter [Supported Webhook Events](/developer-resources/sdks/cli#supported-webhook-events).

<Warning>
Mock-Webhook-Nutzlasten aus `dodo wh trigger` sind nicht signiert. Verwenden Sie während des Testens in Ihrem Webhook-Handler `unsafe_unwrap()` anstelle von `unwrap()`.
</Warning>

## Erweiterte Einstellungen

Der Tab **Advanced** bietet zusätzliche Konfigurationsoptionen zur Feinabstimmung des Verhaltens Ihres Webhook-Endpoints.

### Rate Limiting (Throttling)

Steuern Sie die Rate, mit der Webhook-Ereignisse an Ihren Endpoint zugestellt werden, um eine Überlastung Ihres Systems zu verhindern.

<Steps>
<Step title="Open Advanced Tab">
    Klicken Sie auf der Detailseite Ihres Endpoints auf den Tab **Advanced**.
</Step>

<Step title="Configure Rate Limit">
    Klicken Sie im Abschnitt „Rate Limit (throttling)“ auf **Edit**, um die Rate-Limit-Einstellungen zu ändern.
    
    <Info>
    Standardmäßig gilt für Webhooks kein Rate Limit. Ereignisse werden also zugestellt, sobald sie auftreten.
    </Info>
</Step>

<Step title="Set Your Limit">
    Konfigurieren Sie das gewünschte Rate Limit, um die Häufigkeit der Webhook-Zustellung zu steuern und eine Systemüberlastung zu verhindern.
</Step>
</Steps>

<Tip>
Verwenden Sie Rate Limiting, wenn Ihr Webhook-Handler Zeit zur Verarbeitung von Ereignissen benötigt oder Sie mehrere Ereignisse bündeln möchten.
</Tip>

### Benutzerdefinierte Header

Fügen Sie allen an Ihren Endpoint gesendeten Webhook-Anfragen benutzerdefinierte HTTP-Header hinzu. Dies ist nützlich für Authentifizierung, Routing oder zusätzliche Metadaten.

<Steps>
<Step title="Add Headers">
    Geben Sie im Abschnitt „Custom Headers“ für jeden benutzerdefinierten Header einen **Key** und einen **Value** ein.
</Step>

<Step title="Add Multiple Headers">
    Klicken Sie auf die Schaltfläche **+**, um nach Bedarf weitere benutzerdefinierte Header hinzuzufügen.
</Step>
</Steps>

Ihre benutzerdefinierten Header werden in alle Webhook-Anfragen an diesen Endpoint aufgenommen.

### Transformationen

Mit Transformationen können Sie die Nutzlast eines Webhooks ändern und ihn optional an eine andere URL weiterleiten. Diese leistungsstarke Funktion ermöglicht Ihnen Folgendes:

- Die Struktur der Nutzlast vor der Verarbeitung ändern
- Webhooks anhand ihres Inhalts an verschiedene Endpoints weiterleiten
- Felder zur Nutzlast hinzufügen oder daraus entfernen
- Datenformate umwandeln

<Steps>
<Step title="Enable Transformations">
    Aktivieren Sie den Schalter **Enabled**, um die Transformationsfunktion einzuschalten.
</Step>

<Step title="Configure Transformation">
    Klicken Sie auf **Edit transformation**, um Ihre Transformationsregeln mit JavaScript zu definieren.
</Step>

<Step title="Test Transformation">
    Verwenden Sie die Testoberfläche für Transformationen, um vor dem Produktivstart zu überprüfen, ob Ihre Transformation korrekt funktioniert.
</Step>
</Steps>

<Warning>
Transformationen können die Leistung der Webhook-Zustellung beeinflussen. Testen Sie sie gründlich und halten Sie die Transformationslogik einfach und effizient.
</Warning>

<Tip>
Transformationen sind besonders nützlich für:
- die Konvertierung zwischen verschiedenen Datenformaten
- das Filtern von Ereignissen anhand bestimmter Kriterien
- das Hinzufügen berechneter Felder zur Nutzlast
- das Weiterleiten von Ereignissen an verschiedene Microservices
</Tip>

## Webhook-Logs überwachen

Der Tab **Logs** bietet umfassende Einblicke in den Status Ihrer Webhook-Zustellungen und ermöglicht Ihnen, Webhook-Ereignisse effektiv zu überwachen, zu debuggen und zu verwalten.

<Steps>
<Step title="Navigate to Logs Tab">
    Gehen Sie zu **Developer → Webhooks** und öffnen Sie den Tab **Logs**.
</Step>

<Step title="Browse Delivery History">
    Sehen Sie eine Tabelle mit allen Webhook-Zustellungsversuchen und den Spalten Event type, Message ID, Event ID, Sent at, Attempted at, Response code und Duration.
</Step>

<Step title="Search and Filter">
    Verwenden Sie die Suchleiste, um bestimmte Nachrichten anhand ihrer ID oder ihres Ereignistyps zu finden. Filtern Sie nach Status (Succeeded, Failed, Pending usw.), um sich auf die zu untersuchenden Ereignisse zu konzentrieren.
</Step>

<Step title="View Message Details">
    Klicken Sie auf eine beliebige Nachricht, um die Nachrichtendetailseite zu öffnen. Dort werden angezeigt:
    - die vollständige Webhook-Nutzlast
    - jeder Zustellungsversuch mit Antwortcode und Dauer
    - der Zeitstempel jedes Versuchs
    - alle Fehlermeldungen Ihres Endpoints

    Jeder Versuch enthält eine Aktion **Replay**, sodass Sie diese eine Nachricht erneut auslösen können, ohne die Seite zu verlassen.
</Step>
</Steps>

## Aktivitätsüberwachung

Gehen Sie zu **Developer → Webhooks** und öffnen Sie den Tab **Activity**, um die Zustellungsleistung für Ihre Endpoints anzuzeigen.

**Delivery activity** stellt Versuche im Zeitverlauf dar – abhängig vom Zeitraum gruppiert als **Attempts per 5 minutes**, **Attempts per hour** oder **Attempts per day**. Jeder Balken ist nach Ergebnis unterteilt. Wenn Sie den Mauszeiger über ein Segment bewegen, werden der Status, die Anzahl der Versuche und dessen Anteil an der Gesamtsumme angezeigt. Auf einem Endpoint fasst **Delivery stats (last 24h)** im Tab **Overview** dieselben Informationen für den vergangenen Tag zusammen.

<Tip>
Die Spalte **Error rate (24h)** im Tab **Endpoints** zeigt auf einen Blick, bei welchen Endpoints Handlungsbedarf besteht, bevor Sie einen davon öffnen.
</Tip>

## Nachrichten wiederholen und wiederherstellen

Wie Sie eine Nachricht erneut auslösen, hängt von der benötigten Anzahl ab:

- **Eine Nachricht** — öffnen Sie sie im Tab **Logs** und verwenden Sie die Aktion **Replay** für den Versuch. Der Endpoint muss nicht geöffnet werden.
- **Ein Nachrichtenbereich** — öffnen Sie den Endpoint, da die Massenmodi jeweils nur auf einen Endpoint angewendet werden.

### Massenwiederholung

Öffnen Sie den Endpoint über **Developer → Webhooks**. Es stehen drei Modi zur Verfügung, die jeweils nur auf diesen Endpoint angewendet werden. Der festzulegende Bereich hängt vom Modus ab:

| Modus | Funktion | Ihre Eingabe |
|------|--------------|--------------|
| **Recover failed messages** | Wiederholt jede Nachricht an diesen Endpoint, deren Zustellung fehlgeschlagen ist. | Ein Startpunkt: **8 hours ago**, **Yesterday**, **3 days ago**, **Last week** oder **2 weeks ago** |
| **Replay missing messages** | Wiederholt Nachrichten, die nie an diesen Endpoint gesendet wurden, beispielsweise nachdem Sie ihn für einen neuen Ereignistyp abonniert haben. | Dieselben Startpunkte |
| **Bulk replay messages** | Wiederholt Nachrichten, die den ausgewählten Filtern entsprechen, einschließlich bereits erfolgreich zugestellter Nachrichten. | Grenzen für **Since** und **Until**, standardmäßig die letzten zwei Wochen, sowie optional Ereignistypen, Channel oder Tag |

<Steps>
<Step title="Open More Actions">
    Öffnen Sie auf dem Endpoint **More actions** und wählen Sie einen der drei oben genannten Modi aus.
</Step>

<Step title="Set the Range">
    Geben Sie den für diesen Modus erforderlichen Bereich wie in der Tabelle angegeben ein.
</Step>

<Step title="Start the Run">
    Klicken Sie je nach ausgewähltem Modus auf **Recover** oder **Replay**.
</Step>
</Steps>

Jeder Durchlauf erscheint unter **Replay history** im Tab **Overview** des Endpoints, einschließlich Modus, Zeitraum, Status und Anzahl der erneut gesendeten Nachrichten.

## E-Mail-Benachrichtigungen

Erhalten Sie eine E-Mail-Benachrichtigung, wenn Webhook-Zustellungen an einen Endpoint fehlschlagen, damit Sie Probleme beheben können, bevor sich ein Rückstau bildet.

<Steps>
<Step title="Navigate to Settings Tab">
  Gehen Sie zu **Developer → Webhooks** und öffnen Sie den Tab **Settings**.
</Step>

<Step title="Find Email Alerting">
  Suchen Sie die Karte **Email alerting**.
</Step>

<Step title="Configure Email Addresses">
  Geben Sie die Adressen ein, die die Benachrichtigungen erhalten sollen. Trennen Sie mehrere Adressen durch Kommas. Lassen Sie das Feld leer, um die Benachrichtigungen zu deaktivieren.
</Step>

<Step title="Save">
  Klicken Sie auf **Save**, um Ihre Änderungen anzuwenden.
</Step>
</Steps>

<Tip>
Aktivieren Sie E-Mail-Benachrichtigungen, um Probleme bei der Webhook-Zustellung frühzeitig zu erkennen und zuverlässige Integrationen aufrechtzuerhalten.
</Tip>
