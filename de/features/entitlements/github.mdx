<Info>
Die GitHub-Berechtigung fügt einen zahlenden Kunden als Kollaborator in einem privaten Repository hinzu. Sie wählen die Berechtigungsebene (`pull`, `push`, `triage`, `maintain` oder `admin`) und Dodo Payments übernimmt Einladung, Annahmeüberwachung und Entfernung bei Kündigung.
</Info>

## Was geliefert wird

- Der Kunde wird über einen OAuth-Flow, der seinen GitHub-Account mit dem Kauf verknüpft, zu Ihrem GitHub-Repository eingeladen.
- Sobald sie akzeptieren, gewährt GitHub ihnen auf der konfigurierten Berechtigungsebene Kollaboratorenzugang.
- Kündigung, Rückerstattung oder manueller Widerruf entfernt den Kollaborator.

Häufige Anwendungen sind quelloffene Produkte, bezahlte Vorlagen, Kurscode-Repos und gesperrte Client-SDKs.

## GitHub verbinden

<Steps>

Gehen Sie in Ihrem Dodo Payments-Dashboard zu **Berechtigungen** und klicken Sie auf **+** , um eine neue Berechtigung zu starten.

<Step title="Pick GitHub">
Wählen Sie **GitHub-Zugang** als Integration. Falls GitHub noch nicht verbunden ist, werden Sie aufgefordert, **GitHub verbinden** auszuwählen.

## Berechtigungsstufen

GitHubs Standard-Repository-Berechtigungen gelten:

| Berechtigung | Beste Verwendung |
|---|---|
| `pull` | Nur-Lese-Zugriff. Kunden können das Repo klonen, abrufen und anzeigen. |
| `triage` | Lesezugriff plus die Möglichkeit, Issues und Pull-Anfragen zu verwalten. |
| `push` | Lese- + Schreibzugriff. Kunden können Branches pushen und Pull-Anfragen öffnen. |
| `maintain` | Push-Zugriff plus Verwaltung der Repositoriumseinstellungen (außer sensitiven). |
| `admin` | Volle Kontrolle über das Repository. Mit Vorsicht verwenden. |

<Warning>
Gewähren Sie das **geringste Privileg**, das zu Ihrem Anwendungsfall passt. Die meisten Szenarien mit kostenpflichtigem Inhalt benötigen nur `pull`.
</Warning>

## Kundenfluss

1. Der Kunde schließt den Checkout ab.
2. Dodo Payments erstellt einen Grant im Status `Pending`. Sein `oauth_url` ist `null`, bis der Kunde den Akzeptierungsablauf startet. Zu diesem Zeitpunkt wird es mit einer GitHub-Autorisierungs-URL befüllt.
3. Der Kunde autorisiert den Zugriff über den Link in seiner E-Mail oder im Customer Portal.
4. Dodo Payments lädt das GitHub-Konto des Kunden mit der konfigurierten Berechtigung in das Repository ein. Der Grant wechselt zu `Delivered`, sobald die Einladung erstellt wurde.
5. Wenn das Abonnement gekündigt, erstattet oder widerrufen wird, wird der Kunde als Mitwirkender entfernt.

## Erforderliche Konfiguration

| Feld | Erforderlich | Beschreibung |
|---|---|---|
| `target_id` | Ja | Das Repository, zu dem der Kunde eingeladen werden soll. Der Repository-Auswahldialog im Dashboard füllt dies für Sie aus. |
| `permission` | Ja | Eine der Optionen: `pull`, `push`, `triage`, `maintain`, `admin`. |

## Erstellung über API

<CodeGroup>

```typescript TypeScript theme={null}
const entitlement = await client.entitlements.create({
  name: 'Code Share Repository',
  integration_type: 'github',
  integration_config: {
    target_id: 'acme/private-sdk',
    permission: 'pull',
  },
});
```

```python Python theme={null}
client.entitlements.create(
    name="Code Share Repository",
    integration_type="github",
    integration_config={
        "target_id": "acme/private-sdk",
        "permission": "pull",
    },
)
```

```go Go theme={null}
client.Entitlements.New(ctx, dodopayments.EntitlementNewParams{
  Name:            dodopayments.F("Code Share Repository"),
  IntegrationType: dodopayments.F(dodopayments.EntitlementIntegrationTypeGithub),
  IntegrationConfig: dodopayments.F[dodopayments.IntegrationConfigUnionParam](
    dodopayments.IntegrationConfigGitHubConfigParam{
      TargetID:   dodopayments.F("acme/private-sdk"),
      Permission: dodopayments.F("pull"),
    },
  ),
})
```

</CodeGroup>

## Webhooks

Die Standard-[`entitlement_grant.*` Webhook-Ereignisse](/developer-resources/webhooks/intents/entitlement-grant) decken den GitHub-Flow ab:

- `entitlement_grant.created` wird mit `status: "Pending"` ausgelöst, während `oauth_url` noch `null` ist. Die GitHub-Autorisierungs-URL wird ausgefüllt, sobald der Kunde den Akzeptierungsablauf über seine Zustellungs-E-Mail oder das Customer Portal startet.
- `entitlement_grant.delivered` wird ausgelöst, sobald die Einladung des Mitwirkenden erstellt wurde.
- `entitlement_grant.failed` wird mit `error_code: "github_permission_denied"` (oder einem ähnlichen Wert) ausgelöst, wenn die GitHub App den Zugriff auf das Repository verloren hat.

## Fehlerbehebung

<AccordionGroup>
<Accordion title="Repository picker is empty">
Die Dodo Payments GitHub App muss auf der Org oder dem Benutzer installiert sein, die bzw. der das Repository besitzt. Öffnen Sie **Berechtigungen → Integrationen → GitHub** und installieren Sie die App neu, indem Sie sicherstellen, dass Sie den relevanten Repositories Zugriff gewähren.
</Accordion>

<Accordion title="Grant fails with permission_denied">
Die Installation der GitHub App hat keinen Zugriff mehr auf das Repository oder das Repository wurde umbenannt/übertragen. Gewähren Sie der App erneut Zugang und der nächste Regrant wird erfolgreich sein.
</Accordion>

<Accordion title="Customer hasn't accepted the invite">
Kunden müssen die GitHub-Einladung auf ihrer Benachrichtigungsseite oder durch Klicken auf den Link in ihrer E-Mail annehmen. Bis sie die Einladung annehmen, bleiben sie „eingeladen“, können das Repository jedoch nicht klonen. Aus Sicht von Dodo Payments bleibt die Berechtigung weiterhin `Delivered`; die Einladung ist das, was wir ausstellen.
</Accordion>
</AccordionGroup>
