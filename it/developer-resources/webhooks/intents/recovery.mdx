## Eventi di Recupero del Carrello Abbandonato

I seguenti eventi webhook tracciano il ciclo di vita del recupero del carrello abbandonato:

| Evento | Descrizione |
|-------|-------------|
| `abandoned_checkout.detected` | È stato rilevato un checkout abbandonato. Inviato quando un pagamento viene identificato come abbandonato (fallito o incompleto) e inizia il flusso di lavoro di recupero. |
| `abandoned_checkout.recovered` | Il cliente ha completato il pagamento tramite il link di recupero. Il campo `recovered_payment_id` contiene l'ID del pagamento riuscito. |

### Campi del Payload del Checkout Abbandonato

<ParamField body="payment_id" type="string" required>
Il pagamento originale che è stato abbandonato. Usalo per cercare i dettagli del prodotto, importo e valuta.
</ParamField>

<ParamField body="brand_id" type="string" required>
Il brand a cui appartiene questo checkout abbandonato.
</ParamField>

<ParamField body="customer_id" type="string" required>
Il cliente che ha abbandonato il checkout.
</ParamField>

<ParamField body="abandonment_reason" type="string" required>
Il motivo per cui il checkout è stato abbandonato. Uno tra:
- `payment_failed` — Il cliente ha tentato di effettuare il pagamento, ma non è riuscito
- `checkout_incomplete` — Il cliente ha visitato il checkout, ma non ha mai tentato di effettuare il pagamento
</ParamField>

<ParamField body="status" type="string" required>
Stato attuale del lifecycle di questo tentativo di recupero. Uno tra:
- `abandoned` — Rilevato, nessuna email ancora inviata
- `recovering` — Almeno un'email di recupero inviata
- `recovered` — Il cliente ha completato il pagamento
- `exhausted` — Tutte le email sono state inviate oppure è stato trovato un checkout più recente
- `opted_out` — Il cliente ha annullato l'iscrizione
</ParamField>

<ParamField body="abandoned_at" type="string" required>
Timestamp ISO 8601 del momento in cui il checkout è stato rilevato come abbandonato.
</ParamField>

<ParamField body="recovered_payment_id" type="string | null">
L'ID del pagamento di recupero completato correttamente. `null` fino al recupero del checkout.
</ParamField>

### Esempio: gestione dei webhook ACR

```javascript
app.post('/webhooks/dodo', async (req, res) => {
  const event = req.body;

  switch (event.type) {
    case 'abandoned_checkout.detected':
      console.log(`Checkout abandoned: ${event.data.payment_id}`);
      console.log(`Reason: ${event.data.abandonment_reason}`);
      // Track abandonment in your analytics
      await trackAbandonment(event.data);
      break;

    case 'abandoned_checkout.recovered':
      console.log(`Checkout recovered: ${event.data.payment_id}`);
      console.log(`Recovery payment: ${event.data.recovered_payment_id}`);
      // Grant access, update records
      await handleRecovery(event.data);
      break;
  }

  res.json({ received: true });
});
```

## Eventi di dunning

I seguenti eventi webhook tengono traccia del lifecycle di dunning dell'abbonamento:

| Evento | Descrizione |
|-------|-------------|
| `dunning.started` | È stato creato un tentativo di dunning per un abbonamento che è entrato nello stato `on_hold` o che è stato annullato dal cliente. |
| `dunning.recovered` | Il cliente ha aggiornato il metodo di pagamento e il pagamento risultante è andato a buon fine. Il campo `payment_id` contiene l'ID del pagamento completato correttamente. |

### Campi del payload del tentativo di dunning

<ParamField body="subscription_id" type="string" required>
L'abbonamento che ha attivato il tentativo di dunning.
</ParamField>

<ParamField body="brand_id" type="string" required>
Il brand a cui appartiene questo tentativo di dunning.
</ParamField>

<ParamField body="customer_id" type="string" required>
Il cliente proprietario dell'abbonamento.
</ParamField>

<ParamField body="trigger_state" type="string" required>
Lo stato dell'abbonamento che ha attivato il dunning. Uno di:
- `on_hold` — Rinnovi interrotti a causa di un mancato pagamento
- `cancelled` — Il cliente ha annullato l'abbonamento dal Customer Portal
</ParamField>

<ParamField body="status" type="string" required>
Stato attuale del lifecycle di questo tentativo di dunning. Uno tra:
- `recovering` — Le email di dunning sono in fase di invio
- `recovered` — Il cliente ha aggiornato il metodo di pagamento e il pagamento è andato a buon fine
- `exhausted` — Tutte le email sono state inviate oppure lo stato dell'abbonamento è cambiato
</ParamField>

<ParamField body="created_at" type="string" required>
Timestamp ISO 8601 del momento in cui è stato creato il tentativo di dunning.
</ParamField>

<ParamField body="payment_id" type="string | null">
L'ID del pagamento di recupero completato correttamente. `null` durante il recupero.
</ParamField>

### Esempio: gestione dei webhook di dunning

```javascript
app.post('/webhooks/dodo', async (req, res) => {
  const event = req.body;

  switch (event.type) {
    case 'dunning.started':
      console.log(`Dunning started for subscription: ${event.data.subscription_id}`);
      console.log(`Trigger: ${event.data.trigger_state}`);
      // Track dunning in your system
      await trackDunning(event.data);
      break;

    case 'dunning.recovered':
      console.log(`Subscription recovered: ${event.data.subscription_id}`);
      console.log(`Recovery payment: ${event.data.payment_id}`);
      // Reactivate access, update records
      await handleDunningRecovery(event.data);
      break;
  }

  res.json({ received: true });
});
```

<Tip>
Sottoscrivi entrambi `dunning.started` e `dunning.recovered` per tenere traccia dell'intero lifecycle di dunning. Usa `dunning.started` per sospendere i periodi di tolleranza o contrassegnare nel tuo sistema gli abbonamenti a rischio.
</Tip>
