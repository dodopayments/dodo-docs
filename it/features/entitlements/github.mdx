<Info>
Il diritto GitHub aggiunge un cliente pagante come collaboratore su un repository privato. Scegli il livello di autorizzazione (`pull`, `push`, `triage`, `maintain`, o `admin`) e Dodo Payments gestisce l'invito, il monitoraggio dell'accettazione e la rimozione in caso di cancellazione.
</Info>

## Cosa viene consegnato

- Il cliente viene invitato al tuo repository GitHub tramite un flusso OAuth che collega il suo account GitHub all'acquisto.
- Una volta accettato, GitHub concede loro l'accesso come collaboratori al livello di autorizzazione configurato.
- La cancellazione, il rimborso o la revoca manuale rimuove il collaboratore.

Gli usi comuni includono prodotti con codice sorgente disponibile, modelli a pagamento, repository di codice per corsi e SDK client con accesso limitato.

## Livelli di autorizzazione

Si applicano le autorizzazioni standard del repository GitHub:

| Autorizzazione | Migliore per |
|---|---|
| `pull` | Accesso in sola lettura. I clienti possono clonare, recuperare e visualizzare il repo. |
| `triage` | Accesso di lettura più la possibilità di gestire problemi e richieste di pull. |
| `push` | Accesso in lettura + scrittura. I clienti possono inviare modifiche e aprire richieste di pull. |
| `maintain` | Accesso invio più gestione delle impostazioni del repository (esclusi quelli sensibili). |
| `admin` | Controllo completo del repository. Usare con cautela. |

<Warning>
Concedi il **minimo privilegio** che si adatta al tuo caso d'uso. La maggior parte degli scenari a pagamento richiede solo `pull`.
</Warning>

## Flusso del cliente

1. Il cliente completa il checkout.
2. Dodo Payments crea un grant con stato `Pending`. Il suo `oauth_url` è `null` finché il cliente non avvia il flusso di accettazione; a quel punto viene popolato con un URL di autorizzazione GitHub.
3. Il cliente esegue l'autorizzazione tramite il link contenuto nella propria email o nel customer portal.
4. Dodo Payments invita l'account GitHub del cliente al repository con il livello di autorizzazione configurato. Il grant passa a `Delivered` una volta creata l'invito.
5. Se l'abbonamento viene annullato, rimborsato o revocato, il cliente viene rimosso come collaboratore.

## Configurazione richiesta

| Campo | Necessario | Descrizione |
|---|---|---|
| `target_id` | Sì | Il repository a cui invitare il cliente. Il selettore del repository del dashboard lo riempie per te. |
| `permission` | Sì | Uno di `pull`, `push`, `triage`, `maintain`, `admin`. |

## Creare tramite API

<CodeGroup>

```typescript TypeScript theme={null}
const entitlement = await client.entitlements.create({
  name: 'Code Share Repository',
  integration_type: 'github',
  integration_config: {
    target_id: 'acme/private-sdk',
    permission: 'pull',
  },
});
```

```python Python theme={null}
client.entitlements.create(
    name="Code Share Repository",
    integration_type="github",
    integration_config={
        "target_id": "acme/private-sdk",
        "permission": "pull",
    },
)
```

```go Go theme={null}
client.Entitlements.New(ctx, dodopayments.EntitlementNewParams{
  Name:            dodopayments.F("Code Share Repository"),
  IntegrationType: dodopayments.F(dodopayments.EntitlementIntegrationTypeGithub),
  IntegrationConfig: dodopayments.F[dodopayments.IntegrationConfigUnionParam](
    dodopayments.IntegrationConfigGitHubConfigParam{
      TargetID:   dodopayments.F("acme/private-sdk"),
      Permission: dodopayments.F("pull"),
    },
  ),
})
```

</CodeGroup>

## Webhooks

Gli eventi standard del [webhook](/developer-resources/webhooks/intents/entitlement-grant) `entitlement_grant.*` coprono il flusso GitHub:

- `entitlement_grant.created` viene attivato con `status: "Pending"` e `oauth_url` ancora `null`; l'URL di autorizzazione GitHub viene popolato quando il cliente avvia il flusso di accettazione dalla propria email di consegna o dal customer portal.
- `entitlement_grant.delivered` viene attivato una volta creata l'invito al collaboratore.
- `entitlement_grant.failed` viene attivato con `error_code: "github_permission_denied"` (o un valore simile) se la GitHub App perde l'accesso al repository.

## Risoluzione dei problemi

<AccordionGroup>
<Accordion title="Repository picker is empty">
L'app GitHub Dodo Payments deve essere installata sull'org o sull'utente che possiede il repository. Apri **Diritti → Integrazioni → GitHub** e reinstalla l'app, assicurandoti di concedere l'accesso ai repository pertinenti.
</Accordion>

<Accordion title="Grant fails with permission_denied">
L'installazione dell'app GitHub non ha più accesso al repository, o il repository è stato rinominato/trasferito. Concedi nuovamente l'accesso all'app e il prossimo re-grant avrà successo.
</Accordion>

<Accordion title="Customer hasn't accepted the invite">
I clienti devono accettare l'invitation di GitHub dalla pagina delle notifiche o facendo clic sul link nell'email. Finché non accettano, rimangono "invitati", ma non possono clonare il repository. Dal punto di vista di Dodo Payments, il grant è ancora `Delivered`; l'invitation è ciò che emettiamo.
</Accordion>
</AccordionGroup>
