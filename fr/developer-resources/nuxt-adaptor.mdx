## Présentation

<Info>
Ce guide explique comment intégrer Dodo Payments à votre application Nuxt à l’aide du module Nuxt officiel. Vous apprendrez à configurer les routes API du checkout, du portail client et des webhooks, ainsi qu’à gérer les variables d’environnement de manière sécurisée.
</Info>

## Installation

<Steps>
<Step title="Install the Nuxt module">
Exécutez la commande suivante à la racine de votre projet :

```bash
npm install @dodopayments/nuxt
```

</Step>
<Step title="Register the module in nuxt.config.ts">
Ajoutez <code>@dodopayments/nuxt</code> à votre tableau <code>modules</code> et configurez-le :

```typescript nuxt.config.ts expandable
export default defineNuxtConfig({
  modules: ["@dodopayments/nuxt"],
  devtools: { enabled: true },
  compatibilityDate: "2025-02-25",
  runtimeConfig: {
    private: {
      bearerToken: process.env.NUXT_PRIVATE_BEARER_TOKEN,
      webhookKey: process.env.NUXT_PRIVATE_WEBHOOK_KEY,
      environment: process.env.NUXT_PRIVATE_ENVIRONMENT,
      returnUrl: process.env.NUXT_PRIVATE_RETURNURL
    },
  }
});
```

</Step>
</Steps>

<Warning>
Ne validez jamais votre fichier <code>.env</code> ni vos secrets dans le contrôle de version.
</Warning>

## Gestionnaire de route du checkout

<Info>
Dodo Payments prend en charge trois types de flux de paiement pour intégrer les paiements à votre site web ; cet adaptateur prend en charge tous les types de flux de paiement.
</Info>

- **Liens de paiement statiques :** URL partageables instantanément pour collecter rapidement des paiements, sans code.
- **Liens de paiement dynamiques :** générez des liens de paiement par programmation avec des informations personnalisées à l’aide de l’API ou des SDK.
- **Sessions de checkout :** créez des expériences de checkout sécurisées et personnalisables avec des paniers de produits et des informations client préconfigurés.

<AccordionGroup>
<Accordion title="Static Checkout (GET)">

### Paramètres de requête pris en charge
<ParamField query="productId" type="string" required>

</ParamField>

</ParamField>

</Warning>

### Format de la réponse
Le checkout statique renvoie une réponse JSON contenant l’URL du checkout :

```json
{
  "checkout_url": "https://checkout.dodopayments.com/..."
}
```

</Accordion>
<Accordion title="Dynamic Checkout (POST)">
- Envoyez les paramètres dans le corps JSON d’une requête POST.
- Prend en charge les paiements ponctuels et récurrents.
- Pour obtenir la liste complète des champs pris en charge dans le corps de la requête POST, consultez :
  - [Corps de la requête pour un produit à paiement unique](https://docs.dodopayments.com/api-reference/payments/post-payments)
  - [Corps de la requête pour un produit par abonnement](https://docs.dodopayments.com/api-reference/subscriptions/post-subscriptions)

### Format de la réponse
Le checkout dynamique renvoie une réponse JSON contenant l’URL du checkout :

```json
{
  "checkout_url": "https://checkout.dodopayments.com/..."
}
```

</Accordion>
<Accordion title="Checkout Sessions (POST)">
Les sessions de checkout fournissent une expérience de checkout hébergée et plus sécurisée, qui gère l’intégralité du flux de paiement pour les achats ponctuels et les abonnements, avec un contrôle complet de la personnalisation.

Consultez le [Guide d’intégration des sessions de checkout](https://docs.dodopayments.com/developer-resources/checkout-session) pour plus de détails et la liste complète des champs pris en charge.

### Format de la réponse
Les sessions de checkout renvoient une réponse JSON contenant l’URL du checkout :

```json
{
  "checkout_url": "https://checkout.dodopayments.com/session/..."
}
```

</Accordion>

## Gestionnaire de route webhook

- **Méthode :** seules les requêtes POST sont prises en charge. Les autres méthodes renvoient 405.
- **Vérification de la signature :** vérifie la signature du webhook à l’aide de <code>webhookKey</code>. Renvoie 401 si la vérification échoue.
- **Validation de la charge utile :** validée avec Zod. Renvoie 400 si la charge utile est invalide.
- **Gestion des erreurs :**
  - 401 : signature invalide
  - 400 : charge utile invalide
  - 500 : erreur interne lors de la vérification
- **Routage des événements :** appelle le gestionnaire d’événements approprié en fonction du type de charge utile.
