## Overview

Test mode lets you simulate payments without processing real transactions. All test credentials only work in test mode — never use them in production.

<CardGroup cols={3}>
<Card title="No Real Charges" icon="shield-check">
Test transactions don't process actual payments or affect real accounts.
</Card>

<Card title="Full API Access" icon="code">
All API endpoints work identically in test and live modes.
</Card>

<Card title="Webhook Testing" icon="webhook">
Webhooks fire for test transactions just like production.
</Card>
</CardGroup>

<Warning>
Test credentials only work in test mode. Attempting to use them in live mode will result in payment failures.
</Warning>

### How to Test Renewal Failure

<Steps>
<Step title="Create a test subscription">
Create a subscription with your test API keys using a **success** test card (for example, `4242 4242 4242 4242`). The initial charge should succeed and the subscription should become active.
</Step>

<Step title="Swap in the failure card via Customer Portal">
Open the [Customer Portal](/features/customer-portal), find the subscription you just created, and click **Update Payment Method**. Enter the failure test card `4000 0000 0000 0341` (Expiry: `12/34`, CVC: `123`) and save it as the subscription's payment method.
</Step>

<Step title="Advance the next billing date (optional)">
To trigger renewal immediately instead of waiting for the natural billing cycle, use the Update Subscription API to set `next_billing_date` to the current UTC time. The value must be an ISO 8601 / RFC 3339 UTC timestamp (the `Z` suffix is required).

```http
PATCH /subscriptions/{subscription_id}
{
  "next_billing_date": "2026-05-03T00:00:00Z"
}
```

See the [Update Subscription API reference](/api-reference/subscriptions/patch-subscriptions#body-next-billing-date-one-of-0) for details.
</Step>

<Step title="Verify the failure">
On the next billing attempt:

- The renewal charge declines on the failure card
- The subscription moves to **On-Hold** status
- A `payment.failed` webhook event is delivered
- The customer can return to the Customer Portal to update the payment method and retry
</Step>
</Steps>

<Warning>
This card is specifically for testing renewal failures. The charge will decline on the next billing date, allowing you to test payment retry logic, customer notifications, and failure handling.
</Warning>

## Test UPI

UPI testing uses special VPA (Virtual Payment Address) identifiers that simulate different payment outcomes.

| Status | UPI ID |
| :----- | :----- |
| Success | `success@upi` |
| Failure | `failure@upi` |

### Requirements for UPI Testing

- Billing country must be set to `IN`
- Currency must be `INR`
- For non-Indian merchants: Adaptive Currency must be enabled

For complete UPI documentation including RBI mandate testing for subscriptions, see the [India Payment Methods](/features/payment-methods/india) page.

### Afterpay Testing

<Steps>
<Step title="Select Afterpay">
Choose Afterpay as the payment method in checkout and click Pay.
</Step>

<Step title="Test successful payment">
Use any valid email address and shipping address for successful payments.
</Step>

<Step title="Test failed authentication">
Pour simuler un échec, fermez la fenêtre modale Afterpay sur la page de redirection. Le paiement passe de `requires_customer_action` à `requires_payment_method`.
</Step>
</Steps>

<Note>
Afterpay requires a minimum transaction amount of **$50.01** to appear as a payment option.
</Note>

Pour consulter la documentation complète sur le BNPL, y compris les tests B2B de Billie, consultez la page [Buy Now Pay Later](/features/payment-methods/bnpl).

## Tester les portefeuilles numériques

### Apple Pay

<Steps>
<Step title="Enable test mode">
Utilisez vos clés API de test Dodo Payments.
</Step>

<Step title="Add a card to Apple Wallet">
Ajoutez une carte réelle à votre Apple Wallet. En mode test, la carte ne sera pas débitée.
</Step>

<Step title="Complete test purchase">
Ouvrez le checkout sur un appareil Apple et terminez le parcours Apple Pay.
</Step>
</Steps>

<Warning>
Apple Pay nécessite HTTPS. Il ne s'affichera pas sur `localhost` sans configuration SSL appropriée. La vérification du domaine doit également être terminée.
</Warning>

### Google Pay

<Steps>
<Step title="Join the test card group">
[Rejoignez le groupe de cartes de test Google Pay](https://groups.google.com/g/googlepay-test-mode-stub-data) pour que des cartes de test soient automatiquement ajoutées à votre portefeuille.
</Step>

<Step title="Enable test mode">
Utilisez vos clés API de test Dodo Payments.
</Step>

<Step title="Complete test purchase">
Sélectionnez l'une des cartes de test dans Google Pay pour terminer la transaction.
</Step>
</Steps>

### Amazon Pay, Cash App Pay et RevolutPay

Utilisez vos clés API de test et suivez le parcours de checkout standard. Les transactions de test sont simulées sans débit réel.

Pour consulter la documentation complète sur les portefeuilles numériques, y compris la vérification du domaine pour Apple Pay, consultez la page [Portefeuilles numériques](/features/payment-methods/digital-wallets).

## Test ACH Direct Debit

ACH Direct Debit peut être testé en mode Test en saisissant des coordonnées bancaires de test lors du paiement.

<Steps>
<Step title="Enable test mode">
Utilisez vos clés API de test Dodo Payments.
</Step>

<Step title="Set currency and billing address">
Définissez la devise de facturation sur `USD` et le pays de l’adresse de facturation sur `US`. ACH n’est pas proposé en dehors de cette combinaison.
</Step>

<Step title="Use a one-time payment">
ACH n’est pas disponible lors des paiements d’abonnements. Testez-le donc avec un paiement ponctuel.
</Step>

<Step title="Enter the test bank details">
Saisissez l’une des paires de numéros de routage et de compte de test ci-dessous, puis vérifiez que votre gestionnaire de webhooks reçoit le statut final du paiement — les paiements ACH sont confirmés de manière asynchrone, et non lors du paiement.
</Step>
</Steps>

### Comptes bancaires de test

Utilisez le numéro de routage `110000000` avec l’un des numéros de compte suivants :

| Numéro de compte | Comportement |
| :------------- | :------- |
| `000123456789` | Le paiement aboutit. |
| `000222222227` | Le paiement échoue en raison de fonds insuffisants. |
| `000111111113` | Le paiement échoue car le compte est clôturé. |
| `000555555559` | Le paiement aboutit, puis déclenche une contestation. |
| `000000000009` | Le paiement reste indéfiniment en cours de traitement. |

Pour consulter la liste complète des comptes de test, reportez-vous à la page [ACH Direct Debit](/features/payment-methods/ach#testing).

## Tester les méthodes européennes

Les méthodes de paiement européennes (iDEAL, Bancontact, EPS, Multibanco) peuvent être testées en mode Test.

<Steps>
<Step title="Enable test mode">
Utilisez vos clés API de test Dodo Payments.
</Step>

<Step title="Set billing address">
Définissez le pays de l’adresse de facturation pour qu’il corresponde à la méthode de paiement :
- `NL` pour iDEAL
- `BE` pour Bancontact
- `AT` pour EPS
- `PT` pour Multibanco
</Step>

<Step title="Set currency">
Les méthodes européennes nécessitent la devise EUR.
</Step>

<Step title="Complete test flow">
Suivez le parcours d’authentification bancaire simulé dans l’environnement de test.
</Step>
</Steps>

### IBAN SEPA Direct Debit de test

SEPA Direct Debit nécessite la devise EUR et une adresse de facturation située dans la zone euro. Utilisez ces IBAN de test pour forcer un résultat spécifique :

| IBAN de test | Comportement |
| :-------- | :------- |
| `DE89370400440532013000` | Le paiement aboutit. |
| `DE62370400440532013001` | Le paiement échoue. |
| `DE35370400440532013002` | Le paiement aboutit, puis est immédiatement contesté. |
| `DE65370400440002222227` | Le paiement échoue en raison de fonds insuffisants. |

Pour consulter la liste complète des IBAN de test, y compris les valeurs par pays, reportez-vous à la page [Europe](/features/payment-methods/europe#sepa-test-ibans).

Pour consulter la documentation complète sur les méthodes de paiement européennes, reportez-vous à la page [Europe](/features/payment-methods/europe).

## Bonnes pratiques de test

<AccordionGroup>
<Accordion title="Test all payment scenarios">
Ne testez pas uniquement les paiements réussis. Testez les refus, les annulations et les cas particuliers, comme les fonds insuffisants.
</Accordion>

<Accordion title="Verify webhook handling">
Assurez-vous que vos endpoints de webhook traitent correctement tous les types d’événements, en particulier `payment.succeeded`, `payment.failed` et les événements d’abonnement.

Utilisez la [Dodo Payments CLI](/developer-resources/sdks/cli#webhooks) pour tester les webhooks localement :
- `dodo wh listen` transfère les webhooks de test en direct vers votre serveur local
- `dodo wh trigger` envoie des charges utiles simulées pour tous les types d’événements de webhook pris en charge
</Accordion>

<Accordion title="Test on real devices">
Pour Apple Pay et Google Pay, effectuez les tests sur de véritables appareils iOS et Android. Les simulateurs ne reproduisent pas complètement le comportement des portefeuilles électroniques.
</Accordion>

<Accordion title="Test regional methods with correct addresses">
Les méthodes de paiement régionales (UPI, iDEAL, etc.) nécessitent des adresses de facturation correspondantes. Une adresse de facturation aux États-Unis ne permettra pas d’afficher iDEAL.
</Accordion>

<Accordion title="Verify minimum amounts">
Les méthodes BNPL nécessitent un minimum de 50,01 $. Vérifiez qu’elles s’affichent ou se masquent correctement en fonction du total du panier.
</Accordion>
</AccordionGroup>
