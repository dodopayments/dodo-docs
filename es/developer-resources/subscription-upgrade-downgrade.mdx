## ¿Qué es una actualización o degradación de suscripción?

Cambiar de plan permite mover a un cliente entre niveles o cantidades de suscripción. Úselo para:
- Alinear precios con uso o características
- Pasar de mensual a anual (o viceversa)
- Ajustar la cantidad para productos basados en asientos

<Info>
Los cambios de plan pueden desencadenar un cargo inmediato dependiendo del modo de prorrateo que elija.
</Info>

## Cuándo usar cambios de plan

- Actualizar cuando un cliente necesita más características, uso o asientos
- Degradar cuando el uso disminuye
- Migrar usuarios a un nuevo producto o precio sin cancelar su suscripción

## Requisitos previos

Antes de implementar cambios en el plan de suscripción, asegúrese de tener:

- Una cuenta de comerciante de Dodo Payments con productos de suscripción activos
- Credenciales de API (clave de API y clave secreta de webhook) del panel de control
- Una suscripción activa existente para modificar
- Punto final de webhook configurado para manejar eventos de suscripción

<Info>
Para instrucciones de configuración detalladas, consulte nuestra [Guía de integración](/developer-resources/integration-guide#dashboard-setup).
</Info>

## Guía de implementación paso a paso

Siga esta guía completa para implementar cambios en el plan de suscripción en su aplicación:

<Steps>
<Step title="Entender los requisitos de cambio de plan">
Antes de implementar, determine:
- Qué productos de suscripción se pueden cambiar a cuáles otros
- Qué modo de prorrateo se ajusta a su modelo de negocio
- Cómo manejar los cambios de plan fallidos de manera adecuada
- Qué eventos de webhook rastrear para la gestión del estado

<Tip>
Pruebe los cambios de plan a fondo en modo de prueba antes de implementarlos en producción.
</Tip>
</Step>

<Step title="Elija su estrategia de prorrateo">
Seleccione el enfoque de facturación que se alinee con las necesidades de su negocio:

<Tabs>
<Tab title="prorrateado_inmediatamente">
Mejor para: aplicaciones SaaS que desean cobrar de manera justa por el tiempo no utilizado
- Calcula el monto prorrateado exacto basado en el tiempo restante del ciclo
- Cobra un monto prorrateado basado en el tiempo no utilizado restante en el ciclo
- Proporciona facturación transparente a los clientes
</Tab>

<Tab title="diferencia_inmediatamente">
Mejor para: escenarios claros de actualización/degradación
- Actualización: cobra la diferencia inmediata (por ejemplo, $30→$80 = cobra $50)
- Degradación: acredita el valor restante para renovaciones futuras
- Simplifica la lógica de facturación y la comunicación con el cliente
</Tab>

<Tab title="total_inmediatamente">
Mejor para: cuando desea restablecer el ciclo de facturación
- Cobra el monto total del nuevo plan de inmediato
- Ignora el tiempo restante del antiguo plan
- Útil para transiciones de anual a mensual
</Tab>
</Tabs>
</Step>

<Step title="Implementar la API de cambio de plan">
Utilice la API de cambio de plan para modificar los detalles de la suscripción:

<ParamField path="subscription_id" type="string" required>
El ID de la suscripción activa a modificar.
</ParamField>

<ParamField path="product_id" type="string" required>
El nuevo ID de producto al que cambiar la suscripción.
</ParamField>

<ParamField path="quantity" type="integer" default="1">
Número de unidades para el nuevo plan (para productos basados en asientos).
</ParamField>

<ParamField path="proration_billing_mode" type="string" required>
Cómo manejar la facturación inmediata: `prorated_immediately`, `full_immediately`, o `difference_immediately`.
</ParamField>

<ParamField path="addons" type="array">
Complementos opcionales para el nuevo plan. Dejar esto vacío elimina cualquier complemento existente.
</ParamField>
</Step>

<Step title="Manejar eventos de webhook">
Configure el manejo de webhook para rastrear los resultados del cambio de plan:

- `subscription.active`: Cambio de plan exitoso, suscripción actualizada
- `subscription.plan_changed`: Plan de suscripción cambiado (actualización/degradación/actualización de complemento)
- `subscription.on_hold`: Fallo en el cargo por cambio de plan, suscripción pausada
- `payment.succeeded`: Cargo inmediato por cambio de plan exitoso
- `payment.failed`: Cargo inmediato fallido

<Warning>
Siempre verifique las firmas de los webhooks e implemente un procesamiento de eventos idempotente.
</Warning>
</Step>

<Step title="Actualizar el estado de su aplicación">
Basado en eventos de webhook, actualice su aplicación:
- Conceder/revocar características según el nuevo plan
- Actualizar el panel del cliente con los nuevos detalles del plan
- Enviar correos electrónicos de confirmación sobre cambios de plan
- Registrar cambios de facturación para fines de auditoría
</Step>

<Step title="Probar y monitorear">
Pruebe a fondo su implementación:
- Pruebe todos los modos de prorrateo con diferentes escenarios
- Verifique que el manejo de webhooks funcione correctamente
- Monitoree las tasas de éxito de los cambios de plan
- Configure alertas para cambios de plan fallidos

<Check>
Su implementación de cambio de plan de suscripción ahora está lista para su uso en producción.
</Check>
</Step>
</Steps>

## Gestión de complementos

Al cambiar los planes de suscripción, también puede modificar los complementos:

```javascript
// Add addons to the new plan
await client.subscriptions.changePlan('sub_123', {
  product_id: 'prod_new',
  quantity: 1,
  proration_billing_mode: 'difference_immediately',
  addons: [
    { addon_id: 'addon_123', quantity: 2 }
  ]
});

// Remove all existing addons
await client.subscriptions.changePlan('sub_123', {
  product_id: 'prod_new',
  quantity: 1,
  proration_billing_mode: 'difference_immediately',
  addons: [] // Empty array removes all existing addons
});
```

<Info>
Los complementos se incluyen en el cálculo de prorrateo y se cobrarán de acuerdo con el modo de prorrateo seleccionado.
</Info>

## Modos de prorrateo

Elija cómo facturar al cliente al cambiar de planes:

#### `prorated_immediately`
- Cobra por la diferencia parcial en el ciclo actual
- Si está en prueba, cobra de inmediato y cambia al nuevo plan ahora
- Degradación: puede generar un crédito prorrateado aplicado a renovaciones futuras

#### `full_immediately`
- Cobra el monto total del nuevo plan de inmediato
- Ignora el tiempo restante del antiguo plan

<Info>
Los créditos creados por degradaciones utilizando <code>difference_immediately</code> son específicos de la suscripción y distintos de <a href="/features/customer-credit">Créditos de cliente</a>. Se aplican automáticamente a las renovaciones futuras de la misma suscripción y no son transferibles entre suscripciones.
</Info>

#### `difference_immediately`
- Actualización: cobra inmediatamente la diferencia de precio entre los planes antiguo y nuevo
- Degradación: agrega el valor restante como crédito interno a la suscripción y se aplica automáticamente en las renovaciones

### Escenarios de ejemplo

<Tip>
Elija `prorated_immediately` para una contabilidad justa del tiempo; elija `full_immediately` para reiniciar la facturación; use `difference_immediately` para actualizaciones simples y crédito automático en degradaciones.
</Tip>

## Manejo de webhooks

Rastree el estado de la suscripción a través de webhooks para confirmar cambios de plan y pagos.

### Tipos de eventos a manejar
- `subscription.active`: suscripción activada
- `subscription.plan_changed`: plan de suscripción cambiado (actualización/degradación/cambios de complemento)
- `subscription.on_hold`: cargo fallido, suscripción pausada
- `subscription.renewed`: renovación exitosa
- `payment.succeeded`: pago por cambio de plan o renovación exitoso
- `payment.failed`: pago fallido

<Info>
Recomendamos impulsar la lógica empresarial a partir de eventos de suscripción y utilizar eventos de pago para confirmación y conciliación.
</Info>

### Verificar firmas y manejar intenciones

<Tabs>
  <Tab title="Manejador de rutas de Next.js">

    ```javascript
    import { NextRequest, NextResponse } from 'next/server';
    
    export async function POST(req) {
      const webhookId = req.headers.get('webhook-id');
      const webhookSignature = req.headers.get('webhook-signature');
      const webhookTimestamp = req.headers.get('webhook-timestamp');
      const secret = process.env.DODO_WEBHOOK_SECRET;
    
      const payload = await req.text();
      // verifySignature is a placeholder – in production, use a Standard Webhooks library
      const { valid, event } = await verifySignature(
        payload,
        { id: webhookId, signature: webhookSignature, timestamp: webhookTimestamp },
        secret
      );
      if (!valid) return NextResponse.json({ error: 'Invalid signature' }, { status: 400 });
    
      switch (event.type) {
        case 'subscription.active':
          // mark subscription active in your DB
          break;
        case 'subscription.plan_changed':
          // refresh entitlements and reflect the new plan in your UI
          break;
        case 'subscription.on_hold':
          // notify user to update payment method
          break;
        case 'subscription.renewed':
          // extend access window
          break;
        case 'payment.succeeded':
          // reconcile payment for plan change
          break;
        case 'payment.failed':
          // log and alert
          break;
        default:
          // ignore unknown events
          break;
      }
    
      return NextResponse.json({ received: true });
    }
    ```

## Mejores prácticas

Siga estas recomendaciones para cambios de plan de suscripción confiables:

### Estrategia de cambio de plan
- **Pruebe a fondo**: Siempre pruebe los cambios de plan en modo de prueba antes de la producción
- **Elija el prorrateo con cuidado**: Seleccione el modo de prorrateo que se alinee con su modelo de negocio
- **Maneje fallos de manera adecuada**: Implemente un manejo de errores adecuado y lógica de reintento
- **Monitoree las tasas de éxito**: Rastree las tasas de éxito/fallo de los cambios de plan e investigue problemas

### Implementación de webhook
- **Verifique las firmas**: Siempre valide las firmas de los webhooks para garantizar la autenticidad
- **Implemente idempotencia**: Maneje eventos de webhook duplicados de manera adecuada
- **Procese de manera asíncrona**: No bloquee las respuestas de webhook con operaciones pesadas
- **Registre todo**: Mantenga registros detallados para depuración y fines de auditoría

### Experiencia del usuario
- **Comunique claramente**: Informe a los clientes sobre cambios de facturación y tiempos
- **Proporcione confirmaciones**: Envíe correos electrónicos de confirmación para cambios de plan exitosos
- **Maneje casos extremos**: Considere períodos de prueba, prorrateos y pagos fallidos
- **Actualice la interfaz de usuario de inmediato**: Refleje los cambios de plan en la interfaz de su aplicación

## Problemas comunes y soluciones

Resuelva problemas típicos encontrados durante los cambios de plan de suscripción:

<AccordionGroup>
<Accordion title="Cargo creado pero suscripción no actualizada">
**Síntomas**: La llamada a la API tiene éxito pero la suscripción permanece en el antiguo plan

**Causas comunes**:
- El procesamiento del webhook falló o se retrasó
- El estado de la aplicación no se actualizó después de recibir webhooks
- Problemas de transacción de base de datos durante la actualización del estado

**Soluciones**:
- Implemente un manejo robusto de webhooks con lógica de reintento
- Use operaciones idempotentes para actualizaciones de estado
- Agregue monitoreo para detectar y alertar sobre eventos de webhook perdidos
- Verifique que el punto final del webhook sea accesible y responda correctamente
</Accordion>

<Accordion title="Créditos no aplicados después de la degradación">
**Síntomas**: El cliente degrada pero no ve el saldo de crédito

**Causas comunes**:
- Expectativas del modo de prorrateo: las degradaciones acreditan la diferencia total del precio del plan con `difference_immediately`, mientras que `prorated_immediately` crea un crédito prorrateado basado en el tiempo restante en el ciclo
- Los créditos son específicos de la suscripción y no se transfieren entre suscripciones
- El saldo de crédito no es visible en el panel del cliente

**Soluciones**:
- Use `difference_immediately` para degradaciones cuando desee créditos automáticos
- Explique a los clientes que los créditos se aplican a las renovaciones futuras de la misma suscripción
- Implemente un portal para clientes para mostrar saldos de crédito
- Verifique la vista previa de la próxima factura para ver los créditos aplicados
</Accordion>

<Accordion title="Fallo en la verificación de la firma del webhook">
**Síntomas**: Eventos de webhook rechazados debido a firma no válida

**Causas comunes**:
- Clave secreta de webhook incorrecta
- Cuerpo de la solicitud en bruto modificado antes de la verificación de la firma
- Algoritmo de verificación de firma incorrecto

**Soluciones**:
- Verifique que esté utilizando el correcto `DODO_WEBHOOK_SECRET` del panel de control
- Lea el cuerpo de la solicitud en bruto antes de cualquier middleware de análisis JSON
- Use la biblioteca estándar de verificación de webhook para su plataforma
- Pruebe la verificación de la firma del webhook en el entorno de desarrollo
</Accordion>

<Accordion title="El cambio de plan falla con error 422">
**Síntomas**: La API devuelve un error 422 Entidad no procesable

**Causas comunes**:
- ID de suscripción o ID de producto no válidos
- Suscripción no en estado activo
- Falta de parámetros requeridos
- Producto no disponible para cambios de plan

**Soluciones**:
- Verifique que la suscripción exista y esté activa
- Verifique que el ID de producto sea válido y esté disponible
- Asegúrese de que se proporcionen todos los parámetros requeridos
- Revise la documentación de la API para los requisitos de parámetros
</Accordion>

<Accordion title="El cargo inmediato falla durante el cambio de plan">
**Síntomas**: Cambio de plan iniciado pero el cargo inmediato falla

**Causas comunes**:
- Fondos insuficientes en el método de pago del cliente
- Método de pago caducado o no válido
- El banco rechazó la transacción
- La detección de fraude bloqueó el cargo

**Soluciones**:
- Maneje los eventos de webhook `payment.failed` de manera adecuada
- Notifique al cliente que actualice su método de pago
- Implemente lógica de reintento para fallos temporales
- Considere permitir cambios de plan con cargos inmediatos fallidos
</Accordion>

<Accordion title="Suscripción en espera después del cambio de plan">
**Síntomas**: El cargo por cambio de plan falla y la suscripción pasa al estado `on_hold`

**Qué sucede**:
Cuando un cargo por cambio de plan falla, la suscripción se coloca automáticamente en estado `on_hold`. La suscripción no se renovará automáticamente hasta que se actualice el método de pago.

**Solución**: Actualice el método de pago para reactivar la suscripción

Para reactivar una suscripción del estado `on_hold` después de un cambio de plan fallido:

1. **Actualice el método de pago** utilizando la API de actualización de método de pago
2. **Creación automática de cargo**: La API crea automáticamente un cargo por las deudas restantes
3. **Generación de factura**: Se genera una factura para el cargo
4. **Procesamiento de pago**: El pago se procesa utilizando el nuevo método de pago
5. **Reactivación**: Tras el pago exitoso, la suscripción se reactiva al estado `active`

<CodeGroup>

```javascript Node.js
// Reactivate subscription from on_hold after failed plan change
async function reactivateAfterFailedPlanChange(subscriptionId) {
  // Update payment method - automatically creates charge for remaining dues
  const response = await client.subscriptions.updatePaymentMethod(subscriptionId, {
    type: 'new',
    return_url: 'https://example.com/return'
  });
  
  if (response.payment_id) {
    console.log('Charge created for remaining dues:', response.payment_id);
    console.log('Payment link:', response.payment_link);
    
    // Redirect customer to payment_link to complete payment
    // Monitor webhooks for:
    // 1. payment.succeeded - charge succeeded
    // 2. subscription.active - subscription reactivated
  }
  
  return response;
}

// Or use existing payment method if available
async function reactivateWithExistingPaymentMethod(subscriptionId, paymentMethodId) {
  const response = await client.subscriptions.updatePaymentMethod(subscriptionId, {
    type: 'existing',
    payment_method_id: paymentMethodId
  });
  
  // Monitor webhooks for payment.succeeded and subscription.active
  return response;
}
```

### Códigos de estado HTTP

<AccordionGroup>
<Accordion title="200 OK">
Solicitud de cambio de plan procesada con éxito. La suscripción se está actualizando y el procesamiento de pagos ha comenzado.
</Accordion>

<Accordion title="400 Bad Request">
Parámetros de solicitud no válidos. Verifique que se proporcionen y formateen correctamente todos los campos requeridos.
</Accordion>

<Accordion title="401 Unauthorized">
Clave de API no válida o faltante. Verifique que su `DODO_PAYMENTS_API_KEY` sea correcto y tenga los permisos adecuados.
</Accordion>

<Accordion title="404 Not Found">
ID de suscripción no encontrado o no pertenece a su cuenta.
</Accordion>

<Accordion title="422 Unprocessable Entity">
La suscripción no se puede cambiar (por ejemplo, ya cancelada, producto no disponible, etc.).
</Accordion>

<Accordion title="500 Internal Server Error">
Ocurrió un error en el servidor. Reintente la solicitud después de un breve retraso.
</Accordion>
</AccordionGroup>
